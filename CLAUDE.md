# Cube Chaos modding — project rules

This repo holds one or more Cube Chaos mods plus the Claude Code skills used to build them. It is meant to be shared (git repo, possibly with strangers), so it deliberately contains **no personal data** — see `.gitignore` for what's kept out (local permission files, personal working-style preferences, etc). Keep it that way: don't put real names, emails, absolute machine-specific paths, or session IDs into anything under version control.

## Setting up a new machine or a new contributor

Before diving into a modding task on a machine that hasn't used this repo before (a fresh clone, a different contributor, or the repo owner on a second device), use the `cube-chaos-repo-setup` skill — it decides how git/GitHub should work here (your own fork, a branch on a shared repo, local-only git, or no git at all, each with a stated cost/benefit), checks that the tools every other skill assumes are actually present (`git`, `python3`+Pillow, `bash`, optionally `gh`/`jq`), and runs a one-time personal-preferences questionnaire into a gitignored `.claude/preferences.local.md` (preview-gate strictness, sprite art effort, naming/color check-ins, README timing, proactive write-back, test-launch behavior). `cube-chaos-orchestrator`'s Step 0.5 offers this automatically the first time it notices that file is missing — it's a one-time offer, not a recurring nag, and skipping it just means every preference below defaults to the "Recommended" option documented in that skill.

## The one hard rule: never edit base-game files

`GameData/Base_Core/`, `GameData/Characters/`, `GameData/Main/`, `GameData/Extra_Mechanics/`, `GameData/Modding_Example/`, and the root `ModdingInfo.txt` / `ModdingExplanation.txt` are the game's own files, not this repo's mod content. **Never edit, move, or delete anything under those paths — including sprite sheets.** If a task seems to require it (e.g. "just tweak this one base cube," "add my sprite into the base game's own sheet"), **stop and explicitly warn the user instead of proceeding**, even if only part of a larger task touches them. Read from them freely (grepping for real DSL examples, sampling colors, checking conventions) — reading is always fine, writing never is.

All mod content lives under `GameData/<ModName>/`, one folder per mod. `BelongsTo:` can reference base-game classes/species/perks across packages with no special syntax — that's the correct way to "attach" content to base-game systems, never editing the base files themselves.

## Where to start

Use the `cube-chaos-orchestrator` skill (or just say what you want to do — "create a mod", "edit a mod", "add a new perk," etc.) as the entry point for any modding session. It asks new-mod-vs-existing, routes to the right content-type workflow, and makes sure the domain skills below get invoked in the right order and nothing gets marked "done" without a test-launch and log check.

The domain skills hold the actual technical knowledge and are usually invoked *by* the orchestrator, but are also fine to use directly for a narrow question:
- `cube-chaos-scripting` — the `CUBE:`/`PERK:`/`Ability:` DSL itself.
- `cube-chaos-scenario-scripting` — the `SCENARIO:`/`MAP:`/`NODEMAP:`/`CHOICE:` DSL for battle maps, terrain, campaign maps, challenges, and reward screens.
- `cube-chaos-rule-text` — `Text:`/`Description:` prose conventions.
- `cube-chaos-sprite-art` — sprite sheet sizing, colors, and the full border-pattern library (generate borders from scratch, no reference-file extraction needed).
- `cube-chaos-balancing` — mana/hp/`IDENT` stats and perk `Value:`/`BalanceCap:` pricing.
- `cube-chaos-mod-setup` — mod folder scaffolding, `Loading_Order.txt`, filename-collision pitfalls, the launch-and-check-logs test loop.
- `cube-chaos-audit` — checks an *existing* mod's content against the conventions the skills above already document (ability guards, rule-text wording, `IDENT`/`Value:` balancing, sprite border alignment). Reports findings for approval before fixing anything, since a deviation may have been deliberate. Its checklist only indexes the other skills' rules — it never restates them, so a convention still only has one home.
- `cube-chaos-doc-audit` — the same "reports findings, don't auto-fix" discipline as `cube-chaos-audit`, but pointed at the skill/reference/README tree itself rather than any mod's game content: hardcoded lists that drifted from reality, missing or one-directional cross-references between skills, self-contradictions, and README prose that's drifted from the mod it describes. On-demand/periodic, not a hook — too expensive to run on every edit.

## The highest-priority standing task: turn every lesson into a *rule*, not a war story

**Improving this workflow and these skills with what a task teaches is the single most important
recurring job here — above finishing any individual mod feature.** But a lesson only counts once it's
written as a **prescriptive rule that tells the next session what to DO**, not as a documented "gotcha"
describing what went wrong. Those are different artifacts and only one of them prevents recurrence.

The test, applied to every write-back: *could someone follow this without already knowing the story
behind it?* A gotcha says "inserting a block mid-file shifts every later sprite — this happened to
`Hellstorm` in July." A rule says "**append the block at the end of the file; verify the end with
`grep -n '^CUBE:\|^PERK:' <file>` first; draw its tile in the next free slot.**" The first is a fact
about the past; the second is an instruction for the present. **Real precedent that forced this rule
into existence (2026-08-02):** the mid-file-insertion problem was already documented in *two* skills,
with three incidents' worth of narrative — and it still recurred that same day, because narrative isn't
a procedure. A rule that has been violated after being written down is evidence the writing was in the
wrong *form*, not evidence that people need reminding.

Concretely, when writing a finding back:
1. **Lead with the imperative** — the action to take, in the form of a step someone executes.
2. **Include the verification step**, if the failure was "I thought I had done it right." An
   instruction that can be silently satisfied wrongly needs a check that proves it was satisfied.
3. **Keep the evidence, demote it.** Incident history, `file:line` citations, decompiles and sample
   counts all stay (they're what makes a rule trustworthy and revisable) — but *after* the rule, not
   in place of it.
4. **Prefer removing the choice over documenting the hazard.** If a footgun can be designed out (a
   helper function that can't be called wrongly, a default that's always right), that beats any
   amount of warning text about it.

## Non-negotiable per-edit consistency rules

- **New `CUBE:`/`PERK:` blocks are appended at the END of their `.c.txt`, and their sprite tile goes in the next free slot at the END of the sheet — always, no exceptions for readability or thematic grouping.** Sprite tiles are assigned by pure file order, so any mid-file insert silently shifts every later block's icon onto the wrong entry, with no parse error. **Before inserting, run `grep -n "^CUBE:\|^PERK:" <file>` and confirm the last listed block is where you're about to append** — "it looked like the end of the file" is exactly how this has failed. If the sheet has no free slot, extend it by a whole row and keep the existing column count so no existing tile moves. Full step-by-step procedure and incident history in `cube-chaos-sprite-art`'s "Adding a new `CUBE:`/`PERK:` — the append procedure"; the same rule restated for authoring time in `cube-chaos-scripting`'s "Block formats".
- Any `Ability:`/`WorldAbility:` change (new or edited) gets its paired `Text:`/`Description:` written or re-checked in the *same* edit, never as a follow-up. See `cube-chaos-scripting`'s Text:/Description: requirement and `cube-chaos-rule-text`'s "rule text is never edited independently" principle.
- **Keyword abilities follow one fixed pattern.** A mod-defined `COMPOUND: ABILITY` that reads as a named keyword is written `Text: \C<R> <G> <B> <Name> [CODE 1] \B : \CN \N \C96 96 96 (<full explanation>) \CN End` — coloured header, then the explanation on its own line, parenthesised and dimmed to `96 96 96` so a player who knows the keyword can skip it. **Referencing a keyword in prose (revised 2026-07-29): use `\A <Name> <params>` for any keyword being *granted*, regardless of who defined it** — this mod's own compound or a base-game built-in alike (`\A PoisonX 1` is the base game's own idiom, confirmed real usage at `Characters/GeneralCubes.c.txt:399`; the Steam Workshop "Dinosaurs!" mod does this for base-game keywords throughout, e.g. `\A RetaliateX 1`). **Only when a keyword is being removed or tested rather than granted**, use the bare coloured name instead (`\A`'s "you have this" phrasing reads wrong there) — number before the name if a count is included (`\C255 38 0 1 Strength \CN`, not `Strength 1`), matching natural English word order. Take the exact colour and display name from the ability's own `ModdingInfo.txt` entry. Full rationale (including the now-accepted dimmed/undimmed styling tradeoff, and the caveats on punctuation after `\A`) lives in `cube-chaos-rule-text`.
- Every content change (new or edited `CUBE:`/`PERK:`) ends with an actual game launch and a `Log.txt` check (`%APPDATA%/CubeChaos/Log.txt`) before being reported as done — silent visual/logic bugs are common and don't always throw parse errors.
- **A new skill file, or a structural edit to an existing one (a new section, a reorganization, new cross-references added), isn't done until a scoped `cube-chaos-doc-audit` cold-test pass covers the changed files** — same weight as the launch-and-log gate above, just for the skill system instead of game content. Scope the pass to what changed this session, not a full repo sweep (see that skill's own procedure). Doesn't apply to a small wording-only fix — matching the same proportionality the launch gate already uses for a pure `Text:`/`Description:` reword. Real precedent, 2026-08-02: cold-testing this skill and its companion index immediately after writing them caught a skill claiming a `Research protocol` section it didn't actually have, plus a leftover contradiction in a file that had just been "fixed" minutes earlier — exactly the kind of mistake that's invisible to the person who just wrote it. `.claude/hooks/check-skill-cold-test.sh` nudges (non-blocking) when a skill file looks new or substantially changed.
- **Look it up in our own skill first, the base game second, and write the answer back.** Every domain skill opens with a `## Research protocol` section spelling this out. Before researching anything, check whether the relevant skill already settles it. If it doesn't, consult the game's own read-only ground truth — `ModdingInfo.txt` (~760 lines: every built-in's signature *and* its exact tooltip string), `ModdingExplanation.txt` (~75 lines: how a definition is parsed), real `GameData/**/*.c.txt` examples, real sprite pixels, or `Log.txt` after a launch, depending on the skill. Then **write what you learned back into that skill in the same edit, with its evidence** (`file:line`, exact error text, sample size, or occurrence counts). An un-written-back finding counts as unfinished work, the same as an untested content change — this is what stops every session re-deriving the same conventions. `cube-chaos-orchestrator`'s Step D has the per-skill ground-truth table. **Also check whether the finding is relevant to a different skill's domain** — if so, add a one-line pointer there too (link, don't restate) and a row in `cube-chaos-audit/references/cross-skill-index.md`. A finding only ever written back to its own skill, when it's plainly relevant elsewhere too, is exactly the asymmetric-linking gap a 2026-08-02 audit found repeatedly (e.g. `cube-chaos-scripting/SKILL.md`'s own Text:/Description: section never pointed to `cube-chaos-rule-text`, despite `cube-chaos-rule-text` pointing back to `cube-chaos-scripting` six separate times) — `cube-chaos-doc-audit` is the periodic backstop for whatever this live check misses.
- Sprite edits are scoped to exactly the one tile being changed (its full bounding box, including its own border pixels) — never a wider redraw of a shared sheet, and never extract a border by color-matching against a content-bearing reference tile (see `cube-chaos-sprite-art`'s border pattern library for why, and the from-scratch generators that avoid the problem entirely).
- **Every new or edited `Ability:`/`WorldAbility:` chain defaults to faction-symmetric logic — this is not an opt-in nicety to mention, it's the baseline every cube/perk is written against.** A sideways effect uses `Forwards`/`Backwards`, never a hardcoded `East`/`West` (an AI-owned copy of the same cube has the opposite forward). A "my territory"/"my side of the board" check compares `PlacabilityOfPosition <pos>` against `FactionOfThis` (a `CUBE:`'s own trigger) or `FactionOfCube Caster` (a `PERK:`'s), never a hardcoded faction number (`DoubleConstant 1`/`2`) or an assumption about which edge is "mine" — so the identical ability, owned by either player, reacts to *its own* side and *its own* edge with zero special-casing. Full idiom and real precedent in `cube-chaos-scripting/references/targeting-movement-board.md`'s "Enemy/allied territory" and "Hardcoding East/West" sections; `cube-chaos-audit`'s checklist tests for both (Universal scope — this is engine-correctness, not house style).
