# Grep-before-you-repeat-these: miscellaneous DSL gotchas

Load this when something parses wrong in a way that doesn't fit any other reference file's theme, or
before writing anything touching ability names, load order, STACKING/CONSTANT parameters, or type
conversion (TOKEN→IDENT).

- **`CubeHasName CUBE NAME` takes a bare word**, e.g. `CubeHasName Victim Stone` — do NOT wrap the second argument in `CubeConstant`. That's a different function: `HasNameOfCube CUBE CUBE` takes two full cube-typed expressions, e.g. `HasNameOfCube Culprit CubeConstant Solid_Shadow` is correct *there*, but wrong for `CubeHasName`.
- **Some `COMPOUND: ABILITY` definitions are tagged `LOCAL`** in their source file (e.g. `MyceliumGrowth` in `Characters/1Compounds.c.txt`), meaning they can't be referenced from a different mod package. This fails with an unhelpful `CANT READ ABILITY(Source) <name>` error that gives no hint it's a scoping issue. If a correctly-spelled, real ability keyword mysteriously fails only in your file, grep its `COMPOUND: ABILITY` definition for the word `LOCAL` — if present, pick a different (non-local) ability instead. **Confirmed real, not just theoretical**: a General-mod synergy perk (`General-Fungus`) trying `TargetCube Victim GainAbility MyceliumGrowth` from outside `Characters` failed with exactly this error at load time. There is no legal way to grant that specific tag ability cross-package (defining your own same-named compound to spoof the Fungus species's own `HasAbilityWithName Test MyceliumGrowth` checks elsewhere is untested and risky, not a recommended workaround) — instead, redesign the effect around the real, non-`LOCAL` `CUBE: Mycelium` itself (e.g. `CreateCubeOnPosition CubeConstant Mycelium <position>`, spawning an actual ally instead of tagging an existing one with the growth marker). Check whether the thing you actually want is achievable through the species's own *cubes* (never `LOCAL`) before assuming its internal tag abilities are off-limits entirely.
- **A mod-defined `COMPOUND: ABILITY` can only be referenced from a package that loads AFTER the package defining it, per `Loading_Order.txt`'s own top-to-bottom order — this is a real, separate gotcha from both the same-file ordering rule below and the `LOCAL` flag.** Real incident: the General mod's `General_Cubes.c.txt` defines its own `Faction_Colours` compound (not a base-game ability, no `LOCAL` flag). Adding `Ability: Faction_Colours` to a new DJ-mod cube (`Keyboard`, `DJ/DJ_Cubes.c.txt`) produced `ERROR: CANT READ ABILITY: (Faction_Colours) OFF CUBE WITH NAME: Keyboard IN PACKAGE: DJ` even though DJ's own file had no internal ordering problem — the real cause was `Loading_Order.txt` listing `DJ` before `General`, so `Faction_Colours` simply didn't exist yet from DJ's package's point of view at parse time. Neither this mod's own `DJ_Cubes.c.txt` nor any other DJ file defines a `Faction_Colours`-equivalent at all (its cubes just don't use that tint convention) — the fix was to drop the reference entirely rather than invent a cross-package dependency. **Before reusing what looks like a shared/common mod-defined ability name across two mod packages in this same repo, grep for its actual `COMPOUND: ABILITY` definition and check which package it's really in and where that package sits in `Loading_Order.txt` relative to the one trying to use it** — "I saw this exact ability already used in this repo" is not enough; check *which file*.
- **A `COMPOUND: ABILITY` your own mod defines must appear EARLIER in the same file than the first `CUBE:`/`PERK:` that references it via a bare `Ability: <Name>` grant** — this is a real, empirically-confirmed single-pass top-to-bottom parse constraint, not just a style preference, and it's easy to violate by instinctively grouping "new utility abilities" together near the bottom of a file after the cubes that use them (a natural ordering when adding the ability *because* an existing cube needs it). Real incident: adding a `Faction_Colours` compound ability near the end of `General_Cubes.c.txt` (after `Bunker`, before the file's final `Airport` cube) and referencing it via `Ability: Faction_Colours` on 5 cubes defined *earlier* in the file (`Bomber`, `Artillery`, `Recruit`, `Drop_Helicopter`, `Bunker`) produced `ERROR: CANT READ ABILITY: (Faction_Colours)` for every one of those 5 — while the 6th reference, on `Airport` (defined *after* the compound in file order), loaded clean with no error. Moving the compound's definition to the very top of the file, before any `CUBE:` block, fixed all 5 errors with no other change. This is distinct from the `LOCAL` scoping gotcha above (that's cross-*package*; this is purely about physical line order *within* one file/package) — if `CANT READ ABILITY: (Name)` (note the colon after ABILITY, vs. the `LOCAL` error's `CANT READ ABILITY(Source) Name`) fires on some but not all references to a same-package ability you just added, check definition order before suspecting anything else.
- **To grant a flag-style ability N times** (e.g. "gains this once per X other abilities it has"), don't reach for `GainAbilityStacking ABILITY DOUBLE` unless the ability is itself a STACKING-parameterized constructor (like `GrowthX STACKING`, used as `GrowthX 1`). For simple bare/flag abilities, wrap a plain `GainAbility <Name>` in `XTimes DOUBLE Action` instead — it just repeats the grant N times, sidestepping the type mismatch entirely.
- **`IsSmaller`/`IsLarger DOUBLE DOUBLE` are strict** (`<`/`>`). To test "0 or less" use `IsSmaller X 1` (matches the game's own HP-check convention, e.g. the DJ class ability) rather than `IsEqual X 0`, which is more fragile against any non-integer edge case.
- **A STACKING parameter written inline as part of an ability constructor must be a literal number** — `GainAbility SomeStackingAbility <computed-expression>` fails with `ERROR: FAILED TO INTERPRET AS NUMBER: <expr> OFF CUBE...` because the parser tries to read that slot as a bare number token, not a DOUBLE expression tree. To grant a STACKING-typed ability with a dynamically computed amount (e.g. a rolled random value, or something read via `GetVariableOnCube`), use `GainAbilityStacking ABILITY DOUBLE` instead, with a literal `0` baseline on the ABILITY expression and the real computed value as the trailing DOUBLE — e.g. `GainAbilityStacking EnergyX 0 Division ManaCostOfCube Victim DoubleConstant 2` (real base-game pattern). Plain `GainAbility Name 2` is fine when the value really is a compile-time literal.
  - **`GainAbilityStacking` only drives the value of an ability whose parameter placeholder is `GenericStacking`, NOT one whose placeholder is `GenericConstant`.** The distinction is load-bearing: a `GenericStacking` ability (`ArmorX`/`PoisonX`/`GrowthX`/`RegenerationX`, `Base_Core/1Compounds.c.txt:678-731`) reads its live *stack count* in its body (`NegateX GenericStacking`, etc.), and that stack count is exactly what `GainAbilityStacking` sets/adds — so the granted value takes effect, AND repeated grants merge into one stacking entry. A `GenericConstant` ability (`ExplodesX`, `Base_Core/1Compounds.c.txt:766` — `TakeXDamageEffect GenericConstant 0 NULL`) instead substitutes the *literal argument* you wrote into the ABILITY expression and never reads a stack count, so `GainAbilityStacking ExplodesX 0 <computed>` would grant `ExplodesX 0` (the literal) and silently deal **zero** — the computed stack count is set but unused. The one real base-game `GainAbilityStacking` usage confirms the rule from the working side: `PoisonousX` (`Base_Core/1Compounds.c.txt:737`) drives `PoisonX` (a `GenericStacking` ability) via `GainAbilityStacking PoisonX 1 GenericStacking`. **To grant a computed-value version of a `GenericConstant` ability as a single clean entry, the option is to define your own `GenericStacking` clone of it** and drive that — e.g. a clone of `ExplodesX`'s exact body with `GenericConstant`→`GenericStacking` (call it `UnholyExplodesX`), then `GainAbilityStacking UnholyExplodesX 0 RoundedDown Division ManaCostOfCube Victim DoubleConstant 10`, to make "explode for `floor(cost/10)`" render as one `Explodes N` line (this clone parses clean). **But in most cases just repeat the base ability instead — this is the better default**: `XTimes RoundedDown Division ManaCostOfCube Victim DoubleConstant 10 GainAbility ExplodesX 1` grants N *independent* `ExplodesX 1` instances (they don't merge precisely *because* `GenericConstant` abilities don't stack-merge — so N separate `BeforeThisDies` listeners each deal 1 = N total damage). **The tooltip does NOT show N separate lines** — the game auto-collapses repeated identical ability instances into a single `Nx Explode 1`-style line (user-confirmed for the Unholy mod: N copies of `ExplodesX 1` render as `3x Explode 1`, one line), so the multiple-instances approach reads cleanly and needs no custom compound. The Unholy mod uses this `XTimes` form (`GameData/Unholy/Unholy_Species.c.txt`). Reach for the `GenericStacking` clone only if you specifically need *one* explosion of the summed value (e.g. so a single blast interacts with a target's armor/negation once as `damage N`, rather than as N separate 1-damage hits each reduced independently) — for plain "N total damage to touching cubes," `XTimes GainAbility ExplodesX 1` is simpler, reuses the stock ability, and displays as a single consolidated line anyway.
- **`WORD`-typed arguments (`RemoveAbilityWithName WORD`, `AmountOfAbilitiesOfCubeWithName CUBE WORD`, `CubeHasName CUBE NAME`, `HasAbilityWithName CUBE String` despite its differing type label) are all compile-time-literal-only, the same restriction as STACKING params above, and this is empirically confirmed, not just inferred from convention.** Tested directly: `AmountOfAbilitiesOfCubeWithName Target NameOfAbility Test` (trying to feed a dynamically-computed ability name from `NameOfAbility ABILITY` into the WORD slot) parses `NameOfAbility` alone as the literal word and leaves `Test` as a dangling unconsumed token, cascading into `ERROR: CANT READ ACTION <next-unrelated-token>` several tokens later — the classic "the real mistake is upstream of the reported error" shape. Every real base-game usage of these functions (~40+ checked) also only ever uses bare literals, zero exceptions. **If you need to compare/remove an ability by its *dynamic* identity (e.g. "does this cube already have 2+ copies of whatever ability this loop candidate is"), you cannot go through the name at all — use `IsSameAbility ABILITY ABILITY` (a true value-typed comparison) and `RemoveAbility ABILITY` (removes one specific ability *value*, not "everything with this name") instead.** Real precedent for value-based removal from a loop candidate: `Main/NeutralPerks.c.txt:540`, `EveryAbilityOfCubeWhich Caster AbilityHasName Test MapGenerationTPEB RemoveAbility Target`.
- **`Until BOOLEAN Action Action` takes *two* trailing actions, not one** — easy to miss since most self-chaining constructs (`If`, `TargetCube`, `Cooldown`) take exactly one. The first Action is the loop body (re-run every tick the BOOLEAN stays false); the second runs once, whenever the loop's Action argument as a whole finishes being parsed — in every real usage found (`Base_Core/1Compounds.c.txt`'s `AddDepthRow`) it's just the bare 0-arg `Nothing`, i.e. real code doesn't seem to use the second slot for anything meaningful, but omitting it entirely desyncs the parser (manifests as `CANT READ ACTION Description:`/whatever token happens to follow, far downstream of the actual `Until` call, since the parser is still "hungry" for one more Action when it reaches your `Description:` line). Always end an `Until` block with a trailing `Nothing` unless you have a specific reason to run something else once.
- **Converting an existing `TOKEN` cube to `IDENT` (making it obtainable) needs a `TYPE` line added at the same time, even if the cube never had one before.** A `TOKEN` cube genuinely doesn't need `TYPE` (it never appears in inventory to sort), but the moment it gains an `IDENT` line the engine expects one — omitting it produces `WARNING: CUBE WITHOUT SORTING TYPE: <Name> IN PACKAGE: <Pkg>` at load (not fatal, but a real gap to fix, not noise). Confirmed real: turning General's `Shot`/`Shell`/`Bomb`/`Rocket` (previously bare `TOKEN`s with no `TYPE`) into obtainable `IDENT` cubes triggered this warning for all four until `TYPE Attacker` was added. For a self-propelled `ProjectileX`-based cube specifically, `TYPE Attacker` is the established real convention — checked every obtainable `ProjectileX` cube in the base game (`Magic_Missile`, `Scrappy_Missile`, `Missile`, `Fireball`, `Death_Ball`, `Mindcontrol_Missile`, `Ground_Rocket`, `Lava_Missile`), all use `TYPE Attacker`, zero exceptions.
- **Two different idioms exist for "this cube reaches the enemy on its own," and they're not interchangeable — pick based on whether the cube starts moving from your own side or needs to land exactly where placed:**
  - **Self-propelled missile** (place it anywhere in your own territory, it flies to the enemy under its own power): `Ability: Flying` + `Ability: ChargeEveryX <N>` + `AiPlacementRule: AiMissile`. This is the real base-game `Magic_Missile`/`Scrappy_Missile`/`Missile` shape — `Flying` so gravity doesn't pull it down while it charges forward, `ChargeEveryX` for the actual forward movement, `AiMissile` (a real, dedicated `AiPlacementRule` token) so the AI knows to place it like ranged ammo rather than a frontline body.
  - **Drop-in-place munition** (place it directly on/near the target, no self-movement, gravity does the rest): `Ability: FreePlacement` alone, no `Flying`/`ChargeEveryX`. `FreePlacement` only bypasses the normal placement-support restriction (see `references/targeting-movement-board.md`'s Gravity section) — the cube still falls straight down via gravity from wherever it's dropped, which is the whole point for something meant to land exactly on a target rather than travel toward one.
  Don't default to `FreePlacement` just because a cube is "droppable" in casual phrasing — confirm which of these two the requester actually means, since they produce very different placement/AI behavior and (per `references/authoring-and-inheritance.md`'s substitution-cascade section) very different compatibility obligations with anything that already spawns that cube via an `Ability:` chain.
- **`StrengthX` is `GenericStacking`-based** (`Base_Core/1Compounds.c.txt:748-751`: `StrengthX / BeforeThisDealsDamage NegateX Minus GenericStacking`), confirming a real, working `GainAbilityStacking` call against it does what it looks like. The Unholy mod's `Plague_Ritual` (`Unholy_Cubes.c.txt`) uses `GainAbilityStacking StrengthX 0 AmountOfCubesWhich ...` to grant each spawned `Plague_Imp` a `Strength` equal to its touching-cube count — per the `GenericStacking`-vs-`GenericConstant` distinction above, this is the sound case (unlike trying the same trick on a `GenericConstant` ability like `ExplodesX`), so the perk's rule text ("each gaining 1 Strength per touching cube") is accurate as written.
- **`Secret Action` (`ModdingInfo.txt:267`) has zero confirmed working precedent anywhere** — not in any base-game file, and (as of 2026-07-25) no longer in any mod either: the General mod's `General-Undead` synergy perk was the only user in this whole repo, wrapping `GainAbility Undead` on a spawned Parachute, and it was removed on user instruction ("Undead does not need to be secret there") rather than ever being verified. What it actually does (hide the ability from the target's own tooltip? something else entirely?) is still unknown. If a future ask specifically wants an ability granted-but-hidden-from-tooltip, don't reach for `Secret` on the assumption it does that — there's no evidence either way, so treat it as genuinely untested DSL surface and verify via a real test-launch + tooltip check before relying on it. `Silent Action` (do it without triggering any *other* ability) is the well-documented, well-precedented wrapper for a different purpose — don't confuse the two.
- **A bare terminal action like `HealXDamage DOUBLE`/`TakeXDamage DOUBLE`/`ChangeHp DOUBLE` has no ambient-Caster fallback once you're outside every `TargetCube` scope — it silently no-ops rather than erroring, no log warning either.** `TargetCube CUBE Action` only sets the implicit receiver *within its own trailing `Action` argument*; once that argument tree ends (e.g. after `Both TargetCube Victim Die`, back at the outer `Both`'s second slot), there is no receiver at all, not a fallback to `Caster`. Confirmed real: Unholy's `Blood_Totem` (`Unholy_Cubes.c.txt`) had `Both TargetCube Victim Die` then a bare `HealXDamage DoubleConstant 1` as the second `Both` branch, intending to heal the totem (`Caster`) 1 hp per kill — it parsed clean, loaded clean, the kill worked, but the totem's hp never moved (user-observed in-game: allies died on contact, hp stayed at 4/5 instead of climbing to 5/5). Fix: wrap it explicitly, `TargetCube Caster HealXDamage DoubleConstant 1`, matching the same file's own periodic-tick ability which already self-targets this way (`Both TargetCube Caster TakeXDamage DoubleConstant 1`). **Every real usage of `HealXDamage`/`TakeXDamage` found in this repo and the base game wraps it in an explicit `TargetCube`** — never assume a bare one "obviously" means Caster just because that's the trigger's own subject.
- **A `CUBE:`'s own reactive `Ability:` (e.g. `AfterAnotherAllyIsCreated`) does NOT fire while that cube is sitting unplayed in a hand, even with `HandTime` granted — confirmed by real user playtest, not just inferred (2026-07-26).** The Unholy mod's `Greater_Demon` (since renamed `Two_Headed_Demon`) shipped with `Ability: HandTime` + `Ability: AfterAnotherAllyIsCreated ... Exile the newly-created ally, create this cube instead`, intended as "10% chance, while this sits in your hand, to replace the next created ally with itself." User-tested and confirmed non-functional: the swap never happened while the card was in hand. `HandTime`'s own doc string (`ModdingInfo.txt:161`, `"Experiences time while in hand"`) turned out to be literal and narrow — it appears to (at most) let *periodic* (`EveryX...`)-style ticking happen for a hand-resident cube, not reactive/event triggers tied to *other* cubes' board-side events. **The fix that actually works: move the same effect onto a `PERK:` instead** (`AfterACubeIsCreated`/`AfterACubeDies` on a perk attached to the player's leader, which is always "in play" regardless of what's in hand) — see the Unholy mod's `Mutations`/`Rebirth_of_the_Chosen` perks (`Unholy_Species.c.txt`/`Unholy_UpgradePerks.c.txt`) for the working replacement pattern. **Do not put a "something happens elsewhere on the board while this specific card sits in hand" effect directly on a `CUBE:`'s own `Ability:` block** — host it on a `PERK:` instead, even if that perk's only purpose is to react to a specific cube name/condition.
- **A mod-authored `COMPOUND: ABILITY`/`COMPOUND: ACTION` with a `GenericStacking` (or any `Generic*`) placeholder must use that placeholder only ONCE in its body — using the same placeholder twice makes the parser infer the compound needs two inline arguments instead of one, breaking every `GainAbilityStacking <Name> 0 <computed-value>` grant site.** Real incident, the Broker mod (2026-07-26): a `Gamble` compound written as `AfterEndOfTheBattle ChangeCurrency RandomRoundBetweenXtoY GenericStacking (Multiplication DoubleConstant 2 GenericStacking)` (computing "a random amount between X and 2X", so `GenericStacking` naturally appears twice — once as the low end, once doubled for the high end) produced `ERROR: FAILED TO INTERPRET AS NUMBER: ManaCostOfCube` followed by `ERROR: CANT READ DOUBLE Storage` at the grant site (`GainAbilityStacking Gamble 0 ManaCostOfCube Storage`), even though that grant call's own shape exactly matched confirmed-working real examples (`Main/3GeneralCubes.c.txt:3843`'s `GainAbilityStacking EnergyX 0 HpOfCube CubeInDirectionFromCube South Caster`, a built-in ability with an equally-nested DOUBLE argument). The error is misleading — it looks like the grant site's `ManaCostOfCube Storage` expression is somehow malformed, but the real bug is upstream in the *compound's own definition*: with 2 occurrences of `GenericStacking`, the parser apparently expects `GainAbilityStacking Gamble 0` to be followed by a *second* inline literal number before its real trailing `DOUBLE` argument, so it tries (and fails) to read the grant site's next token (`ManaCostOfCube`) as that second number. **Fix: reference the placeholder only once, and reuse its value via a variable** (`SetVariable NAME GenericStacking` as the first half of a `Both`, then `GetVariableOnCube NAME Caster` everywhere else the value is needed): `AfterEndOfTheBattle Both SetVariable GAMBLEX GenericStacking (ChangeCurrency RandomRoundBetweenXtoY (GetVariableOnCube GAMBLEX Caster) (Multiplication DoubleConstant 2 (GetVariableOnCube GAMBLEX Caster)))` — confirmed fixed, 0 errors on relaunch, no other change. When a custom parameterized compound's body needs the same generic value more than once (a range, a squared term, etc.), always route the repeat uses through a variable snapshot rather than repeating the `Generic*` token itself.
- **Index-based ability iteration, for when you need to compare/dedupe abilities by value rather than act on each independently:** combine a counted `SetVariable`+`Until`+`ChangeVariable` loop (see `Base_Core/1Compounds.c.txt`'s `AddDepthRow` for the idiom) with `NthAbilityOfCubeWhich DOUBLE CUBE BOOLEAN` (1-indexed) instead of `EveryAbilityOfCubeWhich`, specifically because `NthAbilityOfCubeWhich`'s index argument is a plain `DOUBLE` with no ability-typed `Test`/`Target` binding of its own — so it can be called *inside* a nested `IsSameAbility`/`AmountOfAbilitiesOfCubeWhich` predicate without the inner search's own `Test` shadowing the ability you're trying to reference (the exact cross-scope problem `Storage` solves for `CUBE`, but there is no ability-typed equivalent of `Storage`). Iterate the index **downward** (`AmountOfAbilitiesOfCube` down to `1`, stopping once `IsSmaller <idx> 1`) when the loop body removes abilities — removing at the current index only shifts indices *above* it (already visited), never the ones still to come, so a descending walk stays correct without needing to re-snapshot the list. Real usage, the DJ mod's `Added_Variance` perk (`DJ/DJ_Perks.c.txt`): for each index, check `IsLarger (AmountOfAbilitiesOfCubeWhich Target (IsSameAbility Test (NthAbilityOfCubeWhich <idx> Target True))) DoubleConstant 1` and `RemoveAbility (NthAbilityOfCubeWhich <idx> Target True)` if true — self-correcting even though every duplicate instance re-triggers the same check, since by the time a later (lower-index) duplicate is reached the count has already dropped to 1 and the condition no longer fires.
- **`GainAllAbilitiesOfCube CUBE` and `GainAllAbilitiesOfPerk PERK` are NOT interchangeable ways to say "copy this cube's/this player's abilities" — they read from fundamentally different sources.** `GainAllAbilitiesOfCube` (`Base_Core/1Compounds.c.txt:140-142`: `EveryAbilityOfCubeWhich GenericCube True GainAbility Target`) copies a **specific live cube instance's current actual ability list** — including whatever baseline mechanics that cube happens to have simply by existing (e.g. a leader's automatic mana generation), not just things a perk granted it. `GainAllAbilitiesOfPerk` (`Base_Core/1Compounds.c.txt:144-147`: `EveryLeaderAbilityOfPerkWhich GenericPerk True Both ConvertPerkAbilityDescription Target GainAbility Target`) instead walks **one perk's own `Ability:` chains** and grants copies of those specifically — real base-game usage (`Main/GoldenPerks.c.txt`, `Main/NeutralPerks.c.txt`'s `Glitch`-spawning perks, `Characters/Species/Moil.c.txt`) is always "give this new/spawned cube whatever a specific perk would grant a leader," never "clone a leader's current kit wholesale." Real incident, the Voidling mod: a species perk meant to make a spawned cube "gain all abilities your perks grant your leader" was first written with `GainAllAbilitiesOfCube (ARandomLeaderOfFaction FactionOfThis)`, which technically parsed and ran, but pulled in the leader's own baked-in passive abilities (e.g. base mana generation) that no owned perk was actually responsible for — not what "abilities from my perks" meant. Fixed by switching to `EveryPerkInInventoryWhich True GainAllAbilitiesOfPerk Target`, looping over every owned perk instead of reading one cube's live ability list. Pick based on the actual question: "what does this specific cube currently have" → `GainAllAbilitiesOfCube`; "what would my owned perks confer" → `GainAllAbilitiesOfPerk` in a per-perk loop.
- **A species/class base perk whose own `AtTheStartOfTheBattle` ability spawns a cube, combined with that same cube then copying "everything my perks grant" via `GainAllAbilitiesOfPerk`/`EveryPerkInInventoryWhich`, will copy the perk's OWN spawning ability onto the spawned cube — a real, confirmed self-replication bug, not a hypothetical.** Real incident, the Voidling mod's `True_Void`: the species perk's battle-start ability replaces the board's center cube with a neutral `True_Void` that then loops over every owned perk (including the Voidling perk itself) granting it copies of each perk's abilities — which handed `True_Void` its own copy of "replace the center cube with a `True_Void`." Since `True_Void` was sitting exactly at the center, this immediately re-fired on itself, observed in play as the cube "replacing itself every tick." **The general fix is to exclude the perk's own self-referential ability(ies) from whatever wholesale-copy mechanism the spawned cube uses** — either skip the whole originating perk by name (`EveryPerkInInventoryWhich (Not PerkHasNameOfPerk Test PerkConstant <ThisPerk>) GainAllAbilitiesOfPerk Target`, the simple version), or, if some of that same perk's OTHER abilities should still be copied, call `EveryLeaderAbilityOfPerkWhich PERK BOOLEAN Action` directly (the primitive `GainAllAbilitiesOfPerk` wraps) with a custom filter excluding just the offending ability/abilities by name (`And Not AbilityHasName Test <SelfReplicatingAbility> Not AbilityHasName Test <OtherAbilityToSkip>`) — this requires giving each excluded ability its own `COMPOUND: ABILITY` name (a bare inline `Ability: AtTheStartOfTheBattle ...` chain has no name `AbilityHasName` can match against). **Whenever a battle-start (or any) ability creates a cube that will itself inherit "everything my perks grant," always ask whether the creating ability itself is eligible to be re-granted — it usually is, since nothing about `GainAllAbilitiesOfPerk`/`GainAllAbilitiesOfCube` naturally excludes the very ability doing the granting.**
- **The real idiom for "a pure stat-holder `STACKING` ability with no active trigger of its own"** (something other abilities read via `GetStackingOfAbilityOnCube`, but which does nothing by itself) is **`Counter GenericStacking`** as the ability's entire trigger body — confirmed via the base game's own `EnergyX` (`Characters/1Compounds.c.txt:44-50`: `COMPOUND: ABILITY / EnergyX / Counter GenericStacking / Text: ... / NORANDOM / End`), which is exactly this shape and is then driven entirely by other abilities (`EnergyGenerationX`, `ManaCharged`, etc.) via `GainAbilityStacking EnergyX 0 <computed>`. `Counter DOUBLE` (`ModdingInfo.txt:97`) is a real 0-effect Trigger production — don't reach for a fake/always-false `EveryTick If ... Nothing` trigger just to smuggle a `GenericStacking` reference into a marker ability; `Counter` is the real, intended primitive for this. **Don't blindly copy `EnergyX`'s `NORANDOM` flag onto a new stat-holder ability if it's meant to be reachable by a random-ability-grant mechanic** (`GainRandomAbilityOfCube`/`ARandomAbilityOfCubeWhich`) — `NORANDOM` makes an ability ineligible for exactly that kind of pick (see the zero-ability-donor section in `references/creation-and-copying.md`), which defeats the purpose if the whole point of the stat-holder is to be one of several abilities a "gain a random ability of myself" effect can escalate.
- **Re-granting an already-held `GenericStacking` ability via `GainAbility`/`GainRandomAbilityOfCube` (copying a live ability *value*, not calling `GainAbilityStacking` with an explicit number) DOES merge into the existing stack rather than creating a second, separately-tracked instance — user-confirmed in actual play (2026-07-26), not just inferred from the `GenericStacking`-vs-`GenericConstant` distinction documented elsewhere in this file.** The Voidling mod's `True_Void` carries a custom `VoidExpansionX` (`Counter GenericStacking`) stat-holder, occasionally re-granted to itself via `GainRandomAbilityOfCube Test` (which expands to `GainAbility (ARandomAbilityOfCubeWhich GenericCube True)` — a value-copy, not `GainAbilityStacking`); the user observed the ability's own stack count climbing over a battle rather than multiple separate "Void Reach 1" lines appearing. **What's still unconfirmed: the exact growth curve** — since `ARandomAbilityOfCubeWhich` picks the ability's *current* live value and `GainAbility` presumably adds that picked value to the existing stack, repeated picks could plausibly add a flat amount each time or compound (each pick adding whatever the stack has already grown to, i.e. doubling) — not yet distinguished empirically. If a future ability depends on knowing which, watch the exact numbers across 2-3 consecutive picks in a real battle rather than assuming linear growth.
