# Death sequencing, fusion, and reactive-trigger recursion

Load this when writing anything that fires on a cube's own death, reacts to another cube dying,
fuses/combines cubes, or reacts to ability grants (risk of self-triggering recursion).

## Fusing/removing two cubes into one: `Exile` + `CombinationOf2Cubes`

`Exile` is a bare terminal Action (zero arguments) that removes the ambient implicit receiver from play — same shape as `Die`, just without the "death" side effects. `CombinationOf2Cubes CUBE CUBE` is a CUBE-typed expression producing a merged cube from two inputs. The base game's own `Formless` ability (`Extra_Mechanics/1Compounds.c.txt`) is the canonical pattern for "replace these cubes with their combination":
```
Both Exile CreateCubeOnPosition CombinationOf2Cubes Caster Victim PositionOfCube Caster
```
Note `Exile` runs *before* `PositionOfCube`/`CombinationOf2Cubes` still reference the same (now-exiled) cube in the same expression, and that works fine — referencing an already-`Exile`d cube's data (name, position, abilities) later in the same action chain is safe, so there's no need to snapshot position/stats into a variable before exiling. To fuse two *different* cubes (not self + other), exile each explicitly via `TargetCube <cube> Exile` and feed both original references into `CombinationOf2Cubes` — real pattern from a DJ-mod perk (`Forced_Fusion`, `DJ/DJ_Fungus_Perks.c.txt`):
```
Ability: AfterACubeCollides If IsAllyToCaster Victim If IsAllyToCaster Storage If CubeHasName Storage Mycelium
 Both TargetCube Victim Exile
  TargetCube Storage Both Exile CreateCubeOnPosition CombinationOf2Cubes Victim Storage PositionOfCube Storage
```

### In a death context (`AfterThisDies`, or after `Die`/`Exile` on the acting cube), use `PositionOfCube Caster`/`FactionOfCube Caster` — NOT `PositionOfThis`/`FactionOfThis`

`PositionOfThis`/`FactionOfThis` reference "this cube" via the *live board instance*, which no longer exists once the cube is dead — so in a death trigger (or after the cube `Die`s/`Exile`s itself mid-chain) they resolve to nothing/garbage and any create/search built on them **silently produces nothing** (no error). The `...OfCube Caster` forms instead read the stable trigger-bound `Caster` reference, whose position/faction data persists after removal (same principle as the `PositionOfCube Caster`-after-`Exile` note just above). The base game only ever uses the `Caster` form here: `Base_Core/1Compounds.c.txt:584`, `AfterThisDies CreateCubeOnPosition GenericCube PositionOfCube Caster` (a dying cube spawning at its own now-empty tile). Real bug this caused: the Unholy mod's `Cultist` (`GameData/Unholy/Unholy_Cubes.c.txt`) spawns a copy of a random 0-hp hand cube on death and **created nothing** even with an eligible cube in hand (user-reported). Two layers to the fix, learned in order:

1. **`...OfThis` → `...OfCube Caster` was necessary but NOT sufficient.** Switching `FactionOfThis`/`PositionOfThis` to `FactionOfCube Caster`/`PositionOfCube Caster` alone did *not* fix the cascade — it still mostly failed (user: "one or two spawn, most just die").
2. **A hand-SEARCH must run while the cube is still alive — position survives death, a faction-scoped hand lookup does not.** An early attempt `Die`d the acting cube *first*, then ran `ARandomCubeInHandOfFactionWhich FactionOfCube Caster ...` on the now-dead cube, and that search came back empty. So the search has to be snapshotted into `Storage` *before* the cube dies, then read back after. **The fix for a cube's own combat death is `BeforeThisDies` (cube still alive → the hand search works) + `Exile` self to vacate the tile + create from `Storage` at `PositionOfCube Caster`** — the base-game `Formless` `Both Exile (create at PositionOfCube Caster)` shape:
```
Ability: BeforeThisDies If X%Chance DoubleConstant 10
 SetStorage ARandomCubeInHandOfFactionWhich FactionOfCube Caster IsSmaller HpOfCube Test DoubleConstant 1
  Both Exile
   If CubeExists Storage CreateCubeOnPosition CopyWithAction Storage Nothing PositionOfCube Caster
```
**RUNTIME-CONFIRMED WORKING** (Unholy `Cultist`, user playtest 2026-07-24: a frontline Cultist dying from combat spawned the hand cube).

**CRITICAL CORRECTION — `Both Die (create)` does NOT run the create; a cube that `Die`s ITSELF mid-chain halts the rest of that action chain.** An earlier version of this note claimed `SetStorage (search) (Both Die (create))` was the fix ("parse-confirmed, runtime pending"). **User runtime testing disproved it**: the Unholy `Cultist`'s chain reaction used exactly `Both Die (create)` and the chained Cultists died but **spawned nothing**, while the `Both Exile (create)` self-death path (above) spawned correctly in the same run. Conclusion: **`Exile` removes the cube and lets the remaining `Both`/chain actions keep executing; `Die` hands control to the death-processing cascade and the trailing create never runs.** Do NOT use `Both Die (<create/other trailing action>)` and expect the trailing action to fire — it won't. For a self-death spawn, use `Exile` (in-chain) or a separate post-death `AfterThisDies` trigger (Ritual's `AfterThisDies CreateCubeOnPosition CubeConstant Imp PositionOfCube Caster` is the canonical working post-death constant-spawn).

**The mutual-exclusivity this forces, and the marker workaround.** `Die` is required when *other* cubes must react to the death (e.g. a death-chain where each dying cube ripples to trigger the next — they listen on `AfterACubeDies`, which `Exile` does NOT fire). But `Die` blocks the in-chain spawn. So on a *single* cube's death you cannot have both (a) a rippling cascade (needs `Die`) and (b) a reliable at-its-position spawn (needs `Exile` or a separate post-death trigger). To get both, split across three abilities keyed by a `NORANDOM` marker tag (real usage, Unholy `Cultist`, `GameData/Unholy/Unholy_Cubes.c.txt`, parse-clean 2026-07-24, ripple+spawn runtime pending): a `BeforeThisDies` combat-death spawn guarded to *skip* marked deaths (`If Not HasAbilityWithName Caster ChainMark ...Exile...`, so it doesn't `Exile`-abort the ripple), a chain trigger that grants the mark then dies (`AfterACubeDies If ...chain... Both GainAbility ChainMark Die`), and a marked-only post-death spawn (`AfterThisDies If HasAbilityWithName Caster ChainMark CreateCubeOnPosition CubeConstant <X> PositionOfCube Caster`). Note the post-death spawn there must be a **`CubeConstant`** (or otherwise pre-decided cube), not a live hand search — the search would run post-death and fail; `Storage` doesn't bridge from the `AfterACubeDies` trigger into the separate `AfterThisDies` trigger. So the ripple path trades random-from-hand for a fixed spawn cube; the non-ripple `Exile` path keeps random-from-hand.

**But a self-propagating `Die`-ripple at any FIXED percentage is a supercritical branching process that WIPES a whole group instantly once the group is large — do not use it for a unit meant to be fielded in numbers.** Runtime-confirmed (Unholy `Cultist`, user 2026-07-24: "all cultists die at the same time when the first one dies"). The mechanic "each of the N living units rolls `p` to die-and-ripple on *every* unit's death" has mean offspring per death ≈ `p × (living count)`; the moment `p × (N−1) ≥ 1` (e.g. `p=0.10` with 11+ units) the cascade is supercritical and takes the entire stack in one frame. No fixed `p` is safe — a bigger board just needs a smaller `p`, and a "cheap mass unit" is exactly the case that makes the board big. So a true propagating ripple is fundamentally incompatible with a mass-produced unit. The fix the user chose was to **drop the ripple entirely and go single-hop via `Exile`**: `AfterACubeDies If ...same-type ally... If X%Chance p SetStorage(search) (Both Exile (create))` — because `Exile` doesn't fire `AfterACubeDies`, only the *original* (real `Die`) death triggers a wave of rolls, each reactor sacrifices independently, and it stops there (no second generation). This also drops the whole marker/`CubeConstant` apparatus and restores random-from-hand. If a *limited* ripple is genuinely wanted (a few hops, not all-or-nothing), it needs an explicit depth cap or per-hop decay carried on the created/marked cube, never a flat percentage.

General rule: in any self-death spawn, `PositionOfCube Caster` survives the death, but anything that has to *query live game state through the dying cube* (a faction-scoped hand/board search) must be evaluated *before* the cube dies, and the removal itself must be `Exile` (not `Die`) if a trailing in-chain create is to run. An alternative that sidesteps the whole thing: host the spawn on an always-alive observer (the leader via a `PERK:`'s `AfterACubeDies`) and reference the dead cube as the trigger-bound `Victim` — `CreateCubeOnPosition ... PositionOfCube Victim`, exactly the base game's `Earthen_Dead` (`Characters/Species/Undead.c.txt`), whose faction/stat reads off the dead `Victim` (`FactionOfCube Victim`, `MaxHpOfCube Victim`) are all reliable because `Victim` is a stable trigger binding, not a mid-chain-killed `Caster` (the user rejected this for `Cultist` because it wanted the effect cube-local so any faction owning the cube gets it, not only while playing the host species).

## Reacting to `BeforeACubeGainsAnAbility` by granting more abilities: wrap the reactive grant in `Silent` or risk infinite recursion

Any perk that listens for `BeforeACubeGainsAnAbility` and reacts by granting an ability itself (mirroring it, copying it elsewhere, etc.) creates a new ability-grant event — which, if not guarded, can satisfy the *same* perk's own trigger condition again and recurse indefinitely. The real base-game precedent, `Rogue-Moil` (`Characters/Synergies.c.txt:677`): `Ability: BeforeACubeGainsAnAbility If X%Chance 20 TargetCube Victim Silent GainAffectedAbility` — its own `Description:` spells out the reason: "20% chance it gains another copy (**without triggering anything**)." `Silent GainAffectedAbility` (see "Silent" in `ModdingInfo.txt`'s Action list — a bare wrapper, `Silent Action`) grants the ability without re-firing any trigger, breaking the recursion at the source rather than needing an `If Not IsSameAbility ThisAbility ...`-style guard. Real DJ-mod usage, `Feedback` (`DJ/DJ_Perks.c.txt`): `TargetCube Victim Silent GainAffectedAbility` for the identical "20% chance to duplicate a gained ability" shape.

**This directly matters for anything that scans a cube's abilities and grants copies of them onto another cube via a plain (non-`Silent`) `GainAbility`/`GainAllAbilitiesOfCube`/`GainRandomAbilityOfCube` call** — each such grant is a normal, trigger-firing event, so pairing it with any perk that reacts to `BeforeACubeGainsAnAbility` (the base game's `Reciprocity`-shaped perks, or a custom one) risks the same unguarded-recursion class of bug. This was the leading suspect for a real reported game freeze when placing the DJ mod's `Record`/`Microphone` combo (which does a plain multi-ability `GainAllAbilitiesOfCube` grant) alongside the base-game `Reciprocity` perk, which has no `Silent`/self-identity guard on its own mirrored grant — see the project's freeze-investigation notes. If writing a new perk that both *reacts to* ability grants and *causes* them, `Silent` is the first thing to reach for, not an afterthought.

## Bare/unwrapped actions in a perk's own periodic trigger target the player's leader

Inside a `PERK:`'s `Ability:` body (as opposed to a `CUBE:`'s), a periodic trigger like `EveryMinute`/`Every30Seconds`/`EveryXSeconds` has no natural "the cube that did this" binding the way `AfterACubeIsCreated`'s `Victim` does — so a bare/unwrapped terminal action (`GainAbility`, `GainRandomAbilityOfCube`, etc., with no `TargetCube` wrapper) applies to `Caster`, and for a perk-level periodic trigger `Caster` resolves to **the player's own leader cube**. Confirmed by the base game's own `Mycelium_Source` perk (`Ability: EveryMinute GainAbility MyceliumGrowth`, `Description: Every minute your starting leader gains mycelium_growth`) and reused directly for a DJ-mod perk (`DJ-No_Species`, `DJ/DJ_Synergies.c.txt`): `Ability: Every30Seconds SetStorage ARandomCubeInHandOfFactionWhich FactionOfThis ... If CubeExists Storage GainRandomAbilityOfCube Storage` — the final bare `GainRandomAbilityOfCube Storage` needs no `TargetCube Caster` wrapper to land on the leader.

## Death phases: `BeforeThisDies` always fires before `AfterThisDies` — use that to sequence a death-spawn *after* an explosion

A cube's death runs in two ordered phases: every `BeforeThisDies` listener fires, then the cube is removed, then every `AfterThisDies` listener fires. This ordering is reliable and load-bearing. The practical use: **if a cube both explodes and spawns cubes on death, and the spawns land inside the blast, put the spawn in `AfterThisDies` so it happens after the explosion has already resolved.** The spawned cubes never coexist with the blast, so they aren't hit — while the explosion still hits everything that *was* there (allies included, if the explosion is ally-hitting). Real usage: the Unholy species grants every 0-hp cube `ExplodesX` (a `BeforeThisDies` effect hitting all 4 touching tiles), and `Plague_Ritual` spawns allied `Plague_Imp`s on those same touching tiles — moving that spawn from `BeforeThisDies` to `AfterThisDies` is exactly what stops the cube's own blast from killing its imps, with no need to make the explosion enemy-only or shield the spawns (`GameData/Unholy/`, user-driven design). Two consequences to expect, both often desirable: the blast *clears* touching tiles first (more empty spots for the spawns), and anything the `AfterThisDies` chain measures about the neighborhood sees the *post-blast* state (e.g. a "count touching cubes" reads survivors, not who was there pre-blast — this is why `Plague_Ritual`'s per-imp Strength often reads 0 for Unholy, since the blast killed the neighbors it would have counted).

## `BeforeACubeDies`-granted buffs do apply to that same death's damage (e.g. `ExplodesX`/`BeforeThisDies` splash)

A perk that grants `StrengthX` (or similar damage-boosting ability) via `BeforeACubeDies` fires early enough to affect that cube's own death-triggered damage (its `ExplodesX`, or a custom `BeforeThisDies` explosion) — confirmed by the base game's own `Stronger_Blasts` perk (`Characters/Classes/Pyromaniac.c.txt`: `Ability: BeforeACubeDies TargetCube Victim GainAbility StrengthX 2`), whose own `Description:` states the point directly: "increasing its damage by 2." `StrengthX` itself hooks `BeforeThisDealsDamage` (`Base_Core/1Compounds.c.txt`), a generic per-damage-instance hook that fires regardless of *how* the damage is dealt (melee, `TakeXDamage`, `ExplodesX`, etc.) as long as the granting happened before that damage instance resolves — so `BeforeACubeDies: grant Strength` reliably lands in time for a same-cube death explosion, no special ordering trick needed.

## Rate-limiting a reactive trigger: `Cooldown DOUBLE Action`

For "whenever X happens, do Y, but at most once every N seconds" on a reactive (non-periodic) trigger like `AfterACubeTakesDamage`/`AfterACubeDies`/etc., use the real, well-precedented built-in gate `Cooldown DOUBLE Action` — self-chaining (takes exactly one trailing `Action`, same shape as `If`/`TargetCube`), DOUBLE in ticks (60 ticks = 1 second, same rate as everywhere else in this DSL). It is NOT a rare/undocumented primitive despite being absent from every skill file before this note — a plain `grep -r Cooldown GameData/` (system grep, not this harness's `Grep` tool — see the tool-reliability warning in `cube-chaos-mod-setup`) turns up 40+ real usages across `Main/Perks.c.txt`, `Main/UpgradePerks.c.txt`, `Main/Curses.c.txt`, `Characters/Synergies.c.txt`, `Characters/2TokenCubes.c.txt`, `Characters/Classes/Engineer.c.txt`, and more. Placement is exactly where you'd gate the effect, after the trigger's own condition chain and before the actual effect:
```
Ability: AfterACubeTakesDamage If And IsAllyToCaster Victim IsALeader Victim
 Cooldown 600
  <effect Action>
Description: ..., cooldown 10 seconds End
```
Real precedent for the bare-vs-wrapped literal: both `Cooldown 600` (bare number) and `Cooldown DoubleConstant 600` appear in real files — the parser accepts a bare literal directly in a DOUBLE slot here, same tolerance as `ChargeEveryX 180`, so prefer the shorter bare form unless the value is computed. No custom variable/flag-based cooldown scaffolding is ever needed — reaching for a hand-rolled `SetVariable`+`WorldTime`-delta gate (also real and real-precedented, but far more verbose) is solving an already-solved problem.

**Rule-text phrasing**: see `cube-chaos-rule-text`'s matching note — real usage is overwhelmingly lowercase `, cooldown N seconds/minutes` as a trailing comma-separated clause, not a capitalized or leading phrase.
