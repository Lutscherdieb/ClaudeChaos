# Cube Chaos scripting DSL

The full grammar lives in `ModdingInfo.txt` (Trigger/Action/BOOLEAN/CUBE/DIRECTION/DOUBLE/PERK/POSITION/ABILITY/STRING production lists) and `ModdingExplanation.txt` (prose walkthrough + CUBE header field meanings) in the game's root install folder. **Always check these first, then grep `GameData/**/*.c.txt` for a real working example of anything non-trivial before writing it from scratch.** This DSL has almost no error recovery — one wrong argument type or count desyncs the rest of the expression and produces a confusing error far from the actual mistake, so matching a proven pattern is far more reliable than deriving syntax from the grammar list alone.

This file covers the core mechanics needed on nearly every cube/perk write. Situational gotchas and
deep-dive topics live in `references/` (see the index below) — load only the file(s) relevant to what
you're currently writing, not all of them.

## Research protocol — this skill first, base game second, write back always

1. **Check this skill and its `references/` files first.** Most argument-counting, targeting and gotcha questions are already settled below or in one of the reference files. If it's covered, use it and stop.
2. **If not covered, go to the base game**, in this order: `ModdingInfo.txt`'s production lists (the authoritative signature for every token — hand-count against it for anything you didn't copy from working code), then `ModdingExplanation.txt` for how a block is parsed, then `grep GameData/**/*.c.txt` for a *real working example* of the exact function. Prefer copying a proven pattern over deriving syntax from the grammar list — this DSL has almost no error recovery, so a derived-from-grammar guess fails far from the actual mistake.
3. **Write the finding back into this skill (core file or the relevant `references/` file), in the same edit.** New section or a bullet in an existing one, with the evidence: `file:line` for the decisive example, the exact error text if you diagnosed one, and occurrence counts when the conclusion rests on frequency. Record failed approaches too — several sections below exist only because a plausible-looking approach silently didn't work, and that's the expensive knowledge to rediscover. A brand-new *category* of gotcha that doesn't fit any existing reference file gets its own new file plus a new row in the index below, the same way the domain skills themselves grow (see `cube-chaos-orchestrator`'s "Notes for extending" section).

Step 3 is what keeps step 1 worth doing. **Never edit `ModdingInfo.txt`/`ModdingExplanation.txt` or the base-game `GameData/` folders** (see `CLAUDE.md`) — read freely, write never.

## Block formats

**Default rule, every time: a brand-new `CUBE:`/`PERK:` block goes at the END of its `.c.txt` file, full stop — never inserted next to a "thematic sibling" or wherever reads best.** Sprite-sheet tile assignment is pure file order (full step-by-step procedure in `cube-chaos-sprite-art`'s "Adding a new `CUBE:`/`PERK:` — the append procedure" section, including the sheet-extension and verification steps), so inserting mid-file silently shifts every later block's sprite onto the wrong entry — no parse error, just wrong icons in play.

**Verify the end, don't eyeball it — run `grep -n "^CUBE:\|^PERK:" <file>` and check the last listed block against your insertion point before editing.** This has now caused **three** real incidents (Unholy's `Hellstorm`; General's `Annex`/`Retreat`, which were themselves displaced by a mid-file insert; and General's `Iron_Dome` on 2026-08-02, appended after what *looked* like the last block when two more followed). Two of the three were authored via this scripting skill alone without the sprite-art skill ever being consulted — which is exactly why the rule lives here too — and the third happened *despite* the rule already being written in both skills, because the failure wasn't ignorance of the rule but not checking the file's real end. That's why the grep above is now the stated procedure rather than just the principle.

Only deviate from append-at-the-end if there's an explicit reason content must sit elsewhere, and if so, work out the resulting slot shift and fix every affected tile in the same edit — never leave it for later.

**Cube:**
```
CUBE: Name manacost hp maxhp
IDENT rarity aggressive defensive scaling weirdness    (obtainable; rarity 1=common..4=legendary)
   -- or --
TOKEN                                                  (not randomly obtainable; exactly one of IDENT/TOKEN required)
TYPE SomeCategory        (repeatable, free text, inventory-sorting only, no mechanical effect; required once IDENT is present — see below)
Ability: <trigger-or-ability-chain>
Text: <description, ends with the literal word End> End
AiPlacementRule: <BOOLEAN built from AiStacking/AiFrontline/AiBackline/AiEmptyInfront/etc>   (required if IDENT is present)
End
```

**Perk:**
```
PERK: Name
BelongsTo: CLASS | SPECIES | CLASSSPECIES | <ParentPerkName>   (omit for a normal chest-obtainable reward perk)
LevelRequirement: N                                             (optional)
Ability: <trigger-or-ability-chain>
Description: <text, ends with the literal word End> End
ObtainAction: <ACTION>          (repeatable; fires once when the perk is gained, e.g. AddCubeToInventory CubeConstant X)
End
```

`BelongsTo: CLASS` / `BelongsTo: SPECIES` mark the one base perk that defines a whole class/species (grants starting cubes via `ObtainAction: AddCubeToInventory`).

> **Starting-cube baseline: two per class, inventory not deck.** Every base class that grants cubes at all grants exactly **two** via `ObtainAction: AddCubeToInventory CubeConstant <X>` — Chronomancer, Cryomancer, Priest, Programmer, Pyromaniac, Rogue, Wizard, Engineer all follow this (`GameData/Characters/Classes/*.c.txt`; `Warrior`/`Roboticist` grant none, `No_Class` rolls random ones instead). `AddCubeToDeck` is a *separate, rarer* action used only as an extra on top of the two inventory cubes, and only for cheap utility cards — just two instances exist in the whole base game: Engineer's `Tinkering` and Wizard's `Concentrate`. So for a mod class: mana-costing signature cubes go to **inventory**, and reach for `AddCubeToDeck` only for a 0-cost utility card. Granting a third inventory cube is legal and loads fine, but it puts the class above every base class's power baseline — flag it to the user rather than doing it silently.
 `BelongsTo: CLASSSPECIES` + naming the perk exactly `<ClassName>-<SpeciesName>` makes it a synergy perk shown when that class+species pair is selected together. `BelongsTo: <ParentPerkName>` (e.g. `BelongsTo: Fungus`) attributes a normal chest-droppable reward perk to that species/class/perk **even when the reward perk lives in a totally different package from the parent** — confirmed by defining `BelongsTo: Fungus` inside a `DJ/`-package file while `Fungus` itself is defined in `Characters/Species/Fungus.c.txt`; it loaded cleanly and the engine's own reward-perk count for Fungus went up by one. Unlike `COMPOUND: ABILITY`'s `LOCAL` flag (see `references/gotchas-grepped.md`), there is no equivalent package-scoping restriction for `BelongsTo:` perk references. **This means new mod content should always live in the mod's own package folder, never edited into a base-game package** (`Base_Core`, `Characters`, `Main`, `Extra_Mechanics`) just because it's conceptually "about" something the base game defines — cross-package `BelongsTo:` makes that unnecessary.

**A second, non-`CLASSSPECIES` synergy shape: reward a combination of owned *perks* rather than a class+species pairing.** Learned from a `cube-chaos-audit` pass over the Steam Workshop "Dinosaurs!" mod (2026-07-29), `Synergies.c.txt`'s `Mark_Of_Extinction`: `BelongsTo: Everyone` (opts into the generic pool, same idea as `BelongsTo: NULL` for system perks — see `references/perk-economy.md`) plus repeated `PerkRequirement: <PerkName>` lines (one per required perk) and a `PerkRequirementAmount: <N>` (how many of the listed perks must be owned, not necessarily all of them — that mod's example lists 3 requirements with `PerkRequirementAmount: 3`, i.e. all 3, but a smaller `N` against a longer list would mean "any N of these"). Useful for a payoff that should reward *collecting a themed set of perks* regardless of class/species (e.g. "own any 3 of these related perks"), which `CLASSSPECIES` synergies can't express since they're keyed to exactly one class+species pair. Not yet used in this repo's own mods — a real, distinct technique worth reaching for the next time a synergy is genuinely about a perk combo rather than a class/species combo.

## The Text:/Description: requirement

Every **custom** (ad-hoc, multi-step) `Ability:` needs its own tooltip text line immediately after it, or the game logs `ABILITY WITHOUT TEXT`. Built-in named abilities used bare and alone (e.g. `Ability: ChargeEveryX 180`) already have registered tooltip text and don't strictly need one, but as soon as you write a custom trigger chain, give it one.

**For a `CUBE:`, that line is `Text:`, and it genuinely stacks per-ability** — if a cube has 2+ custom `Ability:` lines, each gets its own immediately-following `Text:`, and all of them render in the tooltip (real precedent: `Characters/2TokenCubes.c.txt`'s `Concentrate` cube, two `Ability:`/`Text:` pairs, both show up in-game).

**For a `PERK:`, `Description:` is a single whole-perk field, NOT a per-ability field — it does not stack.** Confirmed two ways: (1) grepping every real base-game `.c.txt` for a `PERK:` block with 2+ `Description:` lines turns up zero matches across `Main/Perks.c.txt`, `Main/UpgradePerks.c.txt`, `Characters/Synergies.c.txt`, `Main/Curses.c.txt` (hundreds of multi-`Ability:` perks checked); (2) writing a perk with 2 `Ability:` lines each followed by its own `Description:` produces `WARNING: Description of <PerkName> changed twice` in `Log.txt` at load — no parse error, but the tooltip silently ends up showing only one of the two descriptions, dropping the other's text entirely with no other warning. The correct pattern for a multi-ability perk, confirmed via the base game's own `Personal_Guard` (`Main/Perks.c.txt`): **one `Description:` (the whole-perk summary, placed wherever in the block — real examples put it before the first `Ability:`) plus one `AbilityText:` immediately after *each* `Ability:` line** (same `... End` terminator convention as `Text:`/`Description:`):
```
PERK: Personal_Guard
Description: After a cube is created in front of an allied leader it gains 3 extra hp and cubes in front of allied leaders can't move End
Ability: AfterACubeIsCreated If IsALeader CubeInDirectionFromCube Backwards Victim If IsAllyToCaster CubeInDirectionFromCube Backwards Victim
TargetCube Victim GainXExtraHp DoubleConstant 3
AbilityText: After a cube is created in front of an allied leader it gains 3 extra hp End
Ability: BeforeACubeMovesNegation If IsALeader CubeInDirectionFromCube Backwards Victim If IsAllyToCaster CubeInDirectionFromCube Backwards Victim NegateX DoubleConstant 1
AbilityText: Before a cube in front of this moves negate that movement End
End
```
A single-ability perk can skip `AbilityText:` and just use `Description:` alone (the common case, and what most perks do) — `AbilityText:` only becomes necessary once a perk has 2+ `Ability:` lines and needs per-ability tooltip breakdown alongside the one overall summary.

**For that common single-ability-plus-bare-`Description:` case, don't trust `Description:` placed *before* `Ability:` even though it looks legal and can appear to work at small scale.** Real incident, the Cubehammer40k mod: 13 `PERK: ... BelongsTo: SPECIES` blocks, each with one custom `Ability:` and one `Description:` placed before it (mirroring this file's own `Personal_Guard` citation above), loaded with zero `ABILITY WITHOUT TEXT` warnings. Adding 8 more same-shaped blocks to the same file (21 total, no other change to the original 13) made **every single one** — including the original 13, unchanged — log `ABILITY WITHOUT TEXT`, with no `ERROR`/`CANT READ` anywhere to explain it. Moving each block's `Description:` line to immediately *after* its `Ability:` line (before `ObtainAction:`/`End`), with no other change, fixed all 21 instantly. Root cause unconfirmed (looks like the engine's Description-to-Ability association is positional/order-sensitive in a way that only breaks past some file-size or block-count threshold, not a simple "before vs. after" rule that fails every time) — but the fix is cheap and the failure mode is silent and total, so just always place `Description:` immediately after the `Ability:` it belongs to for a single-ability perk, rather than before it, regardless of how small the file currently is.

## Argument counting is exact and unforgiving

Every token consumes precisely its declared number of typed arguments (see the production lists in `ModdingInfo.txt`), recursively, prefix-style. There is zero tolerance for extra or missing tokens. When something errors with a vague `CANT READ X` or `excess End`/missing `End`, the *real* mistake is very often several tokens *before* where the error is reported — hand-count your tokens against the grammar for anything you didn't copy from a working example.

## Sequencing multiple effects — no implicit "next statement"

Every `Action`-typed argument slot accepts exactly one `Action` tree — there's no concept of "then do this too" unless the function's own signature provides it.

- **Self-chaining functions already have their own trailing Action parameter** — don't wrap them in `Both`: `SetStorage CUBE Action`, `TargetCube CUBE Action`, `If BOOLEAN Action`, `Cooldown DOUBLE Action`, `EveryCubeWhich BOOLEAN Action`, etc. Whatever comes next is simply that parameter, written directly after.
- **Terminal actions have no trailing Action** and need `Both A B` to sequence them with anything else: `GainAbility`, `SetVariable`, `GenerateXMana`, `NegateX`, `RemoveAbilityWithName`, `ChangeMaxManaOfFaction`, etc. For 3+ terminal actions in a row, nest: `Both A (Both B C)`.
- **Mixing these up is the single most common cause of cascading parse errors** in this DSL — e.g. writing `Both SetStorage X (...)` when `SetStorage` already self-chains leaves `Both`'s second argument slot empty, and the parser then tries to consume the following `Description:`/`End` tokens as if they were more DSL, corrupting everything downstream.

## Implicit target resolution (the trickiest part)

- **Which keyword holds "the other cube" is a property of the specific trigger, not a general convention — never assume it transfers from a similar-sounding trigger, and never assume `Target` is safe on a self-referential trigger.** Confirmed empirically (tallying every real `Ability: <Trigger>` line across the whole game: `AfterThisDies`/`BeforeThisDies`/`AfterThisTakesDamage`/`BeforeThisTakesDamage` bind the other cube to `Culprit`, 34/34; `AfterThisKills` binds it to `Victim`, 6/6) **and** now traced all the way through decompiled bytecode (see the full mechanism in `references/targeting-movement-board.md`, under the `AfterThisCollides` write-up): every `Trigger*` subclass for a self-referential `AfterThis*`/`BeforeThis*` trigger inherits the same base `Trigger.DO(Event E)`, which unconditionally runs `E.Caster = OwnerC; E.Target = OwnerC;` (resetting **both** to the trigger-owning cube itself) immediately before running the ability body — so **`Target` is never usably "the other cube" on any of these triggers, full stop, regardless of what an earlier engine method appeared to set it to.** `Culprit`/`Victim` survive this reset only because a prior step (`Event.EventConversion`) snapshots the incoming `Caster`/`Target` into separate `TriggCaster`/`TriggTarget` fields *before* the reset runs — `Storage` survives too, but for an unrelated reason (the reset never touches it at all). **Practical consequence: before trusting an implicit keyword on a trigger you haven't used before, grep the whole `GameData` tree (base game included) for real prior usage of that *exact* trigger name and copy its binding** — don't reason by analogy from a different trigger, even a closely-related-sounding one, and don't trust a decompile of just the *firing* code (e.g. "the collision handler sets `.Target`") without also tracing what happens between that assignment and the ability body actually running — a first fix attempt on the `Medic` bug below did exactly that, looked correct, and shipped a worse regression (healed itself instead of never healing anyone). **If a trigger has zero real prior usage anywhere to copy from, that's precisely when to decompile *and* trace the full call path (firing site → `TriggerQ` → `Trigger.DO` → the actual `CUBE`-production `.Value(E)` call) rather than stopping at the first plausible-looking assignment** — see [[reference_jar_decompile_technique]].
- `Caster` / `Victim` / `Culprit` are stable, trigger-bound cube references on a self-referential trigger. `Target` is NOT stable the same way — see the bullet above; it gets reset to the trigger-owning cube itself before the ability body runs. All of `Caster`/`Victim`/`Culprit`/`Storage` keep their meaning through any nested loops or `TargetCube` calls — they are never accidentally shadowed.
- `TargetCube CUBE Action` sets `CUBE` as the ambient implicit receiver for bare/unwrapped actions (`GainAbility`, `RemoveThisAbility`, `NegateX`, `GainXExtraHp`, etc.) within its `Action` argument.
- Cube-iterating constructs (`EveryCubeWhich`, `EveryCubeInHandOfFactionWhich`, `EveryCubeTouchingPosition`, etc.) **also** rebind the ambient implicit receiver to their current loop candidate for their `Action` argument — a bare action inside one of these applies to the iterated cube, not to whatever was ambient before entering the loop. (Confirmed by the base game's own `Priest-Dwarf` perk: `EveryCubeInHandOfFactionWhich ... GainAbility RegenerationX 10` heals the iterated Stone cubes, not the caster.)
- `Test` / `Target`, used as CUBE- or ABILITY-typed arguments, both resolve to "the nearest enclosing binder of the matching type" — whichever loop/`TargetCube`/`EveryAbilityOfCubeWhich` call is innermost. They are interchangeable spellings by convention (`Test` inside BOOLEAN predicates, `Target` inside Action bodies) resolving identically, NOT two structurally different mechanisms. **Caveat found for `EveryCubeWhich` specifically — use `Test` for its loop candidate inside the Action body too, not `Target`**: see `references/gotchas-grepped.md`'s `EveryCubeWhich` entry. Every proven-working real usage of `EveryCubeWhich` in this codebase binds its candidate via `Test` inside the Action body (not just the BOOLEAN); a `Target`-based version silently read as `Caster` instead of the loop candidate (root cause not confirmed by isolation testing, but the fix — switching to `Test` — resolved a reported live-game bug with no other change). Don't assume interchangeability holds for this specific construct until proven otherwise.
- **A CUBE-search function's own `Test` binding is confined to its own predicate argument — it does not leak into sibling arguments that follow it.** E.g. in `CreateCubeOnPosition (ARandomCubeInLibraryWhich IsSmaller MaxHpOfCube Test DoubleConstant 1) (PositionInDirectionFromPosition East (PositionOfCube Test))`, the first `Test` (inside the search's own `BOOLEAN`) means "the library candidate being evaluated," while the second `Test` (inside the sibling `POSITION` argument) reverts to whatever `Test` meant in the *outer* enclosing loop (e.g. an outer `EveryCubeWhich`'s candidate) — confirmed by the DJ mod's own `DJ-Dwarf` perk, which relies on exactly this to reference the outer loop's Stone cube for positioning while a nested hand/library search runs its own independent `Test`-scoped predicate right next to it.
- If you need "the loop candidate" to survive past an intervening `TargetCube` call (or vice versa — need to switch the ambient receiver while still referencing the candidate), snapshot it first: `SetStorage CUBE Action`, then read it back later via the bare `Storage` keyword, which is immune to `Test`/`Target` rebinding. This is the standard idiom for accumulator patterns (see `Main/UpgradePerks.c.txt`'s `Inspired_Architects_Help` perk for a real "running minimum across a loop" example, or the base game's `Summoning_Circle_Combine` for a "running combination across a loop" example).
- `SetVariable NAME DOUBLE` + `GetVariableOnCube NAME Caster` is shorthand for a named numeric variable stored on the current Caster — useful for accumulator patterns spanning a whole ability body (as opposed to `Storage`, which only holds one cube reference at a time).
- **Empirically, `TargetCube`'s ambient-receiver rebind does not reliably revert at the end of its own `Action` argument once that `Action` is buried several `If`/`Both` levels deep, contradicting the "scoped to its `Action` argument" description above.** Real incident: the General mod's `Bunker` cube fires a burst of 3 `Shot`s via `EveryXSeconds ... Both If IsPositionEmpty ... (Both CreateCubeOnPosition ... (If CubeExists ... (TargetCube CubeOfPosition(...) GainAbility Flying))) (GainAbilityText EveryXTicks ...)` — a `TargetCube` nested inside `If`-inside-`If`-inside-`Both`, immediately followed by a *sibling* `GainAbilityText` call at the shallower level. By token-counting the grammar, that `GainAbilityText` should sit outside the `TargetCube`'s scope and apply to `Caster` (the ambient receiver from before the `TargetCube` call). In actual play, the user found the granted ability listed on the just-created `Shot` instead of on `Bunker` — confirmed by the resulting bug (`PositionOfThis` inside the granted ability tracked the moving `Shot`'s position instead of `Bunker`'s fixed one, causing later burst-shots to try spawning near wherever the first `Shot` had already traveled to, which read in-game as "shots blocking each other"). **Don't trust automatic scope reversion once a `TargetCube` is nested more than one or two levels deep before a sibling bare action** — explicitly wrap the following action in its own `TargetCube Caster (...)` (or `TargetCube Victim`/whichever cube is actually intended) instead of relying on the ambient receiver having reverted on its own. This is cheap insurance and removes the ambiguity entirely, regardless of whether the root cause is a doc inaccuracy or a genuine engine quirk with deeply-nested scope exit.
- **The same "don't trust it past several nested levels" caution applies to a cube-iterating construct's OWN candidate-rebind, not just `TargetCube`'s.** Real incident, the Voidling mod's `VoidManaSiphon`: a `BeforeACubeTakesDamage` ability nested `EveryCubeWhich CubeHasName Test True_Void` five `If`/`Both` levels deep, relying on bare `GainXExtraHp`/`ChangeMaxHp` applying to the loop's own candidate the whole way down — the effect silently didn't apply (user-reported: "the true void does not gain max hp"). Fixed by adding an explicit `TargetCube Test` immediately inside the loop, wrapping the entire deep chain, with no other change (user-confirmed working afterward). Treat any bare ambient-receiver action nested more than 2-3 `If`/`Both` levels below its binding loop/`TargetCube` as suspect, whether the binder is `TargetCube` or a `EveryCube*Which`-family iterator — wrap explicitly rather than trusting it.
- **`EventAmount` should be snapshotted (`SetVariable NAME EventAmount`) before calling `NegateX EventAmount` if the same ability body needs to read the original amount again afterward** — no confirmed real base-game example reads `EventAmount` a second time after already passing it to `NegateX` in the same chain (every real usage found either reads it once for a condition/computation and negates separately, or negates and never reads it again), so relying on it still holding the pre-negation value past that point is unproven. The Voidling mod's `VoidManaSiphon` snapshots it into `SetVariable VOIDLING_BURN EventAmount` before calling `NegateX EventAmount`, then reads the snapshot (not `EventAmount` directly) for the actual `GainXExtraHp`/`ChangeMaxHp` amounts later in the same chain — cheap insurance against `NegateX` mutating the value it's named after, applied alongside the `TargetCube` fix above, so which of the two actually mattered is unconfirmed, but there's no cost to keeping both.

## Damage has no general type system, but a handful of hardcoded engine damage sources ARE tagged and checkable via `IsType`

`BeforeACubeTakesDamage`/`AfterACubeTakesDamage` fire identically regardless of source in general — there's no `DamageType`-style enum in the grammar, and a mod's own `TakeXDamageEffect DOUBLE int String` calls use a free-text `String` label purely so `IsType <YourLabel>` can key off *your own* custom damage inside your own abilities (see `Zap`/`Eye`/`Melee_Swing` in `Extra_Mechanics/1Compounds.c.txt`). Separately, though, at least one built-in **engine-generated** damage source is real and taggable the same way: **`Excessmana`** — confirmed via the base game's own `No_Class-No_Species` synergy (`Characters/Synergies.c.txt:522-530`): `ExtraTrigger: BeforeACubeTakesDamage If IsAllyToCaster Victim If IsType Excessmana NegateX EventAmount`, described in its own `Description:` as "damage from excess mana." This is the game's internal equivalent of the classic "unspent mana burns you" mechanic (never called "mana burn" anywhere in the files — that's a Magic: The Gathering term bleeding in, not this game's own vocabulary) — reachable from a mod via the identical `If IsType Excessmana` check, with no `String` label of your own needed since the engine already tags it. If a request describes a damage source by a name that doesn't appear anywhere in `ModdingInfo.txt`/`GameData`, don't assume it doesn't exist — it may be a hardcoded `IsType` tag under a different name; ask the user to describe the actual trigger/mechanic before concluding the concept needs inventing from scratch.

## Debugging checklist

1. Read the exact error line — note whether it names a specific perk/cube ("OF PERK X") or not (unlabeled errors are often scoping/registration issues, not local syntax bugs).
2. Grep `GameData/**/*.c.txt` for real usage of the exact function/ability name you're using, and compare your call token-for-token.
3. Hand-count arguments against `ModdingInfo.txt`'s production list for anything you wrote from scratch.
4. Relaunch and recheck logs after every fix — see `cube-chaos-mod-setup` for the test loop.
