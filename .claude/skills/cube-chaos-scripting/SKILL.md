# Cube Chaos scripting DSL

The full grammar lives in `ModdingInfo.txt` (Trigger/Action/BOOLEAN/CUBE/DIRECTION/DOUBLE/PERK/POSITION/ABILITY/STRING production lists) and `ModdingExplanation.txt` (prose walkthrough + CUBE header field meanings) in the game's root install folder. **Always check these first, then grep `GameData/**/*.c.txt` for a real working example of anything non-trivial before writing it from scratch.** This DSL has almost no error recovery — one wrong argument type or count desyncs the rest of the expression and produces a confusing error far from the actual mistake, so matching a proven pattern is far more reliable than deriving syntax from the grammar list alone.

## Block formats

**Cube:**
```
CUBE: Name manacost hp maxhp
IDENT rarity aggressive defensive scaling weirdness    (obtainable; rarity 1=common..4=legendary)
   -- or --
TOKEN                                                  (not randomly obtainable; exactly one of IDENT/TOKEN required)
TYPE SomeCategory        (repeatable, free text, inventory-sorting only, no mechanical effect; required once IDENT is present — see below)
Ability: <trigger-or-ability-chain>
Text: <description, ends with the literal word End> End
AiPlacementRule: <BOOLEAN built from AiStacking/AiFrontline/AiBackline/AiEmptyInfront/etc>   (required if IDENT is present)
End
```

**Perk:**
```
PERK: Name
BelongsTo: CLASS | SPECIES | CLASSSPECIES | <ParentPerkName>   (omit for a normal chest-obtainable reward perk)
LevelRequirement: N                                             (optional)
Ability: <trigger-or-ability-chain>
Description: <text, ends with the literal word End> End
ObtainAction: <ACTION>          (repeatable; fires once when the perk is gained, e.g. AddCubeToInventory CubeConstant X)
End
```

`BelongsTo: CLASS` / `BelongsTo: SPECIES` mark the one base perk that defines a whole class/species (grants starting cubes via `ObtainAction: AddCubeToInventory`). `BelongsTo: CLASSSPECIES` + naming the perk exactly `<ClassName>-<SpeciesName>` makes it a synergy perk shown when that class+species pair is selected together. `BelongsTo: <ParentPerkName>` (e.g. `BelongsTo: Fungus`) attributes a normal chest-droppable reward perk to that species/class/perk **even when the reward perk lives in a totally different package from the parent** — confirmed by defining `BelongsTo: Fungus` inside a `DJ/`-package file while `Fungus` itself is defined in `Characters/Species/Fungus.c.txt`; it loaded cleanly and the engine's own reward-perk count for Fungus went up by one. Unlike `COMPOUND: ABILITY`'s `LOCAL` flag (see below), there is no equivalent package-scoping restriction for `BelongsTo:` perk references. **This means new mod content should always live in the mod's own package folder, never edited into a base-game package** (`Base_Core`, `Characters`, `Main`, `Extra_Mechanics`) just because it's conceptually "about" something the base game defines — cross-package `BelongsTo:` makes that unnecessary.

## The Text:/Description: requirement

Every **custom** (ad-hoc, multi-step) `Ability:` needs its own tooltip text line immediately after it, or the game logs `ABILITY WITHOUT TEXT`. Built-in named abilities used bare and alone (e.g. `Ability: ChargeEveryX 180`) already have registered tooltip text and don't strictly need one, but as soon as you write a custom trigger chain, give it one.

**For a `CUBE:`, that line is `Text:`, and it genuinely stacks per-ability** — if a cube has 2+ custom `Ability:` lines, each gets its own immediately-following `Text:`, and all of them render in the tooltip (real precedent: `Characters/2TokenCubes.c.txt`'s `Concentrate` cube, two `Ability:`/`Text:` pairs, both show up in-game).

**For a `PERK:`, `Description:` is a single whole-perk field, NOT a per-ability field — it does not stack.** Confirmed two ways: (1) grepping every real base-game `.c.txt` for a `PERK:` block with 2+ `Description:` lines turns up zero matches across `Main/Perks.c.txt`, `Main/UpgradePerks.c.txt`, `Characters/Synergies.c.txt`, `Main/Curses.c.txt` (hundreds of multi-`Ability:` perks checked); (2) writing a perk with 2 `Ability:` lines each followed by its own `Description:` produces `WARNING: Description of <PerkName> changed twice` in `Log.txt` at load — no parse error, but the tooltip silently ends up showing only one of the two descriptions, dropping the other's text entirely with no other warning. The correct pattern for a multi-ability perk, confirmed via the base game's own `Personal_Guard` (`Main/Perks.c.txt`): **one `Description:` (the whole-perk summary, placed wherever in the block — real examples put it before the first `Ability:`) plus one `AbilityText:` immediately after *each* `Ability:` line** (same `... End` terminator convention as `Text:`/`Description:`):
```
PERK: Personal_Guard
Description: After a cube is created in front of an allied leader it gains 3 extra hp and cubes in front of allied leaders can't move End
Ability: AfterACubeIsCreated If IsALeader CubeInDirectionFromCube Backwards Victim If IsAllyToCaster CubeInDirectionFromCube Backwards Victim
TargetCube Victim GainXExtraHp DoubleConstant 3
AbilityText: After a cube is created in front of an allied leader it gains 3 extra hp End
Ability: BeforeACubeMovesNegation If IsALeader CubeInDirectionFromCube Backwards Victim If IsAllyToCaster CubeInDirectionFromCube Backwards Victim NegateX DoubleConstant 1
AbilityText: Before a cube in front of this moves negate that movement End
End
```
A single-ability perk can skip `AbilityText:` and just use `Description:` alone (the common case, and what most perks do) — `AbilityText:` only becomes necessary once a perk has 2+ `Ability:` lines and needs per-ability tooltip breakdown alongside the one overall summary.

**For that common single-ability-plus-bare-`Description:` case, don't trust `Description:` placed *before* `Ability:` even though it looks legal and can appear to work at small scale.** Real incident, the Cubehammer40k mod: 13 `PERK: ... BelongsTo: SPECIES` blocks, each with one custom `Ability:` and one `Description:` placed before it (mirroring this file's own `Personal_Guard` citation above), loaded with zero `ABILITY WITHOUT TEXT` warnings. Adding 8 more same-shaped blocks to the same file (21 total, no other change to the original 13) made **every single one** — including the original 13, unchanged — log `ABILITY WITHOUT TEXT`, with no `ERROR`/`CANT READ` anywhere to explain it. Moving each block's `Description:` line to immediately *after* its `Ability:` line (before `ObtainAction:`/`End`), with no other change, fixed all 21 instantly. Root cause unconfirmed (looks like the engine's Description-to-Ability association is positional/order-sensitive in a way that only breaks past some file-size or block-count threshold, not a simple "before vs. after" rule that fails every time) — but the fix is cheap and the failure mode is silent and total, so just always place `Description:` immediately after the `Ability:` it belongs to for a single-ability perk, rather than before it, regardless of how small the file currently is.

## Argument counting is exact and unforgiving

Every token consumes precisely its declared number of typed arguments (see the production lists in `ModdingInfo.txt`), recursively, prefix-style. There is zero tolerance for extra or missing tokens. When something errors with a vague `CANT READ X` or `excess End`/missing `End`, the *real* mistake is very often several tokens *before* where the error is reported — hand-count your tokens against the grammar for anything you didn't copy from a working example.

## Sequencing multiple effects — no implicit "next statement"

Every `Action`-typed argument slot accepts exactly one `Action` tree — there's no concept of "then do this too" unless the function's own signature provides it.

- **Self-chaining functions already have their own trailing Action parameter** — don't wrap them in `Both`: `SetStorage CUBE Action`, `TargetCube CUBE Action`, `If BOOLEAN Action`, `Cooldown DOUBLE Action`, `EveryCubeWhich BOOLEAN Action`, etc. Whatever comes next is simply that parameter, written directly after.
- **Terminal actions have no trailing Action** and need `Both A B` to sequence them with anything else: `GainAbility`, `SetVariable`, `GenerateXMana`, `NegateX`, `RemoveAbilityWithName`, `ChangeMaxManaOfFaction`, etc. For 3+ terminal actions in a row, nest: `Both A (Both B C)`.
- **Mixing these up is the single most common cause of cascading parse errors** in this DSL — e.g. writing `Both SetStorage X (...)` when `SetStorage` already self-chains leaves `Both`'s second argument slot empty, and the parser then tries to consume the following `Description:`/`End` tokens as if they were more DSL, corrupting everything downstream.

## Implicit target resolution (the trickiest part)

- `Caster` / `Victim` / `Culprit` are stable, trigger-bound cube references. They keep their meaning through any nested loops or `TargetCube` calls — they are never accidentally shadowed.
- `TargetCube CUBE Action` sets `CUBE` as the ambient implicit receiver for bare/unwrapped actions (`GainAbility`, `RemoveThisAbility`, `NegateX`, `GainXExtraHp`, etc.) within its `Action` argument.
- Cube-iterating constructs (`EveryCubeWhich`, `EveryCubeInHandOfFactionWhich`, `EveryCubeTouchingPosition`, etc.) **also** rebind the ambient implicit receiver to their current loop candidate for their `Action` argument — a bare action inside one of these applies to the iterated cube, not to whatever was ambient before entering the loop. (Confirmed by the base game's own `Priest-Dwarf` perk: `EveryCubeInHandOfFactionWhich ... GainAbility RegenerationX 10` heals the iterated Stone cubes, not the caster.)
- `Test` / `Target`, used as CUBE- or ABILITY-typed arguments, both resolve to "the nearest enclosing binder of the matching type" — whichever loop/`TargetCube`/`EveryAbilityOfCubeWhich` call is innermost. They are interchangeable spellings by convention (`Test` inside BOOLEAN predicates, `Target` inside Action bodies) resolving identically, NOT two structurally different mechanisms.
- **A CUBE-search function's own `Test` binding is confined to its own predicate argument — it does not leak into sibling arguments that follow it.** E.g. in `CreateCubeOnPosition (ARandomCubeInLibraryWhich IsSmaller MaxHpOfCube Test DoubleConstant 1) (PositionInDirectionFromPosition East (PositionOfCube Test))`, the first `Test` (inside the search's own `BOOLEAN`) means "the library candidate being evaluated," while the second `Test` (inside the sibling `POSITION` argument) reverts to whatever `Test` meant in the *outer* enclosing loop (e.g. an outer `EveryCubeWhich`'s candidate) — confirmed by the DJ mod's own `DJ-Dwarf` perk, which relies on exactly this to reference the outer loop's Stone cube for positioning while a nested hand/library search runs its own independent `Test`-scoped predicate right next to it.
- If you need "the loop candidate" to survive past an intervening `TargetCube` call (or vice versa — need to switch the ambient receiver while still referencing the candidate), snapshot it first: `SetStorage CUBE Action`, then read it back later via the bare `Storage` keyword, which is immune to `Test`/`Target` rebinding. This is the standard idiom for accumulator patterns (see `Main/UpgradePerks.c.txt`'s `Inspired_Architects_Help` perk for a real "running minimum across a loop" example, or the base game's `Summoning_Circle_Combine` for a "running combination across a loop" example).
- `SetVariable NAME DOUBLE` + `GetVariableOnCube NAME Caster` is shorthand for a named numeric variable stored on the current Caster — useful for accumulator patterns spanning a whole ability body (as opposed to `Storage`, which only holds one cube reference at a time).
- **Empirically, `TargetCube`'s ambient-receiver rebind does not reliably revert at the end of its own `Action` argument once that `Action` is buried several `If`/`Both` levels deep, contradicting the "scoped to its `Action` argument" description above.** Real incident: the General mod's `Bunker` cube fires a burst of 3 `Shot`s via `EveryXSeconds ... Both If IsPositionEmpty ... (Both CreateCubeOnPosition ... (If CubeExists ... (TargetCube CubeOfPosition(...) GainAbility Flying))) (GainAbilityText EveryXTicks ...)` — a `TargetCube` nested inside `If`-inside-`If`-inside-`Both`, immediately followed by a *sibling* `GainAbilityText` call at the shallower level. By token-counting the grammar, that `GainAbilityText` should sit outside the `TargetCube`'s scope and apply to `Caster` (the ambient receiver from before the `TargetCube` call). In actual play, the user found the granted ability listed on the just-created `Shot` instead of on `Bunker` — confirmed by the resulting bug (`PositionOfThis` inside the granted ability tracked the moving `Shot`'s position instead of `Bunker`'s fixed one, causing later burst-shots to try spawning near wherever the first `Shot` had already traveled to, which read in-game as "shots blocking each other"). **Don't trust automatic scope reversion once a `TargetCube` is nested more than one or two levels deep before a sibling bare action** — explicitly wrap the following action in its own `TargetCube Caster (...)` (or `TargetCube Victim`/whichever cube is actually intended) instead of relying on the ambient receiver having reverted on its own. This is cheap insurance and removes the ambiguity entirely, regardless of whether the root cause is a doc inaccuracy or a genuine engine quirk with deeply-nested scope exit.

## `Visual:` — placement-preview markers (undocumented in ModdingInfo.txt/ModdingExplanation.txt)

Every base-game cube with a positional effect (deals damage in front, heals below, etc.) has one or more `Visual:` lines in its `CUBE:` block, placed near the end (after the relevant `Text:`, before `AiPlacementRule:`). These draw colored highlight icons at fixed tile offsets when the player is holding/placing the cube, showing which tiles it will affect. Purely cosmetic — omitting them doesn't break the ability, it just makes the cube's effect radius invisible at placement time (confirmed as the root cause when a user noticed custom DJ cubes weren't showing their affected tiles like base-game cubes do). Reverse-engineered from ~500 real usages, since neither grammar doc mentions it:

```
Visual: <Shape> X Y R G B [N]
```

- `X Y` are tile offsets **relative to the cube**, in its default placed orientation: `+X` = Forwards/East, `-X` = Backwards/West, `+Y` = South (down), `-Y` = North (up). Confirmed by cross-referencing cubes whose actual `Ability:` targets `North`/`South`/`Forwards` against their own `Visual:` offsets (e.g. a "heal the cube below" cube uses `Visual: Plus 0 1 ...`).
- `R G B` is the marker color — reuse the game's existing color language rather than inventing one: gray `96 96 96` for "a cube will be created here", red `255 0 0` for damage/threat, green `0 254 33` for healing, ice-blue `109 209 228` or `155 238 255` for buff/utility/"related cube" markers.
- **Shape** picks the icon and argument count: `Square`/`Target`/`Plus`/`Mist` take exactly `X Y R G B` (5 args); `Sword`/`Arrow` take a 6th trailing number (reach/size, not fully decoded — copy an existing value like `1` or `2`). `Area N Mist R G B` is a different overload for radius-based AoE (N = radius, centered on the cube itself, no X/Y). A bare `Visual: Infinite` line directly after a `Target`/`Arrow` line extends that marker's ray to unlimited range (used for "any distance" abilities) instead of one fixed tile.
- **"Touching" means the 4 orthogonal neighbors, not diagonals** — confirmed by a cube whose own tooltip says "all 4 touching positions" while its `Ability:` explicitly checks North/South/East/West only. For an ability using `EveryCubeTouchingPosition`, that's 4 markers: `1 0` / `-1 0` / `0 1` / `0 -1`.

## `CubeColourShift:` — tinting a cube's sprite via a granted ability (undocumented)

Like `Visual:`, `CubeColourShift:` is missing from both `ModdingInfo.txt` and `ModdingExplanation.txt` but is real and load-bearing. It's a field of a `COMPOUND: ABILITY` block (NOT a `CUBE:` block) — whichever cube instance currently *has* that ability gets its sprite tinted live, for as long as it holds the ability:

```
CubeColourShift: <strength 0-1> R G B
```

Confirmed real range for `<strength>`, from ~50 real usages: `0.1` for subtle status tints (`Slowed`, `TemporaryFlying`, `TemporaryStrength`) up to `0.9` for a strong/near-full recolor (base game's own `Golden` ability, and a blue status effect both use `0.9`). Nothing in the base game goes to `1.0` — treat `0.9` as the practical ceiling for "as visible as this field gets" rather than assuming `1.0` is safe/needed.

**`CubeColourShift` blends the tint against the sprite's existing colors, so multi-color art never reads as a fully clean/saturated tint no matter how high the strength goes** — a strength-0.8 blue tint over a gunmetal-gray-plus-olive-green cube (General mod's `Bomber`) still shows faint traces of the original hues, since the blend is per-pixel against whatever color was already there. Bumping `<strength>` toward the `0.9` ceiling is the cheap, zero-art-cost first lever (a one-number change, instantly reversible) — try this first. **If that's still not clean enough, repaint the underlying sprite in plain flat grayscale** (blending a tint against a grayscale image is the same math as a photo "colorize" filter — zero original-hue bleed-through at any strength): convert every non-background pixel to its own luminosity value (`0.299R+0.587G+0.114B`, R=G=B), nothing more. **Do not add a levels/contrast boost on top** (pushing bright/mid tones toward near-white while compressing dark tones toward near-black) — this was tried in the General mod (`Bomber`/`Bomber_West`/`Drop_Helicopter`/`Drop_Helicopter_West`/`Artillery`/`Recruit`/`Bunker`/`Airport`, all 8 tiles that can display the `Faction_Colours` tint) on the theory that a cleaner/more-white base would read as a more obviously-colored tint, and was explicitly reverted by the user ("way too white," "this is not as i intended") back to plain flat luminosity. Plain luminosity preserves the sprite's original shading/contrast relationships exactly — that's the point, and the correct target — rather than flattening most of the art into a narrow near-white band. Apply the LUT as a value-keyed dict built from the sprite's own actual observed grayscale values (sample first via a `Counter` per target tile) for precision, and verify the resulting tint by simulating the blend in a throwaway script (`pixel*(1-strength) + tint*strength` per channel) before trusting it looks right. Note the tint only applies once the granting ability is actually held — for an `AfterThisIsCreated`-granted tag like `Faction_Colours`, hand/inventory icons stay full original color; only placed-on-board instances show the shift.

**Pure cosmetic tag-ability pattern** — for "mark this specific cube instance with a color, no gameplay effect," copy the base game's own `Golden`/`Swarm`/`MyceliumGrowth` shape (all real, all `Nothing`-triggered):
```
COMPOUND: ABILITY
YourTag
Nothing
Text: \C<R> <G> <B> Your Tag Name \CN End
NO_DUPLICATES
NORANDOM
CubeColourShift: 0.9 <R> <G> <B>
End
```
- `Nothing` as the trigger body is valid syntax and means "no functional effect, this ability just exists as a flag/marker."
- `NO_DUPLICATES` stops the tag from stacking if granted more than once.
- `NORANDOM` excludes the ability from random-ability-grant pools. Confirmed by grepping every real `NORANDOM` usage in the base game: applied uniformly to internal AI-only scaffolding abilities (`AiPlacementAdd`, `AiWarrior` in `Base_Core/2AiCompounds.c.txt`) and to abilities explicitly marked deprecated ("no longer used... kept in case some mod uses it"). Reads as a general "never eligible to be handed out by any random-ability mechanic" flag rather than something narrower — apply it to your own tag abilities so a "steal a random ability from a hand/board cube" mechanic (`GainRandomAbilityOfCube`, see the Speaker-style pattern above) doesn't spread your cosmetic marker onto unrelated cubes. (Caveat: not verified by decompiling the engine, just by convention — the base game's own `Golden` tag deliberately does NOT set `NORANDOM`, presumably because being copied is thematically fine for a "golden" bonus; decide per-case whether propagation is desirable for your tag.)
- **There is no known way to fully hide an ability's line from a cube's rules/tooltip panel.** Searched for a `HIDDEN`/`NOTEXT`-style flag across the complete undocumented all-caps flag vocabulary in every `GameData/**/*.c.txt` file and found only `NO_DUPLICATES`, `NORANDOM`, `LOCAL`, `TOKEN`, `IDENT` — nothing that suppresses tooltip rendering. Every granted ability shows at least its `Text:` line, even a minimal one like `Golden`'s (`Text: \C255 238 0 Golden End`). If you want a tag unobtrusive rather than fully gone, the only lever is giving its own `Text:` a low-contrast color against the tooltip's dark background — a deliberate visual trick, not a real hide.
- **The tooltip/rules-panel lists an ability's abilities in grant order, first-granted first.** When a chain grants 2+ abilities to the same cube via `Both (GainAbility A) (GainAbility B)` (or `GainAllAbilitiesOfPerk`/similar), whichever is granted first in the token sequence renders first in-game. Confirmed empirically on `DJ/DJ_Synergies.c.txt`'s `DJ-Moil` perk: swapping `Both (GainAllAbilitiesOfPerk ...) (GainAbility Moil_Blessed)` to `Both (GainAbility Moil_Blessed) (GainAllAbilitiesOfPerk ...)` moved `Moil_Blessed` from the bottom to the top of the rendered ability list, with no other change.

## Runtime gotcha: `GainRandomAbilityOfCube` on a zero-ability cube

`GainRandomAbilityOfCube CUBE` (pick and grant ONE random ability from a cube) crashes at runtime — not at load/parse time — if the source cube happens to have zero `Ability:` lines (e.g. a bare `TOKEN` cube like `Note`). It surfaces as a vague, unlabeled `ERROR: FILE ENDED BUT STILL LOOKING FOR ACTION / OFF NOTHING? / IN PACKAGE: GainStringResolved` in `Log.txt`, interleaved with battle-simulation lines (`AI STATS`, `Total delays`) since it only fires when that specific random pick actually happens mid-battle — never at boot, so a clean load doesn't mean this is safe. This is an easy trap for any "grab a random ability from a random cube/hand-card" mechanic (`ARandomCubeInLibraryWhich True`, scanning hand for cheap/token cubes, etc.).

Guard every such call site with a "has at least one ability" filter: `IsLarger AmountOfAbilitiesOfCubeWhich <CUBE> True DoubleConstant 0`. The "gain **all** abilities" variants (`GainAllAbilitiesOfCube`, `GainAllAbilitiesOfPerk`) don't need this guard — looping over zero abilities is just a no-op, not a crash.

**`RemoveRandomAbility` needs the identical guard, for the identical reason.** It's a bare terminal Action (no arguments, applies to the ambient receiver) that internally expands to `RemoveAbility ARandomAbilityOfCubeWhich Target True` (`Base_Core/1Compounds.c.txt`'s own `COMPOUND: ACTION` definition for it) — picking a random ability from zero is the same crash-shaped problem as `GainRandomAbilityOfCube`. The base game's own `Voids_Price` perk (`Main/NeutralPerks.c.txt`) guards it exactly like this: `If X%Chance DoubleConstant 90 If IsLarger AmountOfAbilitiesOfCube Victim DoubleConstant 0 ...RemoveRandomAbility...`. Note it uses the bare `AmountOfAbilitiesOfCube CUBE` (unfiltered total count) rather than the `...Which CUBE BOOLEAN` filtered variant — either works for a plain "has at least one ability" check, `AmountOfAbilitiesOfCube` is just fewer tokens when you don't need a filter predicate.

## Faction numbers and default allegiance of created cubes

- Factions are numbered `0` = neutral, `1` = one player, `2` = the other (confirmed via dozens of `SetFaction DoubleConstant 1`/`2`/`0` calls, e.g. `Main/Perks.c.txt`'s `Both SetFaction DoubleConstant 1 ...` / `Both SetFaction DoubleConstant 2 ...` pair for "give a copy to each side"). To affect "everyone's hand" (both players) rather than one side relative to the caster, loop `EveryCubeInHandOfFactionWhich DoubleConstant 1 ...` and `EveryCubeInHandOfFactionWhich DoubleConstant 2 ...` explicitly — simpler and more literal than `FactionOfThis`/`InvertedFaction FactionOfThis`, which only get you "mine" vs "the opponent's" relative to the current Caster.
- `CreateCubeOnPosition`/`CopyWithAction` on a bare `CubeConstant X` **defaults to allied-to-Caster**, not neutral — confirmed by `Characters/Species/Shadow.c.txt`'s `Shadow_Hive` perk, which creates `CubeConstant Solid_Shadow_Hive` with no `SetFaction` call at all and its own `Description:` calls the result "an allied Solid_Shadow_Hive". The base game explicitly wraps in `NeutralCopy CUBE` (a different function) or appends `SetFaction DoubleConstant 0` when a spawned cube needs to be neutral instead. Don't assume a freshly created cube inherits the faction of whatever triggered its creation (e.g. `Victim`'s faction) — it won't, unless you explicitly `SetFaction FactionOfCube Victim` (or similar) yourself.

## Duplicating a specific live cube (e.g. pulled from hand) without consuming the original

`CreateCubeOnPosition CUBE POSITION` on a CUBE expression that's a **freshly-instantiated template** (`CubeConstant X`, or a value already built via `SetStorage CopyWithAction CubeConstant X ...` and reused across multiple positions) needs no special handling — every real example of that shape just calls `CreateCubeOnPosition Storage <position>` directly, since `Storage` there holds a template value, not a specific board/hand object.

But when the CUBE expression is a **specific live cube reference** picked out of hand (`ARandomCubeInHandOfFactionWhich`, `SetStorage ARandomCubeInHandOfFactionWhich ... Action`, etc.) and you want to place a duplicate of it while leaving the original sitting in hand untouched, wrap it in `CopyWithAction CUBE Action` — real precedent, `Modding_Example/GeneralCubes.c.txt`'s `Subwoofer` cube: `SetStorage ARandomCubeInHandOfFactionWhich FactionOfThis DoubleConstant 1 CreateCubeOnPosition CopyWithAction Storage PositionOfThis ...`. If there's no extra modification to apply to the copy (no `SetFaction`/`GainAbility` needed — a copy of an already-allied hand cube stays allied on its own), `Nothing` is a real, valid bare 0-argument `Action` (confirmed in `ModdingInfo.txt`'s Action production list, also used as a bare `Trigger:`/`Ability:` body meaning "no functional effect" — see the tag-ability pattern below) and works as `CopyWithAction`'s required trailing argument: `CopyWithAction Storage Nothing`.

`ARandomCubeInHandOfFactionWhich`/`ARandomCubeInLibraryWhich` can return "no match," so guard any read of the result: `SetStorage (search) Action`, then `If CubeExists Storage <use Storage>` inside that Action — real precedent, the DJ mod's own `DJ-No_Species` perk (`DJ/DJ_Synergies.c.txt`). Don't skip this guard just because the search happened inside a loop that already filtered candidates elsewhere; the search itself can still legitimately come up empty (e.g. no 0-mana cube currently in hand).

## "Scan a hand, maybe graft a random ability onto a cube" — check for a built-in analog first

`DJ/DJ_Cubes.c.txt`'s `Speaker` cube already implements almost exactly this shape and is the canonical real example to copy, via `AfterThisCreates` (fires on the cube that DID the creating, with `Victim` = the thing it just created — a stable trigger-bound reference, immune to loop rebinding, so no `SetStorage`/`TargetCube` juggling needed to keep pointing at it):

```
Ability: AfterThisCreates EveryCubeInHandOfFactionWhich FactionOfThis And IsSmaller ManaCostOfCube Test DoubleConstant 1
 IsLarger AmountOfAbilitiesOfCubeWhich Test True DoubleConstant 0
 SetStorage Test If X%Chance DoubleConstant 50 TargetCube Victim GainRandomAbilityOfCube Storage
Text: For each 0 mana cost cube in your hand that has an ability, 50% chance to give the creation one random ability of that cube End
```

Two idioms worth lifting from this: **fold a guard filter (like the zero-ability crash guard) directly into the loop's own `BOOLEAN` argument** (`EveryCubeInHandOfFactionWhich FactionOfThis IsLarger AmountOfAbilitiesOfCubeWhich Test True DoubleConstant 0 ...`) instead of nesting a separate `If` inside the Action body — fewer tokens, same effect. And **`FactionOfThis` inside `EveryCubeInHandOfFactionWhich` means "your hand"** — reach for this by default over hardcoded `DoubleConstant 1`/`2` faction literals unless you genuinely need both hands or a specific absolute side.

If `AfterThisCreates` isn't available (e.g. the creation happens inside a `PERK:`'s `Ability:` via `CreateCubeOnPosition`, not inside a `CUBE:`'s own ability, so there's no stable `Victim`-as-the-creation binding to reuse), fall back to granting the *created* cube a one-shot ad-hoc ability instead: `GainAbilityText ABILITY List` (not `GainAbility`, which only takes a pre-registered named ability — a custom chain needs `GainAbilityText` so it carries its own inline tooltip text, terminated by the literal word `End` just like `Text:`/`Description:`, e.g. `Characters/Classes/ZUpgradeClassPerks.c.txt`'s `Individual_Thought_Time` perk) an `AfterThisIsCreated ... RemoveThisAbility` chain. Inside that granted ability's own trigger body, `Caster` refers to the newly created cube itself (confirmed by `Base_Core/1Compounds.c.txt`'s `UpToXEfficiency` compound), giving you the same kind of stable, loop-proof reference `Victim` provides for `AfterThisCreates`. Real example (DJ-Shadow synergy perk, `DJ/DJ_Synergies.c.txt`): creates an allied Note in place of a dying Solid_Shadow, then runs the same Speaker-style scan against the caster's own hand:

```
CreateCubeOnPosition CopyWithAction CubeConstant Note
 Both SetFaction FactionOfThis
 GainAbilityText AfterThisIsCreated Both
  EveryCubeInHandOfFactionWhich FactionOfThis And IsSmaller ManaCostOfCube Test DoubleConstant 1
   IsLarger AmountOfAbilitiesOfCubeWhich Test True DoubleConstant 0
   SetStorage Test If X%Chance DoubleConstant 50 TargetCube Caster GainRandomAbilityOfCube Storage
  RemoveThisAbility
 For each 0 mana cost cube in your hand that has an ability, 50% chance to give this one random ability of that cube End
PositionOfCube Victim
```

Either way, the `SetStorage Test ...` step is required whenever the receiver (`Victim` or `Caster`) differs from the loop candidate: snapshot the loop candidate into `Storage` *before* switching the ambient receiver via `TargetCube`, since `Target`/`Test` used as a CUBE argument *inside* a `TargetCube` block resolves to that `TargetCube`'s own binder, not the outer loop's candidate. See "Implicit target resolution" above for why.

## Specific gotchas hit while building the DJ mod (grep before you repeat these)

- **`CubeHasName CUBE NAME` takes a bare word**, e.g. `CubeHasName Victim Stone` — do NOT wrap the second argument in `CubeConstant`. That's a different function: `HasNameOfCube CUBE CUBE` takes two full cube-typed expressions, e.g. `HasNameOfCube Culprit CubeConstant Solid_Shadow` is correct *there*, but wrong for `CubeHasName`.
- **Some `COMPOUND: ABILITY` definitions are tagged `LOCAL`** in their source file (e.g. `MyceliumGrowth` in `Characters/1Compounds.c.txt`), meaning they can't be referenced from a different mod package. This fails with an unhelpful `CANT READ ABILITY(Source) <name>` error that gives no hint it's a scoping issue. If a correctly-spelled, real ability keyword mysteriously fails only in your file, grep its `COMPOUND: ABILITY` definition for the word `LOCAL` — if present, pick a different (non-local) ability instead. **Confirmed real, not just theoretical**: a General-mod synergy perk (`General-Fungus`) trying `TargetCube Victim GainAbility MyceliumGrowth` from outside `Characters` failed with exactly this error at load time. There is no legal way to grant that specific tag ability cross-package (defining your own same-named compound to spoof the Fungus species's own `HasAbilityWithName Test MyceliumGrowth` checks elsewhere is untested and risky, not a recommended workaround) — instead, redesign the effect around the real, non-`LOCAL` `CUBE: Mycelium` itself (e.g. `CreateCubeOnPosition CubeConstant Mycelium <position>`, spawning an actual ally instead of tagging an existing one with the growth marker). Check whether the thing you actually want is achievable through the species's own *cubes* (never `LOCAL`) before assuming its internal tag abilities are off-limits entirely.
- **A mod-defined `COMPOUND: ABILITY` can only be referenced from a package that loads AFTER the package defining it, per `Loading_Order.txt`'s own top-to-bottom order — this is a real, separate gotcha from both the same-file ordering rule below and the `LOCAL` flag.** Real incident: the General mod's `General_Cubes.c.txt` defines its own `Faction_Colours` compound (not a base-game ability, no `LOCAL` flag). Adding `Ability: Faction_Colours` to a new DJ-mod cube (`Keyboard`, `DJ/DJ_Cubes.c.txt`) produced `ERROR: CANT READ ABILITY: (Faction_Colours) OFF CUBE WITH NAME: Keyboard IN PACKAGE: DJ` even though DJ's own file had no internal ordering problem — the real cause was `Loading_Order.txt` listing `DJ` before `General`, so `Faction_Colours` simply didn't exist yet from DJ's package's point of view at parse time. Neither this mod's own `DJ_Cubes.c.txt` nor any other DJ file defines a `Faction_Colours`-equivalent at all (its cubes just don't use that tint convention) — the fix was to drop the reference entirely rather than invent a cross-package dependency. **Before reusing what looks like a shared/common mod-defined ability name across two mod packages in this same repo, grep for its actual `COMPOUND: ABILITY` definition and check which package it's really in and where that package sits in `Loading_Order.txt` relative to the one trying to use it** — "I saw this exact ability already used in this repo" is not enough; check *which file*.
- **A `COMPOUND: ABILITY` your own mod defines must appear EARLIER in the same file than the first `CUBE:`/`PERK:` that references it via a bare `Ability: <Name>` grant** — this is a real, empirically-confirmed single-pass top-to-bottom parse constraint, not just a style preference, and it's easy to violate by instinctively grouping "new utility abilities" together near the bottom of a file after the cubes that use them (a natural ordering when adding the ability *because* an existing cube needs it). Real incident: adding a `Faction_Colours` compound ability near the end of `General_Cubes.c.txt` (after `Bunker`, before the file's final `Airport` cube) and referencing it via `Ability: Faction_Colours` on 5 cubes defined *earlier* in the file (`Bomber`, `Artillery`, `Recruit`, `Drop_Helicopter`, `Bunker`) produced `ERROR: CANT READ ABILITY: (Faction_Colours)` for every one of those 5 — while the 6th reference, on `Airport` (defined *after* the compound in file order), loaded clean with no error. Moving the compound's definition to the very top of the file, before any `CUBE:` block, fixed all 5 errors with no other change. This is distinct from the `LOCAL` scoping gotcha above (that's cross-*package*; this is purely about physical line order *within* one file/package) — if `CANT READ ABILITY: (Name)` (note the colon after ABILITY, vs. the `LOCAL` error's `CANT READ ABILITY(Source) Name`) fires on some but not all references to a same-package ability you just added, check definition order before suspecting anything else.
- **To grant a flag-style ability N times** (e.g. "gains this once per X other abilities it has"), don't reach for `GainAbilityStacking ABILITY DOUBLE` unless the ability is itself a STACKING-parameterized constructor (like `GrowthX STACKING`, used as `GrowthX 1`). For simple bare/flag abilities, wrap a plain `GainAbility <Name>` in `XTimes DOUBLE Action` instead — it just repeats the grant N times, sidestepping the type mismatch entirely.
- **`IsSmaller`/`IsLarger DOUBLE DOUBLE` are strict** (`<`/`>`). To test "0 or less" use `IsSmaller X 1` (matches the game's own HP-check convention, e.g. the DJ class ability) rather than `IsEqual X 0`, which is more fragile against any non-integer edge case.
- **A STACKING parameter written inline as part of an ability constructor must be a literal number** — `GainAbility SomeStackingAbility <computed-expression>` fails with `ERROR: FAILED TO INTERPRET AS NUMBER: <expr> OFF CUBE...` because the parser tries to read that slot as a bare number token, not a DOUBLE expression tree. To grant a STACKING-typed ability with a dynamically computed amount (e.g. a rolled random value, or something read via `GetVariableOnCube`), use `GainAbilityStacking ABILITY DOUBLE` instead, with a literal `0` baseline on the ABILITY expression and the real computed value as the trailing DOUBLE — e.g. `GainAbilityStacking EnergyX 0 Division ManaCostOfCube Victim DoubleConstant 2` (real base-game pattern). Plain `GainAbility Name 2` is fine when the value really is a compile-time literal.
- **`WORD`-typed arguments (`RemoveAbilityWithName WORD`, `AmountOfAbilitiesOfCubeWithName CUBE WORD`, `CubeHasName CUBE NAME`, `HasAbilityWithName CUBE String` despite its differing type label) are all compile-time-literal-only, the same restriction as STACKING params above, and this is empirically confirmed, not just inferred from convention.** Tested directly: `AmountOfAbilitiesOfCubeWithName Target NameOfAbility Test` (trying to feed a dynamically-computed ability name from `NameOfAbility ABILITY` into the WORD slot) parses `NameOfAbility` alone as the literal word and leaves `Test` as a dangling unconsumed token, cascading into `ERROR: CANT READ ACTION <next-unrelated-token>` several tokens later — the classic "the real mistake is upstream of the reported error" shape. Every real base-game usage of these functions (~40+ checked) also only ever uses bare literals, zero exceptions. **If you need to compare/remove an ability by its *dynamic* identity (e.g. "does this cube already have 2+ copies of whatever ability this loop candidate is"), you cannot go through the name at all — use `IsSameAbility ABILITY ABILITY` (a true value-typed comparison) and `RemoveAbility ABILITY` (removes one specific ability *value*, not "everything with this name") instead.** Real precedent for value-based removal from a loop candidate: `Main/NeutralPerks.c.txt:540`, `EveryAbilityOfCubeWhich Caster AbilityHasName Test MapGenerationTPEB RemoveAbility Target`.
- **`Until BOOLEAN Action Action` takes *two* trailing actions, not one** — easy to miss since most self-chaining constructs (`If`, `TargetCube`, `Cooldown`) take exactly one. The first Action is the loop body (re-run every tick the BOOLEAN stays false); the second runs once, whenever the loop's Action argument as a whole finishes being parsed — in every real usage found (`Base_Core/1Compounds.c.txt`'s `AddDepthRow`) it's just the bare 0-arg `Nothing`, i.e. real code doesn't seem to use the second slot for anything meaningful, but omitting it entirely desyncs the parser (manifests as `CANT READ ACTION Description:`/whatever token happens to follow, far downstream of the actual `Until` call, since the parser is still "hungry" for one more Action when it reaches your `Description:` line). Always end an `Until` block with a trailing `Nothing` unless you have a specific reason to run something else once.
- **Converting an existing `TOKEN` cube to `IDENT` (making it obtainable) needs a `TYPE` line added at the same time, even if the cube never had one before.** A `TOKEN` cube genuinely doesn't need `TYPE` (it never appears in inventory to sort), but the moment it gains an `IDENT` line the engine expects one — omitting it produces `WARNING: CUBE WITHOUT SORTING TYPE: <Name> IN PACKAGE: <Pkg>` at load (not fatal, but a real gap to fix, not noise). Confirmed real: turning General's `Shot`/`Shell`/`Bomb`/`Rocket` (previously bare `TOKEN`s with no `TYPE`) into obtainable `IDENT` cubes triggered this warning for all four until `TYPE Attacker` was added. For a self-propelled `ProjectileX`-based cube specifically, `TYPE Attacker` is the established real convention — checked every obtainable `ProjectileX` cube in the base game (`Magic_Missile`, `Scrappy_Missile`, `Missile`, `Fireball`, `Death_Ball`, `Mindcontrol_Missile`, `Ground_Rocket`, `Lava_Missile`), all use `TYPE Attacker`, zero exceptions.
- **Two different idioms exist for "this cube reaches the enemy on its own," and they're not interchangeable — pick based on whether the cube starts moving from your own side or needs to land exactly where placed:**
  - **Self-propelled missile** (place it anywhere in your own territory, it flies to the enemy under its own power): `Ability: Flying` + `Ability: ChargeEveryX <N>` + `AiPlacementRule: AiMissile`. This is the real base-game `Magic_Missile`/`Scrappy_Missile`/`Missile` shape — `Flying` so gravity doesn't pull it down while it charges forward, `ChargeEveryX` for the actual forward movement, `AiMissile` (a real, dedicated `AiPlacementRule` token) so the AI knows to place it like ranged ammo rather than a frontline body.
  - **Drop-in-place munition** (place it directly on/near the target, no self-movement, gravity does the rest): `Ability: FreePlacement` alone, no `Flying`/`ChargeEveryX`. `FreePlacement` only bypasses the normal placement-support restriction (see the `Gravity`/`FreePlacement` section below) — the cube still falls straight down via gravity from wherever it's dropped, which is the whole point for something meant to land exactly on a target rather than travel toward one.
  Don't default to `FreePlacement` just because a cube is "droppable" in casual phrasing — confirm which of these two the requester actually means, since they produce very different placement/AI behavior and (per the next section) very different compatibility obligations with anything that already spawns that cube via an `Ability:` chain.
- **Index-based ability iteration, for when you need to compare/dedupe abilities by value rather than act on each independently:** combine a counted `SetVariable`+`Until`+`ChangeVariable` loop (see `Base_Core/1Compounds.c.txt`'s `AddDepthRow` for the idiom) with `NthAbilityOfCubeWhich DOUBLE CUBE BOOLEAN` (1-indexed) instead of `EveryAbilityOfCubeWhich`, specifically because `NthAbilityOfCubeWhich`'s index argument is a plain `DOUBLE` with no ability-typed `Test`/`Target` binding of its own — so it can be called *inside* a nested `IsSameAbility`/`AmountOfAbilitiesOfCubeWhich` predicate without the inner search's own `Test` shadowing the ability you're trying to reference (the exact cross-scope problem `Storage` solves for `CUBE`, but there is no ability-typed equivalent of `Storage`). Iterate the index **downward** (`AmountOfAbilitiesOfCube` down to `1`, stopping once `IsSmaller <idx> 1`) when the loop body removes abilities — removing at the current index only shifts indices *above* it (already visited), never the ones still to come, so a descending walk stays correct without needing to re-snapshot the list. Real usage, the DJ mod's `Added_Variance` perk (`DJ/DJ_Perks.c.txt`): for each index, check `IsLarger (AmountOfAbilitiesOfCubeWhich Target (IsSameAbility Test (NthAbilityOfCubeWhich <idx> Target True))) DoubleConstant 1` and `RemoveAbility (NthAbilityOfCubeWhich <idx> Target True)` if true — self-correcting even though every duplicate instance re-triggers the same check, since by the time a later (lower-index) duplicate is reached the count has already dropped to 1 and the condition no longer fires.

## Perk economy fields: `Value:` and `IsUpgradeFrom:`

**A perk with `BelongsTo: <an actual class/species name>` carries NO `Value:` line — ever.** Audited all 167 base-game class/species reward perks this way: zero have one (e.g. `Rogue.c.txt` has none at all across 9 perks, several of which still have forge upgrades — the upgrade path needs no base Value to exist). `Value:` is a price tag, not a power rating: its real consumers are trade/pool systems — Consumables (avg ~11), Boons (25–50), Curses/Blights (negative), Golden perks, Neutral perks, CubeUpgrades — plus `ValueOfPerk`-based filters like `Characters/Synergies.c.txt`'s Programmer No_Species logic (`IsLarger ValueOfPerk Target 0`, used to recognize "a priced/pooled perk" generically). A perk truly tied to one class/species is never bought, sold, or drawn from that generic pool, so it has nothing to price.

**Exception, and it's a real one: `BelongsTo: NULL`.** This is a *different* category from omitting `BelongsTo:` or naming a real class — it marks an engine-internal/system perk (`Gravity`, `Reroll_Cost_Increase`, `Debt_Effects`, `Old_Shop_Key`, `Programmer_Manufactory`...) that isn't actually attributed to whatever class file it happens to be filed under, scattered across `Base_Core/GameRulePerks.c.txt`, `Extra_Mechanics/Boons.c.txt`, class files, etc. Being `BelongsTo: NULL` opts a perk *out* of the class-specific pool and into the generic one — which is exactly why `Programmer_Manufactory` (defined inside `Programmer.c.txt`, easy to mistake for a Programmer reward perk at a glance) legitimately carries `Value: 50`. Caught by the user spotting it mid-edit: don't let "lives in a class file" stand in for "is that class's reward perk" — check the actual `BelongsTo:` value.

An early DJ-mod pass put `Value: 40/60` on eight `BelongsTo: DJ` reward perks by pattern-matching its own earlier mistake, not this rule; all were removed after the 167:0 audit. Audit the *right* reference class (same real `BelongsTo:` kind) — not your own mod's precedent, and not "any perk that happens to live near class content."

**`Value:` does NOT determine which category a perk belongs to (Curse/Blight/Boon/Neutral/Golden/etc.) — `BelongsTo:`/`PerkIsType` does, and the ranges overlap too much to be a classifier.** Tempting to assume a perk's sign/magnitude of Value maps to a category (negative=Curse, small positive=Boon, big positive=Golden), but the real ranges disprove it — measured across every real base-game entry in each category: Curses `-400..-50`, Blights `-300..-25`, Boons `20..75`, **Neutral `-150..400`** (spans deep into both curse AND golden territory), Golden `60..1000` (overlaps Boon's `20..75` at `60..75`). If Value drove classification, a `-150` Neutral perk would render as a Curse and the `60-75` band would be ambiguous between Boon/Golden — neither happens. `PerkIsType PERK String` (confirmed real, e.g. `PerkIsType Test TargetFragment`) reads the literal `BelongsTo:` string; that's the actual classifier. Treat `Value:` as pure pricing *within* whichever category `BelongsTo:` already assigned, never as a way to *make* something a Curse/Boon/etc.

**A class/species reward perk having no `Value:` does NOT mean it's excluded from shops** — confirmed wrong by the user's own play-testing (`Undead.c.txt`'s `Risen_Enemies`, `BelongsTo: Undead`, no `Value:` line, observed for sale in a Rogue/Undead shop; a DJ perk was later confirmed the same way). Two genuinely different mechanics were conflated here: `Sell_One_Positive` (**selling** a perk you already own) has a real, DSL-visible filter `PERKREQ: IsLarger ValueOfPerk Target 0` — that's why class perks can't be sold, confirmed correct. But the `SHOP:` block (**buying** new perks — `Extra_Mechanics/Reward_Scenarios.c.txt`'s `Shop`, `Main/NeutralPerks.c.txt`'s `Soul_Shop`) carries no `VALUE:`/`BELONGSTO:` filter field anywhere in its own DSL text — unlike `PERK_REWARD:` blocks, which do (`Basic_Curse_Reward`'s `VALUE: -50 -10`, a literal min/max range). **The shop's buy-side candidate selection is engine-internal and not visible in any `.c.txt` file** — don't assume it mirrors the sell-side `Value` filter just because both involve gold. Empirically, a shop appears to draw partly from your own active class/species's reward-perk pool regardless of `Value`, alongside the generic priced categories. If a "will my perk show up in the shop" question comes up, the honest answer is "probably, if base-game class perks like `Risen_Enemies` do, but the exact odds/logic aren't determinable from the text files" — don't overclaim certainty either direction.

An upgrade perk is a full standalone redefinition of the base perk's `Ability:`/`Description:` (not a diff/patch) plus a trailing `IsUpgradeFrom: <BasePerkName> <N>` field. **What `<N>` means (engine-verified, user-corrected):** the Forge scenario (`Extra_Mechanics/Reward_Scenarios.c.txt:47`) prices upgrades as `Subtraction ValueOfPerk UpgradeOfPerk Target ValueOfPerk Target` — **upgrade cost = upgrade's value − base's value** (minus a one-time 20g first-forge discount). The written `<N>` is best understood as **that difference itself, i.e. the gold price at the forge** (with `ValueOfPerk(upgrade)` = base's Value + N): strictly-better upgrades exist with N *below* their base's Value (`The_Names` Value 100 → `The_Names_Mk2` N=50; `Programmer_Manufactory` Value 50 → `Accelerated_...` N=40), which would produce nonsensical negative forge prices if N were the upgrade's absolute value. Since class/species reward perks have no Value at all, for them N is simply the forge price outright — there's no base Value to subtract. **Pricing ladder** (from all 629 base-game upgrades — N clusters hard at 40 (89×), 60 (258×), 80 (124×), 100 (54×), 120 (33×)): 40 = minor tweak, 60 = standard upgrade, 80–120 = major scope/power jump, 200+ = rare deliberate extremes. Upgrade perks never carry their own `Value:` line (0/629), usually omit `BelongsTo:` (only 36/634 keep it — legal, doesn't double-count the base's reward-perk pool), and **need no sprite of their own** — confirmed by `UpgradeSpeciesPerks.c.txt` having zero corresponding `Sprites/*.c.png` despite ~20 upgrade perks; they reuse the base perk's icon (see `cube-chaos-sprite-art`).

**`BalanceCap: N`** is a separate optional header field, undocumented in `ModdingInfo.txt`/`ModdingExplanation.txt`, used across every perk category (Curses, Blights, Boons, regular reward Perks, CubeUpgrades). Reverse-engineered by correlating `Value:` against `BalanceCap:` across all 130+ real curses in `Main/Curses.c.txt`: there's a strong, consistent **inverse** relationship — powerful curses (`Value: -400`/`-300`/`-200`) mostly sit at `BalanceCap: 0–15`, while weak curses (`Value: -50`) range up to `BalanceCap: 100–1000`. Reads as a soft cap on how many times the reward system will offer/let a specific perk stack within one run — weak effects are allowed to pile up, strong/run-defining ones are capped low so they can't snowball. Not confirmed against engine source, just a strong empirical pattern — when picking a value for a new perk, grep real perks at the same `Value:` tier and match their typical `BalanceCap` rather than guessing (e.g. real `-200`-value curses cluster around `BalanceCap: 10`, real `-100`-value curses also cluster around `10`).

## Curse-specific `PERK:` conventions

Curses (plain `PERK:`s with no `BelongsTo:` field at all — unlike Blights, which use `BelongsTo: Blight`) follow a few conventions distinct from ordinary reward perks, confirmed via `Main/Curses.c.txt`'s 150+ real entries:

- They use **`WorldAbility:`** as their trigger-block keyword instead of `Ability:`. Same DSL underneath (still needs a paired `Description:`, same argument-counting rules), just a different header keyword — reserved for perks whose effect isn't tied to a specific player's own `Caster` context the way a class/species/reward perk's `Ability:` is.
- Inside a `WorldAbility:`, allegiance checks use the bare **`IsAlly CUBE`/`IsEnemy CUBE`** (curse-relative: "ally/enemy of whoever has the curse") instead of `IsAllyToCaster`/`IsEnemyToCaster`. Real pattern: `AfterACubeIsCreated If IsAlly Victim ...` / `If IsEnemy Victim ...`.
- **`IsPlaced`** is a bare 0-argument `BOOLEAN` (checks the current trigger's own `Victim` implicitly, no `CUBE` argument slot) — real pattern: `AfterACubeIsCreated If IsEnemy Victim If IsPlaced TargetCube Victim GainAbility StrengthX 1` (`Curse_Of_Strength`). Don't try to pass it a cube argument; it'll fail argument counting.
- Curses cluster their `Value:` into round multiples of 50 (`-50` through `-400` seen; `-50`/`-100` are by far the most common, 81 and 38 real occurrences respectively) — an oddball value like `-40` or `-175` stands out as non-idiomatic even though the grammar would accept it.

## `AfterACubeCollides` binding roles (undocumented in ModdingInfo.txt/ModdingExplanation.txt)

For the `AfterACubeCollides` trigger (fires when a cube's movement collides it into another cube): `Culprit` = the cube that performed/caused the move, `Victim` = the cube that actually got moved (equal to `Culprit` for a plain self-move, different when one cube pushes another), and `Storage` = auto-bound by the trigger itself to the cube that was collided *into* — readable immediately with no `SetStorage` call needed. Confirmed by the base game's own `Mycelium_Tunneling`/`Advanced_Mycelium_Tunneling` species perks, which read `CubeHasName Storage Mycelium` straight out of the trigger with no prior assignment. `Storage` here follows the same "immune to `Test`/`Target` rebinding" rule as any other `Storage` use (see "Implicit target resolution" above), so it stays valid across nested `TargetCube` calls in the same ability body.

## Fusing/removing two cubes into one: `Exile` + `CombinationOf2Cubes`

`Exile` is a bare terminal Action (zero arguments) that removes the ambient implicit receiver from play — same shape as `Die`, just without the "death" side effects. `CombinationOf2Cubes CUBE CUBE` is a CUBE-typed expression producing a merged cube from two inputs. The base game's own `Formless` ability (`Extra_Mechanics/1Compounds.c.txt`) is the canonical pattern for "replace these cubes with their combination":
```
Both Exile CreateCubeOnPosition CombinationOf2Cubes Caster Victim PositionOfCube Caster
```
Note `Exile` runs *before* `PositionOfCube`/`CombinationOf2Cubes` still reference the same (now-exiled) cube in the same expression, and that works fine — referencing an already-`Exile`d cube's data (name, position, abilities) later in the same action chain is safe, so there's no need to snapshot position/stats into a variable before exiling. To fuse two *different* cubes (not self + other), exile each explicitly via `TargetCube <cube> Exile` and feed both original references into `CombinationOf2Cubes` — real pattern from a DJ-mod perk (`Forced_Fusion`, `DJ/DJ_Fungus_Perks.c.txt`):
```
Ability: AfterACubeCollides If IsAllyToCaster Victim If IsAllyToCaster Storage If CubeHasName Storage Mycelium
 Both TargetCube Victim Exile
  TargetCube Storage Both Exile CreateCubeOnPosition CombinationOf2Cubes Victim Storage PositionOfCube Storage
```

## Reacting to `BeforeACubeGainsAnAbility` by granting more abilities: wrap the reactive grant in `Silent` or risk infinite recursion

Any perk that listens for `BeforeACubeGainsAnAbility` and reacts by granting an ability itself (mirroring it, copying it elsewhere, etc.) creates a new ability-grant event — which, if not guarded, can satisfy the *same* perk's own trigger condition again and recurse indefinitely. The real base-game precedent, `Rogue-Moil` (`Characters/Synergies.c.txt:677`): `Ability: BeforeACubeGainsAnAbility If X%Chance 20 TargetCube Victim Silent GainAffectedAbility` — its own `Description:` spells out the reason: "20% chance it gains another copy (**without triggering anything**)." `Silent GainAffectedAbility` (see "Silent" in `ModdingInfo.txt`'s Action list — a bare wrapper, `Silent Action`) grants the ability without re-firing any trigger, breaking the recursion at the source rather than needing an `If Not IsSameAbility ThisAbility ...`-style guard. Real DJ-mod usage, `Feedback` (`DJ/DJ_Perks.c.txt`): `TargetCube Victim Silent GainAffectedAbility` for the identical "20% chance to duplicate a gained ability" shape.

**This directly matters for anything that scans a cube's abilities and grants copies of them onto another cube via a plain (non-`Silent`) `GainAbility`/`GainAllAbilitiesOfCube`/`GainRandomAbilityOfCube` call** — each such grant is a normal, trigger-firing event, so pairing it with any perk that reacts to `BeforeACubeGainsAnAbility` (the base game's `Reciprocity`-shaped perks, or a custom one) risks the same unguarded-recursion class of bug. This was the leading suspect for a real reported game freeze when placing the DJ mod's `Record`/`Microphone` combo (which does a plain multi-ability `GainAllAbilitiesOfCube` grant) alongside the base-game `Reciprocity` perk, which has no `Silent`/self-identity guard on its own mirrored grant — see the project's freeze-investigation notes. If writing a new perk that both *reacts to* ability grants and *causes* them, `Silent` is the first thing to reach for, not an afterthought.

## Bare/unwrapped actions in a perk's own periodic trigger target the player's leader

Inside a `PERK:`'s `Ability:` body (as opposed to a `CUBE:`'s), a periodic trigger like `EveryMinute`/`Every30Seconds`/`EveryXSeconds` has no natural "the cube that did this" binding the way `AfterACubeIsCreated`'s `Victim` does — so a bare/unwrapped terminal action (`GainAbility`, `GainRandomAbilityOfCube`, etc., with no `TargetCube` wrapper) applies to `Caster`, and for a perk-level periodic trigger `Caster` resolves to **the player's own leader cube**. Confirmed by the base game's own `Mycelium_Source` perk (`Ability: EveryMinute GainAbility MyceliumGrowth`, `Description: Every minute your starting leader gains mycelium_growth`) and reused directly for a DJ-mod perk (`DJ-No_Species`, `DJ/DJ_Synergies.c.txt`): `Ability: Every30Seconds SetStorage ARandomCubeInHandOfFactionWhich FactionOfThis ... If CubeExists Storage GainRandomAbilityOfCube Storage` — the final bare `GainRandomAbilityOfCube Storage` needs no `TargetCube Caster` wrapper to land on the leader.

## Perk stacking: each owned copy independently re-triggers, and there's no self-reference to "this perk"

- Owning the same non-unique reward `PERK:` multiple times is normal (unique perks opt out via `Unique`/`PerkIsUnique`), and **each owned copy runs its own full, independent `Ability:` chain against the same game event** — there is no dedup/merge, N copies behave as if the whole `Ability:` block were pasted N times. Confirmed by two real base-game perks that document this explicitly in their own `Description:`: `Main/Perks.c.txt`'s `Memory_Cache` ("Stacking this perk more than roughly 5 times may have strange effects on the ui") and `Safety_Foam` ("additional copies of this perk can trigger on the foams creation").
- There is **no `ThisPerk` self-reference** for a `PERK:`'s own `Ability:` to identify itself — checked the complete `PERK:`-typed production list in `ModdingInfo.txt` (`Target`, `Test`, `PerkConstant String`, `ARandomPerkIn...Which`, `PerkNInInventory`, `UpgradeOfPerk`, `GenericPerk`) and there's no self keyword, nor any ABILITY→PERK reverse lookup to bridge over from `ThisAbility`. To count "how many copies of myself does the player own," you must hardcode the perk's own literal name: `AmountOfPerksInInventoryWhich IsSameString NameOfPerk Test StringConstant <ExactPerkName>` (equivalently `PerkHasNameOfPerk Test PerkConstant <ExactPerkName>`). This is confirmed as the real base-game idiom, not a workaround — `Witchery`, `Cursed_Components`, `Mold_Exchange`, `Self_Sufficient_Witchery`, and `Manyfold_Cursed_Components` (across `Main/Perks.c.txt`/`Main/UpgradePerks.c.txt`/`Main/NeutralPerks.c.txt`) all do exactly this. **Renaming the perk breaks this silently** (the count just reads 0 forever, no error) — keep the literal name in sync if you ever rename the perk (bit us once in the DJ mod's `Encore`→`Echo` rename).
- To scale a `PERK:`'s own effect by how many copies of it (or of perks matching some other predicate) the player owns, wrap the effect in `XTimes <DOUBLE> Action` where the DOUBLE is `AmountOfPerksInInventoryWhich <predicate>`. Real examples: `Jumble_Storm`/`Grand_Jumble_Storm` (`XTimes AmountOfPerksInInventoryWhich True ...`, scaling by *every* perk owned) and `Harsh_Environment`/`Varied_Environment` (feeding the count directly into `GainXExtraHp` instead of `XTimes`, scaling by a *category* predicate like `PerkIsType Test Neutral`). Combine with the self-name predicate above to scale specifically by copies of the perk itself — real DJ-mod usage: `Echo`'s hand-ability-steal loop is wrapped in `XTimes AmountOfPerksInInventoryWhich IsSameString NameOfPerk Test StringConstant Echo (...)` so owning more copies gives more steal attempts, while its separate `X%Chance DoubleConstant 10` Note-creation roll is left unscaled (each copy still rolls independently at the literal `10`, so the *aggregate* chance across all owned copies rises with stack count even though no single roll's probability number changes).
- If a stacked perk's `Ability:` creates a cube at a shared position derived from the trigger event itself (e.g. `CreateCubeOnPosition ... PositionOfCube Victim` inside `AfterACubeDies`), only the first copy to successfully fire actually places it — a second copy's creation attempt targets the now-occupied tile. This is inferred from convention rather than independently load-tested: every other create-at-a-position pattern in this codebase explicitly `Exile`s the occupant first (see "Fusing/removing two cubes into one" above), implying create-on-an-occupied-tile isn't a normal supported flow.
- **"Each copy affects a different cube" (1st copy → 1st cube, 2nd copy → 2nd cube, etc.) needs no counter at all** — since copies fire sequentially against the same event (no dedup/merge, per above) and there's no `ThisPerk` self-reference to compute "which copy am I," the idiom is: search with `TheFirstCubeInHandOfFactionWhich FactionOfThis <predicate excluding cubes already touched>`, then act on the found cube in a way that also makes it fail that same predicate going forward, so the *next* copy's identical search naturally skips it and lands on the next-first untouched cube. Real base-game precedent: `Main/Perks.c.txt`'s `Bird_Feather` (`TargetCube TheFirstCubeInHandOfFactionWhich FactionOfThis Not HasAbilityWithName Test Flying GainAbility Flying`) — stacking copies each give Flying to the next flightless cube in hand order, using the granted ability itself as both the effect and the exclusion flag. **If the effect instead exiles/replaces the found cube** (rather than tagging it in place), no marker ability is even needed — the exiled original is simply gone from hand, so it can never be found again, and any newly-added replacement cubes get appended after the original hand slots, so subsequent copies still walk through the untouched originals first. Real DJ-mod usage, `Inspiration` (`DJ/DJ_Perks.c.txt`): `TargetCube TheFirstCubeInHandOfFactionWhich FactionOfThis Not HasLimitedUses Test` finds the first hand cube without the `Limited` status (reusing the base game's own `HasLimitedUses`/`RegeneratingUsesX` predicate as a ready-made "unlimited cube" filter, no custom tag needed), then `Both Exile XTimes DoubleConstant 3 AddCubeToHandOfFaction CopyWithAction Target NoManaCost FactionOfThis` exiles it and adds 3 fresh 0-mana copies. Went through two revisions before landing here: v1 tagged the original cube with a custom marker ability (worked, but needed inventing a marker); v2 tried granting `GainRegeneratingUsesX` (a genuine "limited uses" ability) to fake a flat 3-charge item, which required either `SetVariableOnCube` (zero precedent anywhere in the codebase, high risk) or accepted the built-in "always starts at 1, N = regen-interval-in-minutes" semantics — abandoned once the user pointed out **exiling the original and creating all N copies together in the same `CopyWithAction` call is strictly more robust for hand-UI stacking**, since all N instances go through byte-identical construction, whereas "keep the original, `CopyWithAction` it N-1 more times" risks the original silently diverging from its clones (e.g. different internal ability-grant timing) and not stacking visually even though they're mechanically the same.
- **Apply a modifier to freshly-created copies via `CopyWithAction`'s own trailing `Action` parameter, not by modifying the source cube first.** `CopyWithAction CUBE Action` runs `Action` on the *copy*, not the source — so `AddCubeToHandOfFaction CopyWithAction Target NoManaCost FactionOfThis` makes each new copy free without ever touching `Target`'s own mana cost. This composes cleanly with `XTimes N (...)` for "add N modified copies" in one line, and avoids the ordering hazard of "modify original, then copy it" (where forgetting to modify-before-copy silently ships unmodified copies).

## "Enemy/allied territory" (which side can *place* a cube here) vs. faction of a cube standing there

The board has no dedicated `IsInEnemyTerritory`-style BOOLEAN. The real idiom, confirmed via the base game's own `Explosive_Decay`/`Nuclear_Explosive_Decay` perks (`Characters/Classes/Pyromaniac.c.txt`, `ZUpgradeClassPerks.c.txt`) and user-confirmed as the intended meaning ("territory = the place where I can place cubes vs. where the opponent can place"):
```
Not IsEqual PlacabilityOfPosition <POSITION> FactionOfCube <reference-cube>
```
`PlacabilityOfPosition POSITION` (a `DOUBLE`) returns which faction is allowed to *place* a cube at that position — i.e. whose home half of the board it is, independent of who currently occupies it. Compare that against the *reference* cube's own faction (usually `Caster`/`Victim`, whichever cube's perspective "enemy territory" is relative to): if they differ, the position belongs to the other side. Real precedent uses the *observer's* faction (`FactionOfCube Caster`) as the reference even when checking an enemy `Victim`, since `Caster` reliably represents "the player who owns this perk" regardless of which side `Victim` is on. For a `CUBE:`'s own self-check (not perk-level), use `FactionOfThis` in place of `FactionOfCube Caster`.

For "is there an enemy *anywhere* in this direction, not just adjacent" (as opposed to `CubeInDirectionFromCube`, which only reads the immediately-touching tile), use the skip-searching `TheFirstCubeInDirectionFromPositionWhich DIRECTION POSITION BOOLEAN` — it scans outward past non-matching cubes and returns the nearest one that satisfies the predicate (`Test` inside the `BOOLEAN`, same binding convention as other `...Which` searches), e.g. `TheFirstCubeInDirectionFromPositionWhich South PositionOfThis IsEnemyToCaster Test`. Guard the result with `CubeExists` before using it, same as any other cube search that can come up empty.

## Custom-radius explosions: `ExplodesX` is fixed at "touching," not a configurable radius

`ExplodesX CONSTANT` (built-in) always means "before this dies, deal `CONSTANT` damage to the 4 touching cubes" — the radius is NOT a parameter, despite the name inviting that assumption. For a genuinely bigger blast radius, don't reach for `ExplodesX`; write a custom `BeforeThisDies`/`AfterThisDies` ability using `EveryCubeInRadiusXAroundTarget DOUBLE Action` instead — real base-game precedent (`Main/2TokenCubes.c.txt`'s `Blast_Mortar_Projectile`, several `3GeneralCubes.c.txt` cubes):
```
Ability: BeforeThisDies Both EveryCubeInRadiusXAroundTarget DoubleConstant 2 TakeXDamage DoubleConstant 4
 Both CreateAoEParticlesColourRadiusPosition DoubleConstant 16738816 DoubleConstant 2 PositionOfThis
 PlaySound Small_Explosion
```
**No `TargetCube`/`SetCaster` wrapper is needed when this is the cube's own self-trigger** (`BeforeThisDies`/`AfterThisDies`) — `EveryCubeInRadiusXAroundTarget`'s implicit center defaults to the ambient receiver, which is already "this cube" in a self-trigger context. The `SetCaster Victim TargetCube Victim` dance seen on a few cubes (`Explosive_Imbuement`) is only needed for the *global* variant `BeforeACubeDies`/`AfterACubeDies` (reacting to *any* cube dying, not just this one) — don't copy that wrapper onto a plain self-trigger, it's solving a different problem.

## Hardcoding `East`/`West` instead of `Forwards`/`Backwards` is a real, easy-to-miss bug class — audit for it whenever a cube/perk creates or targets something sideways

`East`/`West` are absolute map directions; `Forwards`/`Backwards` resolve relative to whichever faction owns the acting cube/perk (see the `EventDirection`/`Backwards` discussion below for the movement-specific version of this same distinction). Any effect that creates, targets, or checks something to one side — "spawn a Shell to the east," "fire east," "create a Note east of this" — silently breaks when the AI/opponent owns that cube or perk, since their forward is actually west: the effect fires backward into their own lines instead of toward the enemy. `North`/`South` are fine to hardcode (up/down doesn't flip per faction), only the left/right axis needs `Forwards`/`Backwards`.

This is not a rare mistake — a real audit of both mods in this repo (grep `\bEast\b|\bWest\b` across every `.c.txt`, excluding cube-name identifiers like `Bomber_West`) turned up 4 real instances, caught only when a user actually placed the affected cube as the opponent and watched it fire the wrong way: General's `Bunker` and `Artillery` (both hardcoded `East` for where they spawn/fire), and DJ's `Speaker` cube and `DJ-Dwarf` synergy perk (both hardcoded `East` for where they spawn a Note). All four were simple find-and-replace fixes to `Forwards`, confirmed safe via real base-game precedent for `Forwards` used inside a `PERK:`'s own `Ability:` chain too, not just a `CUBE:`'s self-trigger (`Main/Perks.c.txt`'s `Lashing_Out`: `TargetCube CubeInDirectionFromCube Forwards Caster TakeXDamage DoubleConstant 1`, and `Protectors_Shield`: `CubeInDirectionFromCube Forwards Victim`) — `Forwards` resolves relative to `Caster` (the perk-owning player) regardless of which cube in the chain (`Victim`/`Test`/etc.) it's being measured from.

**Whenever writing a new cube/perk that creates or targets something to one side, default to `Forwards`/`Backwards` and only reach for a literal `East`/`West` if there's a genuine reason the effect must be map-absolute** (rare — no real example of this need was found anywhere in either mod). When reviewing/debugging an existing sideways effect that seems to misbehave only for one player, grep for `East`/`West` in that ability chain before looking anywhere else.

## Reverse-movement patrol: swapping `ChargeEveryX` for `FleeEveryX`

`FleeEveryX TIME` (built-in, `Base_Core/1Compounds.c.txt`) is the real "move backwards every X" ability — the mirror image of `ChargeEveryX`. For a cube that should patrol back and forth (advance until some condition, then retreat, then re-advance), swap the two abilities in and out rather than granting both at once (having both active simultaneously fires opposing per-tick moves and the cube visually jitters in place instead of travelling).

**`IfElse BOOLEAN Action Action` is a real, self-chaining 2-branch conditional** (confirmed real precedent: `Characters/2TokenCubes.c.txt`'s `Robot_Remote` — `IfElse HasAbilityWithName Target ChargeEveryX (swap-to-Flee Action) (If HasAbilityWithName Target FleeEveryX (swap-to-Charge Action))`) — reach for it instead of two separate `If`-only `Ability:` blocks when a single trigger needs to pick exactly one of two mutually-exclusive branches, since it collapses what would otherwise be two guarded, near-duplicate `Ability:`/`Text:` pairs into one:
```
Ability: <trigger> If <blocked/other reversal condition>
 IfElse HasAbilityWithName Caster ChargeEveryX
  Both RemoveAbilityWithName ChargeEveryX GainAbility FleeEveryX 60
  If HasAbilityWithName Caster FleeEveryX
   Both RemoveAbilityWithName FleeEveryX GainAbility ChargeEveryX 60
```
The `HasAbilityWithName Caster ChargeEveryX`/`FleeEveryX` checks make the two branches mutually exclusive by construction (the cube is never in both states at once), so there's no listener-ordering concern. Remember any *other* ability that permanently removes the movement ability (e.g. a later "stop moving and become inert" effect) needs to strip **both** `ChargeEveryX` and `FleeEveryX` by name, since the cube could be in either state at the time that ability fires.

**For the reversal trigger itself, "blocked from moving" (a real, idiomatic condition) is often a better fit than positional detection** (checking for a specific cube/territory at some board coordinate), and composes cleanly with the `IfElse` pattern above via a single trigger instead of two separate `AfterThisMoves` abilities each re-deriving "am I currently charging or fleeing." The real DSL idiom for "about to be blocked," confirmed via the base game's own `Climbing` ability (`Extra_Mechanics/1Compounds.c.txt`: `Text: Climbing: Before this is blocked from moving horizontally move upwards`):
```
BeforeThisMoves If CubeExists CubeInDirectionFromCube EventDirection Caster
 <effect>
```
`EventDirection` is the direction of the attempted move, bound within `BeforeThisMoves`/`AfterThisMoves`; `CubeInDirectionFromCube DIRECTION CUBE` reads whatever's immediately touching in that direction (only the adjacent tile — for "anywhere further out," see `TheFirstCubeInDirectionFromPositionWhich` below). `Caster` refers to the cube itself inside a `CUBE:`'s own self-trigger, same as `This`. This check fires **before** the move resolves, whether or not the destination is actually occupied.

**By itself, this check misses being blocked by the edge of the map** — no cube exists off-board either, same as an empty movable tile, so `CubeInDirectionFromCube` alone can't distinguish "empty tile, will move fine" from "off the board, can't move at all." Caught the hard way: a first version of `Bomber`'s reversal used only this check and reversed correctly when blocked by another cube while charging forward, but never reversed back from fleeing, since fleeing heads toward the player's own board edge where nothing was there to trigger it — the cube just silently got stuck trying to flee forever. The fix is `PositionExists POSITION` (confirmed real, used by the base game's own `Star_Gift`/`Sky_Vine` cubes for exactly "is this the edge of the map" checks, e.g. `Main/2TokenCubes.c.txt`'s `Star_Gift`: `If Not PositionExists PositionInDirectionFromPosition North PositionOfThis Both Die ...`) — `Or` it alongside the `CubeInDirectionFromCube` check to catch both kinds of blocking.

**Confirmed via real in-game testing (both edges of the map): `EventDirection` does not reliably report `Backwards` for a `FleeEveryX`-driven move.** Wiring the combined check above through a shared `EventDirection` (one `Ability:` reacting to whichever direction the trigger reports) fixed the charging-direction/forward-edge case, but the fleeing-direction/backward-edge case silently never fired — confirmed fixed by switching to the literal `Backwards` constant instead of `EventDirection` (see below), with no other change, and user-confirmed working on both sides of the map afterward. Treat this as a real, load-bearing gap for any cube reacting to `BeforeThisMoves`/`EventDirection` on a cube that also holds `FleeEveryX` — don't rely on `EventDirection` alone once `FleeEveryX` is in play, even though it demonstrably works fine for the `Forwards`/`ChargeEveryX` case.

**The robust fix: derive the direction to check from which movement ability the cube currently holds, not from `EventDirection` at all.** Since `Forwards`/`Backwards` are themselves valid `DIRECTION` literals (same production list as `North`/`South`/`East`/`West`, confirmed via `Climbing`'s own `IsSameDirection EventDirection Forwards` check), every place `EventDirection` was used above can instead be replaced with the literal `Forwards` or `Backwards`, picked via whichever of `ChargeEveryX`/`FleeEveryX` is currently held — sidestepping `EventDirection` entirely:
```
Ability: BeforeThisMoves IfElse HasAbilityWithName Caster ChargeEveryX
 If Or CubeExists CubeInDirectionFromCube Forwards Caster
  Not PositionExists PositionInDirectionFromPosition Forwards PositionOfThis
  <effect when charging is about to be blocked>
 If HasAbilityWithName Caster FleeEveryX
  If Or CubeExists CubeInDirectionFromCube Backwards Caster
   Not PositionExists PositionInDirectionFromPosition Backwards PositionOfThis
   <effect when fleeing is about to be blocked>
```
Combining both patterns, a full "patrol until blocked, then reverse" cube needs only ONE reversal `Ability:` instead of two (real before/after comparison: General mod's `Bomber` cube originally used the two-`AfterThisMoves`-blocks shape above keyed on enemy-leader detection, then the `EventDirection`-based single-trigger shape, then this ability-state-keyed shape once the `EventDirection`/`Backwards` gap surfaced in actual play — see `GameData/General/General_Cubes.c.txt`).

## Preserving a dynamically-granted ability through a "replace this cube with a different cube" cascade

A perk that intercepts cube creation and substitutes a different cube type (`AfterACubeIsCreated: If CubeHasName Victim X, Exile + CreateCubeOnPosition CubeConstant Y`, e.g. an ammo-tier upgrade chain) creates a **fresh** cube from `Y`'s own template — it does NOT inherit any ability that was dynamically granted to the specific `X` instance being replaced (e.g. `Arcing`/`ChargeEveryX` granted only to that one fired shot, not baked into `X`'s or `Y`'s `CUBE:` definition). Trying to thread that grant through every substitution rule (checking "did the replaced cube have Arcing, if so re-grant it onto the replacement") works but tightly couples the substitution perk to the granter's internal mechanics, and has to be repeated at every tier of the cascade.

**Cleaner: decouple the two concerns entirely.** Have the *original granter* (the cube/perk that dynamically granted the ability in the first place) apply it *after* creation, by looking up whatever cube currently occupies the target position — rather than attaching it to the specific instance being created:
```
Ability: EveryXSeconds DoubleConstant 20 Both CreateCubeOnPosition CubeConstant Shell PositionInDirectionFromPosition North PositionOfThis
 If CubeExists CubeOfPosition PositionInDirectionFromPosition North PositionOfThis
  TargetCube CubeOfPosition PositionInDirectionFromPosition North PositionOfThis
   Both GainAbility Arcing DoubleConstant 180
    Both GainAbility ChargeEveryX 15
     SetVariable ARCING RandomRoundBetweenXtoY DoubleConstant 17 DoubleConstant 25
```
This relies on the DSL's synchronous execution model: by the time the second half of the `Both` runs, any `AfterACubeIsCreated` reactions triggered by the `CreateCubeOnPosition` call above it (including a cascading substitution perk that itself replaces the cube one or more times) have already fully resolved, so `CubeOfPosition` at that same position reliably finds whatever the *final* cube ended up being — Shell, or whatever it got upgraded into — with no coordination needed between the granter and the substitution perk at all. Note this also means `GainAbilityText AfterThisIsCreated ...` (the usual idiom for initializing a variable like `ARCING` on a freshly-created cube, see "Scan a hand, maybe graft a random ability" above) is the **wrong** tool here — the found cube was already created, so `AfterThisIsCreated` will never fire for it again. Use a bare, immediate `SetVariable` instead, since we're acting directly on an already-existing cube via `TargetCube`, not reacting to its creation.

**Corollary bug shape: don't bake a movement/behavior ability into just one cube of a substitution chain if its siblings don't share it.** A token cube meant to be swapped mid-chain (e.g. `Shot` → `Shell` → `Bomb` → `Rocket` via an `Arms_Race`-style ammo-tier perk) should either have ALL chain members share the ability, or none of them baked in (granting it dynamically at each creation site instead, per the pattern above) — never just one link. Real incident, an earlier version of the General mod's own `Bunker`/`Shot`: `Bunker` fires a burst of 3 `Shot`s from a fixed position, and `Shot` alone (not `Shell`/`Rocket`) had `Ability: ChargeEveryX 15` baked in to move it out of the spawn tile before the next burst-shot. This looked fine in isolation, but the moment the player also owned `Arms_Race` (Shot→Shell substitution), each fired `Shot` got `Exile`d and replaced by a fresh, immobile `Shell` (no `ChargeEveryX` baked into *its* block) — the substitution is a same-position replacement, so the baked ability never had a chance to matter, and the immobile Shell then blocked every subsequent burst (`IsPositionEmpty` never true again). That incident's fix at the time was the "dynamic grant at the spawn site" branch: strip `ChargeEveryX` from `Shot`'s own block, grant it via `Bunker`'s own post-creation lookup instead.

**A later session deliberately picked the other branch, and the reasoning is worth recording since both branches are legitimate depending on what's actually being asked.** When `Shot`/`Shell`/`Bomb`/`Rocket` were made independently obtainable/hand-placeable (real mana cost + `IDENT`), the ask was for all four to self-propel toward the enemy like a normal missile when placed directly from hand — which is only possible if the movement is baked into every one of them (a hand-placed cube has no spawner around to dynamically grant it anything). This reintroduced `Flying`+`ChargeEveryX 15` into all four `CUBE:` blocks uniformly (the "all chain members share it" branch, still satisfying the rule above), which made the *existing* per-spawner dynamic grants in `Bunker` (Shot), `Artillery` (Shell, alongside `Arcing`), and `Rocket_Silo` (Rocket, alongside `Take_Off`+`HomingX`) either purely redundant or actively conflicting (a second independent `ChargeEveryX` instance stacked on top of the baked one; or a baked forward-charge fighting `Rocket_Silo`'s intentionally-different vertical `Take_Off` launch).

**Before baking a new `Ability:` into a `CUBE:` that's already created by other cubes'/perks' abilities elsewhere in the codebase, grep every `CreateCubeOnPosition CubeConstant <ThatCube>` site first** (across the whole mod, not just the file being edited) — each hit is a place that might already dynamically grant something which now needs handling one of two ways:
- **Exactly duplicates the new baked ability** (e.g. `Bunker` granting the same `Flying`+`ChargeEveryX 15` `Shot` now has by default): delete the now-redundant grant from the spawner entirely.
- **Wants genuinely different behavior than the new default** (e.g. `Rocket_Silo` wants `Take_Off`'s vertical launch, not the new baked forward-charge; `Bomber`'s dropped `Bomb` needs to fall straight down, not fly off): keep the spawner's own grant, but first strip the now-unwanted baked ability at that one spawn site using the same `CubeOfPosition`-after-creation lookup, just with `RemoveAbilityWithName` in place of `GainAbility`:
```
Both CreateCubeOnPosition CubeConstant Bomb PositionInDirectionFromPosition South PositionOfThis
 If CubeExists CubeOfPosition PositionInDirectionFromPosition South PositionOfThis
  TargetCube CubeOfPosition PositionInDirectionFromPosition South PositionOfThis
   Both RemoveAbilityWithName Flying RemoveAbilityWithName ChargeEveryX
```
Real usage: `Bomb` got the same baked `Flying`+`ChargeEveryX` as its siblings for the direct-placement "flies like a missile" case, but `Bomber`'s own "drop a bomb below me" mechanic (and this mod's own `General-Shadow` synergy and `Bombardier` cube, both of which also create `Bomb` for a "drops from above" effect) all depend on that specific dropped `Bomb` falling straight down instead — all three of those spawn sites now strip `Flying`/`ChargeEveryX` off immediately after creating it, leaving the baked default (fly toward the enemy) intact for every *other* path a `Bomb` can come from (hand-placement, `General-Devourer`'s "add to hand" synergy, landing at the end of an `Arms_Race`-chain substitution). This scales to as many "opt this one spawn site out" cases as needed — each is independent and doesn't affect the others.

## `BeforeACubeDies`-granted buffs do apply to that same death's damage (e.g. `ExplodesX`/`BeforeThisDies` splash)

A perk that grants `StrengthX` (or similar damage-boosting ability) via `BeforeACubeDies` fires early enough to affect that cube's own death-triggered damage (its `ExplodesX`, or a custom `BeforeThisDies` explosion) — confirmed by the base game's own `Stronger_Blasts` perk (`Characters/Classes/Pyromaniac.c.txt`: `Ability: BeforeACubeDies TargetCube Victim GainAbility StrengthX 2`), whose own `Description:` states the point directly: "increasing its damage by 2." `StrengthX` itself hooks `BeforeThisDealsDamage` (`Base_Core/1Compounds.c.txt`), a generic per-damage-instance hook that fires regardless of *how* the damage is dealt (melee, `TakeXDamage`, `ExplodesX`, etc.) as long as the granting happened before that damage instance resolves — so `BeforeACubeDies: grant Strength` reliably lands in time for a same-cube death explosion, no special ordering trick needed.

## Gravity is a real, literal per-tick falling mechanic — not just flavor text, and there's no separate stacking/z-axis

There is **no cube-stacking/altitude/z-axis system at all** — "above"/"below" a cube always just means the North/South grid neighbor tile (confirmed via `NoCubeAbove`, `AboveExists`, `TopPositionAboveCube`, and dozens of real cubes like `Slime_Transport_Belt`/`Healing_Pillar` that read "the cube sitting on me" as `CubeInDirectionFromCube North Caster`). Don't reach for a stacking mechanic that doesn't exist when a mod concept sounds like it needs "layers."

`PERK: Gravity` (`Base_Core/GameRulePerks.c.txt`) is a real per-tick effect — a `WorldCube` moves every cube one tile in `GravityDirection` (South by default) ~15×/second unless negated — but it's technically opt-in per scenario (`SCENARIO:` blocks each list `PERK: Gravity` explicitly), not a hardcoded engine rule. In practice it's granted by every normal-play scenario checked (`Tutorial`, `Campaign`, `Random_Daily_Campaign`, `Mirror_Breaker`, the `Extra_Mechanics` node-map campaign) so treat it as baseline-on for any mod targeting normal play.

**The negation idiom**, used by every real gravity-immunity ability (`Flying`, `Hovering`/`Advanced_Hovering`, `Buoyant`): hook `BeforeThisMovesNegation` (self) or `BeforeACubeMovesNegation` (reacting to a *different* cube's fall) and check `If IsSameCube Culprit WorldCube` before negating — this specifically targets gravity-caused moves without blocking the cube's own `ChargeEveryX`/`FleeEveryX`-driven moves, since those have a different `Culprit`. Conditional/partial negation (rather than a flat permanent immunity like `Flying`) is a normal, precedented shape — `Hovering` only negates `If CubeExists CubeOfPosition PositionInDirectionFromPosition South PositionInDirectionFromPosition South PositionOfCube Caster` (i.e. only while something is 2 tiles below it):
```
COMPOUND: ABILITY
Hovering
```

**`FreePlacement` only bypasses the placement-support check, not gravity itself** (`Base_Core/1Compounds.c.txt`: `BeforeThisIsPlaced NegateX DoubleConstant -10`) — a `FreePlacement` cube dropped over open space with nothing under it will fall via gravity, tile by tile, until blocked by another cube or the map edge. This is what makes a cube like the General mod's `Paratrooper` (`IDENT` + `FreePlacement`, no `Flying`) actually work thematically as "dropped from height, falls to the ground" with zero extra DSL — the fall is the base game's own gravity doing the work, not something the cube's own ability chain needs to implement.

## Rate-limiting a reactive trigger: `Cooldown DOUBLE Action`

For "whenever X happens, do Y, but at most once every N seconds" on a reactive (non-periodic) trigger like `AfterACubeTakesDamage`/`AfterACubeDies`/etc., use the real, well-precedented built-in gate `Cooldown DOUBLE Action` — self-chaining (takes exactly one trailing `Action`, same shape as `If`/`TargetCube`), DOUBLE in ticks (60 ticks = 1 second, same rate as everywhere else in this DSL). It is NOT a rare/undocumented primitive despite being absent from every skill file before this note — a plain `grep -r Cooldown GameData/` (system grep, not this harness's `Grep` tool — see the tool-reliability warning in `cube-chaos-mod-setup`) turns up 40+ real usages across `Main/Perks.c.txt`, `Main/UpgradePerks.c.txt`, `Main/Curses.c.txt`, `Characters/Synergies.c.txt`, `Characters/2TokenCubes.c.txt`, `Characters/Classes/Engineer.c.txt`, and more. Placement is exactly where you'd gate the effect, after the trigger's own condition chain and before the actual effect:
```
Ability: AfterACubeTakesDamage If And IsAllyToCaster Victim IsALeader Victim
 Cooldown 600
  <effect Action>
Description: ..., cooldown 10 seconds End
```
Real precedent for the bare-vs-wrapped literal: both `Cooldown 600` (bare number) and `Cooldown DoubleConstant 600` appear in real files — the parser accepts a bare literal directly in a DOUBLE slot here, same tolerance as `ChargeEveryX 180`, so prefer the shorter bare form unless the value is computed. No custom variable/flag-based cooldown scaffolding is ever needed — reaching for a hand-rolled `SetVariable`+`WorldTime`-delta gate (also real and real-precedented, but far more verbose) is solving an already-solved problem.

**Rule-text phrasing**: see `cube-chaos-rule-text`'s matching note — real usage is overwhelmingly lowercase `, cooldown N seconds/minutes` as a trailing comma-separated clause, not a capitalized or leading phrase.

## Debugging checklist

1. Read the exact error line — note whether it names a specific perk/cube ("OF PERK X") or not (unlabeled errors are often scoping/registration issues, not local syntax bugs).
2. Grep `GameData/**/*.c.txt` for real usage of the exact function/ability name you're using, and compare your call token-for-token.
3. Hand-count arguments against `ModdingInfo.txt`'s production list for anything you wrote from scratch.
4. Relaunch and recheck logs after every fix — see `cube-chaos-mod-setup` for the test loop.
