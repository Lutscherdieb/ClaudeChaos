# Workflow: Class/Species base perk, or a Class+Species synergy

**Before writing any file, run the orchestrator's Step C preview-and-approve gate** for either flow below: print the theoretical spec (granted cubes + the real passive/synergy `Ability:` chain + the `Text:` *derived from that chain*) and get the user's explicit OK, iterating on the printed table until they approve. Two wrinkles specific to this workflow: (1) a class/species color is itself a gated decision — confirm it with the user (per the "ask before picking colors" memory) as part of the spec, not silently; (2) the base-perk flow's color-pick step happens *before drawing* by necessity, but the actual sprite pixels — like every other content type — are still drawn only after the design OK.

## Class or Species base perk (`BelongsTo: CLASS` / `BelongsTo: SPECIES`)

Exactly one of these per class/species — it's what grants the starting cubes.

1. Gather: class/species name, starting cube(s) it grants (`ObtainAction: AddCubeToInventory CubeConstant X`), `LevelRequirement:` if any, what its passive `Ability:` (if any) does.
2. **`cube-chaos-sprite-art`** first this time, not last — before writing anything, pick an unused color via the color-dump snippet (dump the dominant non-background color of every existing class's/species's first tile, avoid reusing one). This color is used in *two* places (the icon fill and the border), so nail it down before drawing.
3. **`cube-chaos-scripting`** — the `PERK:` block, `Ability:` + `Text:` if it has a passive effect, `ObtainAction:` lines for starting cubes.
4. **`cube-chaos-rule-text`** — review the `Description:`.
5. **`cube-chaos-sprite-art`** — draw the icon: solid-filled in the chosen color, centered in the ~19×19 interior, then Style 1 border (`plain_class_border(chosen_color)`) from the border-pattern library — generate it, don't hand-copy pixels from another tile.
6. **Generate/refresh `GameData/<Mod>/Image.png` from this same tile** — this is the mod's Steam Workshop thumbnail, and for a single-class/single-species mod it defaults to that class/species's own base-perk icon (the tile just drawn in step 5), not something separately commissioned. Crop the tile, strip the 1px magenta guide-ring border (fine as an in-game tile edge, reads as an unwanted pink frame standalone), nearest-neighbor upscale to ~500×500 — exact recipe and rationale in `cube-chaos-mod-setup`'s `references/workshop-publishing.md`, don't duplicate it here, just follow it. Re-run this step any time the base-perk icon itself changes. If the mod already has more than one class/species (no single obvious "default" icon), skip the auto-default and ask the user what `Image.png` should show instead.
7. **Test-launch.**

If this mod wants to extend the class color as a family-branding border onto its *other* reward perks too (not just the one base perk), that's a deliberate, optional style choice — see `cube-chaos-sprite-art`'s "Optionally extending the class-color border" section — reuse the exact same RGB, don't invent a near-miss shade.

## Class+Species synergy (`BelongsTo: CLASSSPECIES`)

Named exactly `<ClassName>-<SpeciesName>` (e.g. `DJ-Plant`) — that naming, not a separate field, is what makes the engine recognize it as the synergy for that pair.

1. Gather: which class+species pair(s), what the synergy effect does.
2. **`cube-chaos-scripting`** — the `PERK:` block and `Ability:`/`Text:`.
3. **`cube-chaos-rule-text`** — review the `Description:`.
4. **`cube-chaos-sprite-art`** — this one's mandatory border is the CLASSSPECIES fancy frame (Style 4 in the border-pattern library — apply the literal baked mask, don't re-extract it from a reference file), and character art placement is **bottom-anchored, not centered**: horizontally centered between cols 6–20, but the lowest non-background pixel must land on row 20 with zero gap. This is the single most commonly-missed detail in this style — verify with an actual bounding-box measurement, not by eye.
   - **When drawing a whole batch of synergy tiles at once (one mod × several classes, or one mod × several species), ask the user up front for a shared visual identifier to thread through every tile** — the same idea as DJ's synergy set sharing a headphones motif across all its species portraits, or Unholy's sharing demonic horns across all its class portraits (2026-07-25). Whichever side of the pair is *fixed* across the batch (the mod's own class or species) is what needs a consistent visual anchor so the set reads as one family at a glance — don't silently invent one. Ask before drawing, same footing as the color-pick gate above.
   - **The shared identifier is a small connecting thread (e.g. horns), NOT license to reuse one shared silhouette with a different small icon glued on beside it per tile.** A first pass on Unholy did exactly that — one identical demon bust + a same-sized floating class-colored symbol next to it, repeated 11 times — and the user rejected it on sight as "too sameish," asking for each tile to read as a genuinely distinct variant instead (a Demon *Warrior* in armor with a sword, a *Burning* Demon wreathed in flame, etc.), the same "tie the silhouette to the actual theme, don't just palette-swap/prop-swap one template" lesson `cube-chaos-sprite-art`'s dragon-line corollary already documents for Baby/Adult dragons. Build each tile's body/head shape genuinely differently (armor + helmet, a hood + robe, a boxy glitchy body, flame/ice-shard shoulders, etc.) around the one shared small identifier, not a fixed body with a swappable accessory.
   - **At 27×27 with only a ~15×15 safe interior, a shared identifier plus a per-class body variation will not both fit as independently-centered elements** — a full silhouette alone can span nearly the full safe width if drawn front-and-center. Design each tile's whole silhouette (shared identifier included) as one composition from the start, off-centering pieces as needed, rather than drawing a fixed base first and trying to wedge something else into whatever space is left — a first pass centered a demon bust alone, left no real gap, and a bolted-on side prop overflowed past column 20 into the frame's own border band. Verify the *combined* bounding box of everything on the tile, not just the main body, against the row 20/cols 6–20 rule.
   - **Small/thin decorative details (a sword blade, an ice-spike tip, a gear's spokes) must be composited AFTER the main silhouette's auto-outline pass, never unioned into it before that pass runs.** The auto-outliner recolors any pixel touching background to flat outline color, and an isolated small shape is *nearly all* boundary pixels, so running it together with the main body swallows the whole small shape into a flat near-black blob with no visible color at all — this is `cube-chaos-sprite-art`'s own documented "practical build technique" pitfall (from the `Hell_Dragon`/`Bass_Dragon` wing/sound-wave case) and it recurred here despite that precedent, so it's worth restating at the synergy-portrait scale specifically: draw the main body mask → outline it → THEN paint every small accent shape directly in its final color.
   - **Small per-item details also need solid, blocky fills, not thin 1-2px line art** — thin outlined strokes render as illegible scribbles at 27px once thresholded down from a high-res working canvas. Prefer filled polygons/rectangles, and if built via the high-res-draw-then-threshold pipeline, use a lower threshold (~60 instead of ~120) for small accent shapes specifically so they survive the downscale (see `cube-chaos-sprite-art`'s "Color composition" section, which already recommends this for tiny accents like eyes — the same fix applies to any small themed prop).
5. **Test-launch.**
