# Cube Chaos mod scaffolding & testing workflow

For the DSL used inside the `.c.txt` files themselves (CUBE:/PERK:/Ability: syntax), see the `cube-chaos-scripting` skill. For sprite sheet sizing/coloring, see `cube-chaos-sprite-art`. This skill is just the surrounding plumbing: folder layout, activation, and the test loop. For getting a finished mod onto the Steam Workshop (the game's own in-game publishing UI, its `Image.png`/tag requirements), see `references/workshop-publishing.md`.

**Always add new content inside the active mod's own package folder (e.g. `GameData/DJ/`), never into a base-game package (`Base_Core`, `Extra_Mechanics`, `Characters`, `Main`) or another mod's folder — even for content that's conceptually "attached" to a base-game class/species (a new reward perk `BelongsTo:` an existing species, a new synergy for an existing cube, etc).** Cross-package references work fine for this — `BelongsTo: <SpeciesName>` correctly attributes a perk to a species defined in a totally different package with no special syntax, confirmed by adding a DJ-mod perk with `BelongsTo: Fungus` (Fungus itself is defined in `Characters/Species/Fungus.c.txt`) and seeing it picked up cleanly, including the engine's own reward-perk count for that species going up by one. If you catch yourself editing a file under `Base_Core/`, `Characters/`, `Main/`, or `Extra_Mechanics/`, stop and re-home that change into the mod folder instead — do not leave modded content living in the base game's own files, and don't forget to revert any base-game file you already touched by mistake (including any sprite sheet you painted into) back to its original state.

## Research protocol — this skill first, base game second, write back always

1. **Check this skill first.** Folder structure, `Loading_Order.txt`, the `Description` format, filename collisions and the expected-vs-real log warnings are all below. If it's covered, use it and stop.
2. **If not covered, the ground truth is what the engine actually does, not what a file implies.** In order: `ModdingExplanation.txt` for block/definition structure, the base game's own `GameData/<Package>/` folders as a working reference layout, and then **`%APPDATA%/CubeChaos/Log.txt` after a real launch** — the log is authoritative where the files are only suggestive. Runtime and UI behaviour in particular cannot be inferred from data files: the game has an in-game Mods screen whose toggles are not visible anywhere in `Loading_Order.txt`, and shop candidate selection is engine-internal with no `.c.txt` representation at all. If a question is about what the *engine* does, the honest answer may be "not determinable from the files" — say so rather than inferring.
3. **Write the finding back into this skill, in the same edit** — including the exact log line text if you diagnosed something from the log, since the next person will be grepping for that string.

**Never edit base-game files or the root `ModdingInfo.txt`/`ModdingExplanation.txt`** (see `CLAUDE.md`).

## How the game discovers content

Every top-level folder under `GameData/` is a "package" (Base_Core, Extra_Mechanics, Characters, Main are the base game's own packages). `GameData/Loading_Order.txt` lists which package folders actually get loaded, **in order, one per line**. A folder that exists but isn't listed is completely inert — e.g. `GameData/Modding_Example/` ships with the game but is deliberately absent from `Loading_Order.txt`, so editing it has zero effect. This is a common trap: don't assume a folder is "the mod" just because it looks mod-shaped: check `Loading_Order.txt`.

**The engine tokenizes EVERY file in a loaded package folder, not just `.c.txt` — including `README.md` and any other doc.** Confirmed at load: `Log.txt` shows `Cut Into Words Test<...>` lines for a doc's own Markdown headers. This is harmless *as long as no bare (non-backtick-wrapped) DSL keyword the parser recognizes appears anywhere in the doc* (`CUBE:`, `PERK:`, `Ability:`, `COMPOUND:`, `Description:`, `Text:`, etc.) — the tokenizer just finds no valid block and moves on.

**Real incident, 2026-07-25 — the danger is NOT limited to "starts a line" as this note previously (incorrectly) claimed.** A prose sentence in a mod's (now-removed) design doc read "...mana/hp for every cube: `Unholy_Cubes.c.txt`**" — `cube:` was a bare lowercase word mid-sentence, nowhere near the start of its physical line, immediately followed by a backtick-wrapped filename. On next launch the game flooded `Log.txt` with thousands of `ERROR: CAN'T READ GENERAL CUBE PART (<word>) OF CUBE \`Unholy_Cubes.c.txt\`**` / `ERROR: FAILED TO INTERPRET AS NUMBER: <word>` lines — one per subsequent English word in the file — because the tokenizer matched `cube:` (apparently case-insensitively; the real `CUBE:` keyword is uppercase) as a block start, took the very next token (`` `Unholy_Cubes.c.txt`** ``) as the cube's *name*, and then kept consuming every following word as an attempted cube body/number, cascading indefinitely with no natural terminator — the exact "one wrong token desyncs everything downstream" failure shape `cube-chaos-scripting` describes for real `.c.txt` parsing, just triggered from a Markdown doc instead. Fix was a two-word reword (`for every cube:` → `for every cube lives in`) breaking the bare `cube:` pattern; confirmed fixed via an actual test launch (0 `ERROR`/`CANT READ` lines, clean `Saved Profile on exit`).

**The corrected rule: a DSL keyword must never appear as a bare, non-backtick-wrapped word immediately followed by `:`, anywhere in a `README.md` or other package-folder doc — not just at the start of a line, and this applies however the keyword is capitalized.** Markdown tables (`| \`CUBE: ...\` |`) and fully-backtick-wrapped inline code (`` `PERK: Name BelongsTo: X` ``) are still safe — those were tested and are unaffected — the danger is specifically a *bare* keyword-colon token with nothing protecting it. When writing prose that needs to say "cube:"/"perk:"/etc. as an ordinary English word immediately before a colon, reword to break the colon-adjacency (e.g. "every cube lives in `X.c.txt`" instead of "every cube: `X.c.txt`") rather than assuming casing or line-position makes it safe.

**Second real incident, same shape, different keyword (2026-07-25, from a mod's now-removed design doc):** "a small helper compound: when the `Damned_Soul` later dies, ..." — bare `compound:` immediately followed by `when`, matching `COMPOUND:` case-insensitively. Produced `ERROR: Couldn't figure out part of compound: when in package: Unholy`, repeated dozens of times (same cascading-desync shape as the `cube:` incident, just with an `IN PACKAGE:` tag this time instead of no tag at all — labeling isn't consistent, don't rely on a label being present to recognize this failure mode). Fix was identical: break the colon-adjacency (an em dash instead of a colon before "when"). **Any of the DSL block-start keywords can trigger this, not just `CUBE:`** — `PERK:`, `ABILITY:`(as part of `Ability:`), `COMPOUND:`, `TEXT:`, `DESCRIPTION:` are all real block/field starters per `cube-chaos-scripting`'s grammar, so treat this as a blanket rule for the whole keyword vocabulary, not a `CUBE:`-specific quirk. When auditing a `README.md` (or any package-folder doc) for this class of bug, grep it case-insensitively for each keyword followed by `:` (`grep -i 'compound:\|ability:\|perk:\|cube:\|text:\|description:'`) and check every hit is either inside backticks or not actually keyword-shaped.

**Third real incident, a DIFFERENT shape — no colon needed at all (2026-07-25, from a mod's now-removed design doc):** the prose "would let a misplaced Leader **end** the battle instantly" — a completely ordinary, lowercase, colon-free English word — produced `ERROR: excess 'End' in package Unholy` on every launch. Isolated by bisection (binary-search reverting/reapplying paragraphs and relaunching between each): with that one sentence present the error reproduced 100% of the time; changing only that single word (`end` → `finish`) made it vanish, with every other new paragraph in the same edit left untouched. **The bare terminator keyword `End` itself — not just the six block/field-*starter* keywords above — is dangerous as an ordinary word, case-insensitively, with NO colon required and NO backtick-wrapping tested as a mitigation (unlike the starter-keyword incidents, this one was fixed by rewording, not by adding backticks — backtick-protection for a bare `End` was not verified and shouldn't be assumed safe by analogy).** This makes sense once you know the shape of the underlying parser: `CUBE:`/`PERK:`/etc. need a colon to *open* a fake block, but `End` doesn't need anything to *close* whatever's currently open in the package's combined token stream — so any bare "end" anywhere in a tokenized doc can consume a real block's intended terminator early, leaving a later legitimate `End` with nothing left to close (`excess 'End'`, as opposed to the "missing End"-shaped errors the first two incidents produced). **Grep every `README.md` (or other package-folder doc) edit for the standalone word, case-insensitive** (`grep -noiE '\bend\b' path/to/file.md`) and reword any hit (e.g. "end the battle" → "finish the battle") — do not rely on backticks to protect it since that mitigation is unconfirmed for this specific keyword. Words containing "end" as a substring (`ending`, `ended`, `weekend`) were not implicated and are presumed safe (the tokenizer splits on word boundaries), but were not separately stress-tested — if a future incident implicates one, update this note.

**`Loading_Order.txt` inclusion is necessary but not sufficient — the game also has its own in-game Mods screen (from the main menu) where each listed mod must be toggled on.** Confirmed directly by the user (not discoverable from data files — it's compiled UI, not GameData config): a mod can be correctly scaffolded and present in `Loading_Order.txt` and still not actually be active in a run until it's also enabled from that screen. When writing install instructions or when a test-launch doesn't show expected content, check both — don't assume `Loading_Order.txt` alone is the whole activation story.

To create a new mod:

1. Make a new folder: `GameData/<YourModName>/`.
2. Add a `Description` file (plain text, no extension) directly in that folder:
   ```
   ID: <random unique 10-digit number>
   Name: <YourModName>
   Tag: <TagFromWorkshopList>
   Tag: <AnotherTagFromWorkshopList>
   End
   ```
   The `Tag:` values aren't actually freeform — the game validates them against a fixed 12-value list at Workshop-publish time (`Classes/Species`, `Perks`, `Cubes`, `Terrain`, `Scenarios`, `Curses`, `Events`, `Consumables`, `Modding`, `Resprite`, `Balance`, `NodeMap`) and warns on anything else. See `references/workshop-publishing.md` for the full picture; picking real values from that list up front avoids a rename pass later.
3. Add one or more `.c.txt` files containing your `CUBE:`/`PERK:` definitions (see `cube-chaos-scripting`).
4. Add a `Sprites/` subfolder with `.c.png` files matching each `.c.txt` file's basename (see `cube-chaos-sprite-art`).
5. **Append your folder name as a new line at the end of `GameData/Loading_Order.txt`.** Without this step nothing you wrote will ever load, no matter how correct it is. It's still not *active* until also toggled on in the in-game Mods screen (main menu) — see above.
6. Do **not** create a `README.md` yet — see the governance note below on when to.

## `README.md`/`Preview/` governance: create late, not at mod creation

**Don't create a mod's `README.md` as part of initial scaffolding, and don't create one proactively partway through a session of adding content.** A README that exists has to be kept in sync on nearly every subsequent change (new content, sprite edits, wording tweaks — see the maintenance rule below), which is real ongoing overhead for a mod that's still taking shape and could still be renamed/restructured/abandoned. This timing is controlled by `.claude/preferences.local.md`'s `readme_timing` setting (default: `late-ask-first`, i.e. exactly what's described here — see `cube-chaos-repo-setup`); per that default: create a mod's README **as late as reasonably possible** — when the user asks for one directly, or when *you* judge a session's work has landed at a genuinely feature-complete point (a new mod with its initial content set built out, or a substantial addition that rounds out an existing mod) — and even then, **ask first** rather than just creating it. Surface the judgment call rather than deciding it silently: say something like "this feels like a natural point to add a README with preview cards, if you'd like one — want me to?" and let the user pick the timing. This applies to a brand-new mod (no README yet) and to an existing mod that has never had one; it does not apply to reducing maintenance on a README that already exists (see below).

## If a mod already has a `README.md`/`Preview/` folder, keep it current — this is the maintenance half of the same governance

Once a mod *does* have a `README.md` (the user asked for one, or agreed when you raised it), treat it as real content that must not go stale: every content or sprite change from that point on should regenerate previews and update the doc, same as this repo has always done. Don't ask again each time — the "ask before creating" rule is a one-time gate at README-creation time, not a recurring check on every edit once one already exists. Check for the file's existence (`GameData/<Mod>/README.md`) before assuming either governance branch applies.

## Each mod keeps its own `README.md` and `Preview/` folder (once one exists)

Every mod folder that has reached the point of getting a `README.md` (e.g. `GameData/DJ/`) keeps it self-contained — a short description, a `## Preview` section showing every cube/perk/curse/etc. rendered as a game-accurate tooltip card, and a closing `## Installing this mod (to play it)` section (the 3-step "find your install folder / copy this folder in / enable the Mod" instructions, e.g. `GameData/DJ/README.md`). Category subheadings in that Preview section should be bare (`### Cubes`, `### Perks`, ...) rather than listing every item's name in the heading — the cards themselves already show each name, so repeating them in the heading is redundant.

**Revised 2026-07-31 — a per-mod README stops at "Installing this mod," full stop.** Earlier revisions of this skill also had every per-mod README carry a "monorepo-only note" callout plus its own "Regenerating the preview cards" section (reasoning: this repo might eventually split one mod per repo, so mark what wouldn't travel with it). The user has since decided to keep this as a single repository permanently — that whole premise no longer applies, so both are gone: no monorepo note anywhere, and the regen-command instructions live **only** in `cube-chaos-sprite-art`'s own `SKILL.md` (its "Rendering README preview cards..." section), never duplicated into a per-mod README. If you're updating an older mod's README and still see a `---` rule followed by a monorepo-only callout and/or its own `## Regenerating the preview cards` section, delete both — they're stale, not a mod-specific choice to preserve.

The preview images live in `GameData/<Mod>/Preview/` and are generated (never hand-drawn) by `cube-chaos-sprite-art`'s `scripts/render_preview_cards.py` — see that skill's "Rendering README preview cards..." section for what the script does, the reverse-engineered facts (font, border-cropping rules, keyword coloring) it encodes, and the exact regen command. Re-run it whenever a mod's content or sprites change, so `Preview/` never drifts from what the `.c.txt`/`.c.png` files actually contain. The script renders every mod registered in its own `render_mod(...)` calls at the bottom of the file (DJ, General, Unholy, Voidling, Broker, DJ_Voidling, Great_Wall, and Home_Turf_Advantage, as of this repo's current mods) — add a new `render_mod(os.path.join(ROOT, "GameData", "<YourMod>"), "<YourModPrefix>")` line there for a new mod rather than repointing the old single-mod `MOD_DIR`/`MOD_PREFIX` constants (grid sizing is computed per-category from the actual tile count, so it works unmodified for any mod's own cube/perk counts). **A Terrain-only mod's perk file uses a 7th category, `TerrainPerks`** (`<ModPrefix>_TerrainPerks.c.txt` + matching sprite sheet) — `build_terrain_perks()` in the script handles it the same as Curses/Consumables (no `Value:` line, since Terrain perks never carry one). **A mod with a `BelongsTo: Neutral` perk needs the `Neutral` category too** (`build_neutral()`, added 2026-07-31 alongside this repo's first Neutral perk, `Home_Turf_Advantage`) — both registered in `BUILDERS` alongside the other categories.

## The repo-root `README.md`/`WORKFLOW_OVERVIEW.md` are a separate thing from per-mod READMEs

Everything above governs a *per-mod* `GameData/<Mod>/README.md` — create-late, ask-first, self-contained. The repo root also carries its own `README.md` (a short, minimal overview: what the repo is, a table of mods each linking to its own README, how to use the Claude Code skills) plus `WORKFLOW_OVERVIEW.md` (a `mermaid`-diagrammed walkthrough of how a request moves through `cube-chaos-orchestrator` — routing, gates, domain skills). Unlike a per-mod README, **the root README isn't create-late/ask-first** — it's foundational repo documentation expected to exist from early on and stay minimal by design (details live in linked-out docs, not inline). **Keep both in sync as the repo actually changes**: a new mod gets a row in the root README's mod table; a change to the orchestrator's dispatch table, Step B menu, or gate sequence gets reflected in `WORKFLOW_OVERVIEW.md`'s diagram and skill table. `WORKFLOW_OVERVIEW.md`'s Mermaid diagram deliberately uses shape (rounded = start/end, diamond = question, hexagon = gate, rectangle = action) rather than custom colors to carry meaning, since GitHub's Markdown renderer doesn't reliably apply arbitrary CSS/theme-aware `classDef` colors the way a hosted HTML page can.

## Filename collisions (a silent, hard-to-diagnose bug)

The engine appears to key sprite/data association by **filename**, not full path. If your mod defines a file named e.g. `Perks.c.txt` and the base game (or another mod) already has `Main/Perks.c.txt`, your content can get silently mis-associated with the OTHER file's sprite sheet — no error, just wrong icons rendered from the wrong sheet. Before naming a file, grep the whole `GameData` tree for that exact basename:

```bash
find GameData -iname "YourProposedName.c.txt"
```

Prefix every file with your mod's name (`DJ_Perks.c.txt`, `DJ_Cubes.c.txt`, `DJ_Synergies.c.txt`) rather than using generic names like `Perks.c.txt`/`Cubes.c.txt`/`Synergies.c.txt` — those are exactly the names the base game itself tends to use.

**`IsUpgradeFrom:` perks belong in their own `<ModPrefix>_UpgradePerks.c.txt`, never mixed into `<ModPrefix>_Perks.c.txt`** — this matches the base game's own convention (`Characters/Classes/ZUpgradeClassPerks.c.txt`, `Main/UpgradePerks.c.txt`, etc. are all separate, sprite-less files) and sidesteps a whole class of sprite-sheet slot-counting bugs. See `cube-chaos-sprite-art`'s upgrade-perk section for the full reasoning — this file needs no matching `Sprites/*.c.png` at all, since an upgrade perk always visually reuses its base perk's icon.

**Every other perk-family category (Curse, Consumable, Blight, Boon, Golden, Neutral) also gets its own `<ModPrefix>_<Category>.c.txt` file with its own matching `Sprites/<ModPrefix>_<Category>.c.png`, never mixed into `<ModPrefix>_Perks.c.txt`** — the same one-category-per-file discipline as the `IsUpgradeFrom:` rule above, just generalized to every category, not just upgrades. This mirrors the base game's own layout (`Main/Consumables.c.txt`, `Characters/Sprites/Curses.c.png`, etc. are always their own files, never appended to `Main/Perks.c.txt`) and this repo's own DJ mod (`DJ_Curses.c.txt`, `DJ_Consumables.c.txt`, separate from `DJ_Perks.c.txt`). **Real incident, the General mod (2026-07-27):** two new `BelongsTo: Consumable` perks (`Moral_Booster`, `War_Supply`) were first written straight into `General_Perks.c.txt` (which otherwise holds only `BelongsTo: General`/`BelongsTo: CLASS` reward perks) — user caught it and asked for the DJ-style split, requiring the two `PERK:` blocks to be moved into a new `General_Consumables.c.txt`, their sprite tiles relocated from `General_Perks.c.png`'s next two slots (cleared back to plain background) into a fresh 2-tile `General_Consumables.c.png`, and the mod's own `Description` file updated with the matching `Tag: Consumables` line (see the `Tag:` list a few paragraphs up — a category getting its own file and getting its own Workshop `Tag:` are two halves of the same "this category is a first-class thing in this mod" signal, do both together). Decide the category-vs-plain-reward-perk split *before* writing the `PERK:` block and its sprite slot, the same way file-basename and name-collision checks happen before writing, not after — retrofitting it means moving both DSL text and sprite pixels. **But this "add a matching `Tag:`" step only applies to categories that are actually real Workshop tags — `Curses`/`Consumables`/`Terrain`/`Scenarios` are (see the `Tag:` list a few paragraphs up, sourced from `references/workshop-publishing.md`'s `ModManager.CorrectTags`), but `Blight`/`Boon`/`Golden`/`Nightmare`/`Neutral` are NOT in that fixed 12-value list.** A perk-family category getting its own file is still the right call regardless (the one-category-per-file discipline is a DSL/sprite-slot convention, independent of Workshop tagging), but adding e.g. `Tag: Neutral` to `Description` produces `Unknown tag Neutral detected` at publish/update time — real mistake caught in this repo (2026-07-31, the since-relocated `Home_Turf_Advantage` Neutral perk): tag a mod with a Neutral/Golden/Blight/Boon/Nightmare perk as `Tag: Perks` instead (it's still just a perk from the Workshop's point of view), never invent a tag matching the in-game category name.

## A class/species's own base perk and its ordinary `BelongsTo: <ThatName>` reward perks must live in ONE file, never split

`.c.txt` files within a single mod package appear to load in alphabetical-by-filename order (not `.c.txt` file-list/declaration order — there's no such list, just whatever's on disk), and a `PERK:`'s `BelongsTo: <ClassOrSpeciesName>` reference needs that class/species to already be registered (i.e. its own `BelongsTo: CLASS`/`BelongsTo: SPECIES` perk already parsed) at the point the referencing perk is parsed. **Real incident, the Voidling mod (2026-07-30):** a new reward perk (`Void_Growth`, `BelongsTo: Voidling`) was put in a freshly-created `Voidling_Perks.c.txt`, separate from the species' own base `PERK: Voidling` / `BelongsTo: SPECIES` in the pre-existing `Voidling_Species.c.txt`. Load failed with `ERROR: Perk Void_Growth belongsTo Voidling can't be determined` — caused purely by alphabetical ordering: `Voidling_Perks.c.txt` (`...Pe...`) sorts before `Voidling_Species.c.txt` (`...Sp...`), so the species wasn't registered yet when `Void_Growth` was parsed. Confirmed by cross-checking every real base-game/mod precedent: **every class/species's base perk and its plain reward perks always live in the SAME file** — DJ's `PERK: DJ` (`BelongsTo: CLASS`) and its reward perks (`Echo`, `Symphony`, `Bass_Drop`, etc., all `BelongsTo: DJ`) all share one `DJ_Perks.c.txt`; Unholy's base `PERK: Unholy` and its reward perks (`Hell_Dragon_Egg`, `Phylactery`, `Mutations`) all share `Unholy_Species.c.txt` — there is no real example anywhere of a mod splitting these across two files. **Fix: always add a new `BelongsTo: <ThatClassOrSpecies>` reward perk into whichever single file already holds that class/species's own base `BelongsTo: CLASS`/`SPECIES` perk** (named `<ModPrefix>_Perks.c.txt` for a DJ/General-style mod, `<ModPrefix>_Species.c.txt` for a Unholy/Voidling-style species mod — check which basename the mod already uses, never assume `_Perks.c.txt` by default). This is a different rule from the category-split rule above (Curse/Blight/Consumable/etc. each getting their own file) — those are genuinely separate perk *categories* with no `BelongsTo:` cross-reference to the class/species at all, so no load-order dependency exists between them; a class/species's own reward perks are a special case specifically because of the `BelongsTo:` name resolution, and splitting them can silently work or silently fail purely based on where the two filenames happen to sort alphabetically. `IsUpgradeFrom:` perks are still the one legitimate exception (their own `<ModPrefix>_UpgradePerks.c.txt`, per the rule above) since an upgrade never carries `BelongsTo:` at all (see `cube-chaos-scripting/references/perk-economy.md`) — nothing there depends on the class/species being registered first.

## `CUBE:`/`PERK:` *name* collisions — a different bug from the filename collision above, same silent shape

The filename collision above is about two `.c.txt` files sharing a basename; this is about two `CUBE:`/`PERK:` blocks (in totally differently-named files) sharing the same *name* token — e.g. `CUBE: Claim` in a mod package when the base game already has its own unrelated `CUBE: Claim` (`Main/3GeneralCubes.c.txt`). **Real incident, the General mod (2026-07-27):** a new 0-mana territory-control cube was named `Claim`, not realizing the base game already has a real, obtainable `Claim` (35 mana, "convert the neutral cube below to your faction") in `Main/3GeneralCubes.c.txt`. Every `CubeConstant Claim` reference (the class perk's own hand-grant, in this exact mod) silently resolved to the *base game's* `Claim` instead — no parse error, no load warning, the mod's own `CUBE: Claim` block loaded fine and just was never reachable by name. This is what made it look, from the outside, like the granted cube already had "real art" (it did — it was the base game's fully-illustrated `Claim`, a completely different cube) while behaving nothing like what was written. **Before naming any new `CUBE:`/`PERK:`, grep the whole `GameData` tree for that exact name** (`CUBE: YourProposedName\b` / `PERK: YourProposedName\b`) — scoped per-subfolder (`GameData/Main`, `GameData/Base_Core`, `GameData/Characters`, `GameData/Extra_Mechanics`, plus every other mod folder), not a single whole-tree grep, since this repo's grep tool can silently return zero results when scoped to the full `GameData` directory (the install path's space is the suspected cause — see the debugging-checklist note below). Fixed here by renaming to `Annex`, confirmed collision-free the same way. This check belongs at the same point as picking a new file basename — both are "pick a name, grep first" habits, just checking a different string.

## The test-and-iterate loop

There is no hot-reload: the game parses all `GameData` content fresh at startup. After every edit:

**The game has an in-game debug console** (bindable via Options → Rebind Keys, no default key) that executes typed
text through the exact same DSL parser as `Ability:`/`ObtainAction:` fields — useful for spawning a mod's cubes/
perks straight into a run (`AddCubeToInventory CubeConstant X`, `AddCubeToDeck CubeConstant X`, `ObtainPerk
PerkConstant X`, ...) or for opening a live parse-error screen (`ERROR`) without waiting for a clean exit and
`Log.txt` read. See `references/console-commands.md` for the full command grammar and a caveat about the
`Campaign.Cheated` flag it sets on the save. This speeds up manual iteration but doesn't replace the `Log.txt` check
below as the pass/fail signal reported back to the user.

1. Kill any already-running game process first (`Get-Process -Name javaw | Stop-Process -Force` on Windows) — a stale running instance will not reflect new edits, and you'll waste a cycle thinking a fix didn't work.
2. Launch the game (`Cube Chaos.exe`), wait several seconds for full boot (loading + sprite-cutting takes a couple seconds, but give it ~10-15s margin before checking).
3. Check `%APPDATA%/CubeChaos/Log.txt` (Windows: `C:\Users\<user>\AppData\Roaming\CubeChaos\Log.txt`) for `WARNING`/`ERROR` lines, and check `CrashLog.txt`'s modification time to confirm no new crash occurred. Also check the launched process's own stdout if you redirected it to a file — some errors print there but not to Log.txt.
4. **Don't close the game after the log check** unless `.claude/preferences.local.md`'s `test_launch_behavior` is set to `auto-close` (default: `leave-running` — see `cube-chaos-repo-setup`). By default, leave it running at the Main Menu — the user wants to pick up manual testing themselves right after a clean log check, and closing it just makes them wait for a relaunch. Only kill it (step 1's command) if *another* edit is about to be tested immediately, not as a routine cleanup step.

**PowerShell gotcha when checking whether the process is (still) running:** `Get-Process -Name "Cube Chaos" | Select-Object ...` reports a nonzero exit from this harness's PowerShell tool when the process isn't found (a non-terminating error hits `Select-Object`'s empty pipeline and flips `$?` to false even with no visible exception text) — don't read that as the launch having failed. Use `$p = Get-Process -Name "Cube Chaos" -ErrorAction SilentlyContinue; if ($p) {...} else {...}` instead, and treat the actual `Log.txt` content (reaching `Saved Profile on exit` with no `ERROR`/`CANT READ` lines = a clean full boot-and-exit cycle) as the real signal, not process-liveness at whatever moment you happened to check — the game may have already booted, parsed everything, and exited on its own by the time you poll.

A clean `Log.txt` confirms the mod's files *parsed* correctly — parsing happens at boot for everything listed in `Loading_Order.txt` regardless of the in-game Mods-screen toggle above. It does NOT confirm the mod is actually enabled for play; that's a separate, human/UI-only check (there's no known way to verify or flip that toggle from the log or any GameData file), so don't tell a user "it's confirmed working" based on the log alone if what they actually asked about was whether they'd see it in a real run.

### Warnings you will see that are expected/harmless (not bugs)

- `WARNING: CLASS + X HAS 0 REWARD PERKS, BUT ATLEAST ONE HAS 9` — normal if your class only has its base class perk so far and no optional chest-obtainable reward perks yet.
- `WARNING: Missing: <YourClass>-<Species>` (once per species, ~12 lines) — normal until you've written `CLASSSPECIES` synergy perks for that class; each missing one just means that particular class+species combo has no special synergy defined yet.
- `WARNING: Couldn't innitiate steam API, is steam not on?` — unrelated to your mod, appears whenever Steam isn't running alongside the game.

### Scope sprite fixes to exactly the tile you're working on

A user may be hand-editing icons in the same shared sprite sheet PNG in parallel with your own edits in the same session. Confirmed real incident: while fixing one perk icon's border color, an earlier pass had reloaded and resaved a tile's full region instead of touching only that tile's own bounding box, which clobbered a user's in-progress hand-drawn art on that tile. When fixing/updating a single tile in a multi-icon sheet, restrict every read and write to exactly that tile's own `T`×`T` bounding box (including its own border pixels) — never touch, resample, or blanket-resave pixels outside the one tile you're intentionally changing. See `cube-chaos-sprite-art` for the tile-offset math and compositing recipes.

### Errors that mean a real bug in your files

- `WARNING: CUBE/PERK X IN PACKAGE Y ABILITY WITHOUT TEXT` — a custom `Ability:` line has no matching `Text:`/`Description:` right after it. See `cube-chaos-scripting`.
- `WARNING: Description of X changed twice` — a `PERK:` with 2+ `Ability:` lines each followed by its own `Description:` (that field is a single whole-perk slot, not per-ability like `CUBE:`'s `Text:` — one of the two descriptions gets silently dropped from the tooltip). Fix by using one `Description:` for the whole perk plus `AbilityText:` per individual `Ability:` line. See `cube-chaos-scripting`'s Text:/Description: requirement section.
- `ERROR: CANT READ ACTION/ABILITY/GENERAL PERK PART (token) OF PERK X` and `ERROR: excess End in package X` / missing End — a real parse/argument-count bug, almost always located EARLIER in the same ability chain than where the error surfaces (a miscounted argument desyncs everything that follows). See `cube-chaos-scripting` for the common causes and how to hand-count tokens.
- `ERROR: CANT READ ABILITY(Source) <name>` with no "OF PERK X" tag — often means the referenced ability is declared `LOCAL` to a different package and can't be used from yours. See `cube-chaos-scripting`.

When an error message doesn't clearly point at the bug, don't guess blindly — grep `GameData/**/*.c.txt` for real working usages of the exact function/ability name in question and compare token-for-token against your own line. **If a grep search against the whole `GameData` tree returns "no matches" for something you're confident is real, don't trust that result** — this repo's game-install path contains a space (`Cube Chaos`), and at least one grep tool has been observed to silently return zero results when scoped to the full `GameData` directory while working fine when scoped to a specific subfolder (`GameData/Main`, `GameData/Base_Core`, etc.) with the exact same pattern. Re-run against individual subfolders before concluding something doesn't exist.
